A run page that stays still

The run page no longer flickers, collapses or jumps while you filter and read.

  • Section bar: a bar under the run header takes you to Overview, Errors, Items, Latency and traces, with counts, and holds the item Filters.
  • Keeps your place: filtering, sorting, paging, searching or opening an item leaves the button you clicked where it was.
  • Why it failed, at a glance: every item row shows the reason it failed, and clicking a Pass, Fail or Error bar jumps to those items with a Clear filter banner.
  • Quieter step latency: it starts folded into one line, with normal text sizes. Open it when you need it.
  • Live runs: a running run updates in place with “Live · updated 3 s ago”, and stops when it ends.

Reviews as a queue

Reviews opens on what still needs you, and each project decides who may approve.

  • To review first: Reviews opens on pending corrections, oldest first, and loads quickly even with thousands of them.
  • Keyboard review: approve or reject, and the next card is ready.
  • Project approval rules: a manager can choose who approves corrections (all members, or managers only) and require a different reviewer than the author. Self-approved corrections are tagged.
  • Submit with a note: submitting a run asks for confirmation and an optional comment. Managers can submit for the owner, or hand a run to another member. Removing a member offers to hand over all of their runs.
  • Approved scores stay approved: scores of submitted or approved runs are locked, and every score edit is recorded with a Reset to original.

Every view has a link

Send a teammate exactly what you are looking at.

  • Links that remember: the Runs list, Charts, Models, Compare and Reviews keep filters, sorting, page and search in the address. So does the run page for its items (filters, search, sort, page, layout and columns), and the Overview for its trend range.
  • Link to an item: Copy link on an open item opens the run with that item open and highlighted.
  • Next run: up and down arrows in the run header open the previous and next run of the Runs list you came from, in its order and with its filters, across pages.
  • Back works: Back, Forward and reload return you to the same spot on the page.
  • Click through: run names, datasets, models, owners and projects are real links. Open them in a new tab as you like.

Compare that tells you what changed

Pick a baseline and see what really moved.

  • Baseline and noise: each metric shows its change against the baseline, with a band for normal run-to-run noise, and how many items got better or worse. Click a count to see those items.
  • Short names: runs are labelled by model and date. Hover for the full name.
  • Same data check: Compare warns when the runs used different datasets or versions.
  • Compare with previous: one button on the run page compares a run with the previous finished run of the same task, model and dataset.
  • Trend: the Overview dashboard shows how a task’s main metric moved over 7, 30 or 90 days.

Datasets you can search and trace

Find any item fast and see how a dataset changed over time.

  • Search everything: search matches item IDs, inputs, expected outputs and metadata, and stays fast on large datasets.
  • Changes in time order: lineage, compare and diff list changes in the order they happened, each with its time and who made it.
  • Big diffs load in pages: 50 changes at a time, with Show more.
  • Undo a delete: deleted datasets are listed and a manager can restore them.
  • Safer uploads: columns the wizard does not recognise are kept as metadata instead of being dropped.

A faster Runs list

Find a run in seconds, without the list shifting under you.

  • Search runs: press / and type part of a run name or ID.
  • Fast on big projects: the summaries behind Runs, Charts and Models are computed in the database and shared, so they open quickly on projects with thousands of runs.
  • Any date range: pick 30 days or your own two dates, on Runs, Charts and Models.
  • Calmer shortcuts: single-key shortcuts work only on the table, never while typing or in a menu, and can be turned off.
  • Every deleted run: Deleted Runs is a paged table across your projects, with search and bulk restore.
  • Instant status: after you submit or approve, the row shows the new status at once.
  • Selection kept: runs you check for Compare stay checked when you come Back, until you clear them.
  • Room for scores: on a laptop screen, frozen columns that would cover most of the table scroll until it fits. Your choice is kept.

✓UI, UX and fixes

Dialogs keep the keyboard inside, close on Escape and start on Cancel for anything destructive. Arabic text is right-aligned with comfortable line spacing on Reviews, datasets, traces and run details. Code and IDs use your system’s monospace font. Empty states such as “No datasets yet” appear only when there really is nothing, never after a failed load. Background tabs stop refreshing, toasts are read out by screen readers, and many smaller fixes across runs, Compare, datasets, reviews and admin pages.

⚠Before you update

No SDK update is needed. A few things now work differently.

Reviewed scores are locked

Scores of a submitted or approved run can’t be edited or reset. Reject or withdraw the decision first.

Production is for managers

Moving a dataset’s production alias or changing its slug needs a project manager, including from the SDK and CLI. Members still create, publish and delete their own datasets. A renamed dataset is uploaded to under its new name or its slug; the old name gets an error that says the new one.

Editing an approved correction

It goes back to To review, so someone approves the new version.

Decide only what is pending

Approve and Reject work on pending corrections, Reset on approved or rejected ones, also over the API. In the All tab, bulk actions skip the rows they don’t fit and say how many.

Deleting passes

Only the run’s owner, a manager or an admin can delete passes, and not on a submitted or approved run.

Fewer shortcuts

t, h and m are gone. Press ? to see the rest, or turn single-key shortcuts off.

Sign-in limits

After 5 wrong passwords, password sign-in for that email pauses for a few minutes, but only from the address that sent them. Signing in from anywhere else still works, unless the email collects 50 failed attempts from all addresses within 15 minutes.

For admins

  • The database upgrades by itself when the new version starts. Dataset search, run search and the project overview keep working while background jobs prepare their faster versions; you can follow them in Admin › Maintenance.
  • Open email sign-up is now off once an admin exists. Set QYM_AUTH_LOCAL_SIGNUP=true to keep it open.
  • Behind a load balancer, set FORWARDED_ALLOW_IPS so sign-in limits apply per user and not to everyone at once.
  • Only admins can rename a project, list all users or change roles, and an admin can’t remove their own admin role.
  • Optional: QYM_WEB_WORKERS runs several web processes per pod. See the operations guide.

After updating: open a run and try the section bar, then press ? on the Runs list. Full guidance is under Docs in qym.
