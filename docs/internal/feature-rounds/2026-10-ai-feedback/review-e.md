Not fixed, with the reason:

* **QE-9, QE-172**: Priority 101, Complexity 118 and the Request minimum 160 come from the DataTable header minimum (label + sort glyph + padding). Changing the primitive is outside a feedback fix pass and would move every table in the app.
* **QE-11 (1024)**: the consequence of the fix above. With a 168 px Request column a 30 to 40 character title wraps; keeping names whole (DESIGN_LANGUAGE section 7) wins over a fixed row height. A real fix is a wider Request column, which needs one column to leave the table below 1100 px (a design decision).
* **QE-55**: a scroll trigger needs scroll anchoring so the log does not jump when 50 messages are prepended; larger than a small fix.
* **QE-125 (request page)**: the loaded height depends on the request text, the number of events and related requests, and on whether the viewer is an administrator (triage panel in the rail). A skeleton can match the sections, not the height.

## 3. End-to-end flow against the stub (what I did and what the server stored)

All of it on SQLite; the PostgreSQL parts are the test runs in section 6.

* **Connection (administrator).** `PUT /v1/admin/feedback-agent` with base URL, model `feedback:<script>`, a dummy key: response `llm_api_key_set: true`, hint `••••7890`; column stored as a Fernet token (`gAAAAAB...`); the key is in no response, platform log, stub log, audit row or message row. `Test connection` in the page: success callout "Connected: feedback:ask_then_propose answered in 9 ms and called a test tool." and failures "the model does not support tool calls", "the key was rejected", "not reachable", each leaving the stored connection unchanged. `__KEEP__` is sent for a blank key. Behaviour: 0 days and 5 messages are refused by the API; the form clamps 0 to 1. Remove connection: dialog, then `/feedback` shows "The feedback assistant is not set up", `New feedback` disabled, `/feedback/new` shows the not-set-up page (member: `Browse requests`, administrator: `Open Feedback agent settings`). A server without `QYM_LLM_CONFIG_ENCRYPTION_KEY` shows the error callout naming the variable with Save disabled (API 400 `encryption_not_configured`); a server with another key answers turns with "The stored key cannot be decrypted. Save the connection again." for the administrator and "The assistant is not available." for a member. Key rotation (`reencrypt_llm_keys`, copy of the DB): scanned 1, reencrypted 1; the token then decrypts with the new key only; a second run reports `already_current`.
* **Subject step, both subjects.** Platform: radio group, textarea, one create on a double click. Product: Project select, `Point at` (Nothing, Run, Experiment, Dataset) and the project's runs ("text2sql on spider-dev", ...); a member without project access gets 403 `no_project_access` on create and on the targets route; `?subject=product&project=support-agent&kind=run` preselects. A product request with a run target was created and confirmed (FB-0011): meta `support-agent · run 0c390dd6` with a link to the run.
* **Checklist incomplete, then complete.** First message -> turn: the stub asks a question, checklist `1 of 6`, no proposal, phase `asking`. With the stub script `propose_too_early` (tries to propose with only the business need known) the server refuses: 0 proposals, the assistant asks again. Second message -> checklist complete (four filled, two declined: `6 of 6`), the assistant searches (`Searched requests for "pdf export compare", 5 results`, real ids), `propose_request` is stored, closing text streams, phase `proposed`.
* **Duplicate warning with real ids.** Script `duplicate_found`: related FB-0001 (duplicate) and FB-0002 (conflict) with titles and statuses filled from the database; callout "This looks like a duplicate of FB-0001", button `Submit as a possible duplicate` (194x24); after confirm the list row shows `Possible duplicate of FB-0001`.
* **Non-existent id.** Script `invalid_request_id` names FB-9999: the model is told twice, the server then stores the proposal without it (`repaired: [related:FB-9999]`, 0 related rows) and the log shows the muted line "The assistant's proposal named a request that does not exist. It was removed before you saw it." A draft uuid, a made-up id and four extra duplicates in one proposal were also cleaned (3 related kept, extra duplicates downgraded to `related`); a priority of `critical` asked for by the injected text stays what the model proposed and remains editable. `bad_scale`: nothing stored.
* **Edit and confirm.** Priority Medium -> High and Complexity M -> L ("You changed it from Medium." / "You changed it from M."), `agent_priority` / `agent_complexity` unchanged; description emptied disables Submit; stale `proposal_seq` 409; invalid enum 422; 422 and network failures keep the edits; submit -> `FB-0009`, toast `Submitted as FB-0009`; a second confirm is 409 `already_confirmed` with `request: FB-0011` and no new row.
* **Request page, Conversation tab, history.** Header 1193x72.4, tabs 1193x34, strip 827x104.8, confirmed card, history (newest first), Related card; the Conversation tab is read-only and ends "Dev User submitted the proposal · 18:58"; a member sees all of it without the triage panel.
* **Admin triage.** Priority without a note -> "Add a note: it is shown in the history." with focus on the note; with a note -> one `PATCH` with only the changed fields, toast, strip "Revised by Dev User on Oct 23 (was High).", history; complexity with a note; duplicate marking both ways (FB-0009 -> FB-0001 shows the callout on FB-0009 and "Marked as a duplicate of this request." on FB-0001; clearing it); `duplicate_chain` and `has_duplicates` ("Move its duplicates first.") refused; decline without a reason 422, with a reason the callout "Declined by Dev User on Oct 23 / Out of scope this quarter" shows for everyone; stale save -> "Someone else changed this request. Reload to see their changes."; triage of a draft 409 `not_confirmed` (404 for another user). Audit rows (entity `feedback_request`): `feedback.confirmed`, `.status_changed`, `.priority_revised`, `.complexity_revised`, `.duplicate_marked`, `.declined`, `.draft_deleted`, `.drafts_purged`, `.export`, `.agent_connection_updated/_tested/_removed`; `before`/`after` carry the changed fields only.
* **Drafts, resume, retention, limits.** The strip shows only the author's drafts (the administrator saw none of the member's); Resume/Discard name the draft; a 2-day-old draft shows "Welcome back"; the hourly purge (`run_purge`) deleted exactly the two drafts aged 40 days with their messages, kept 9 confirmed requests and wrote one `feedback.drafts_purged {count: 2}` row. * **Streaming and interruption.** First byte 14 ms; `Content-Type: text/event-stream`; one `done` per finished turn; the assistant text grows token by token with `writing…`, `aria-busy=true` on the streaming message, status words "The assistant is writing" / "The assistant answered"; `Stop` keeps the partial text marked `stopped` (persists after reload); a stream cut mid-answer keeps the text as `interrupted` with `Retry`; stub `down` (HTTP 500), `bad_key`, `no_tools` end with one `error` event and a Retry that does not duplicate the user message; a second turn while one runs is 409 `turn_in_progress` (the UI shows "The assistant is already answering in another window."); a phase older than 120 s proceeds.

* QE-132 (session ended / no access `ErrorState` variants): needs an expired session; judged from the shared component and the API's 401.
* QE-126 refresh-failed `StaleBanner`: present in `FeedbackListPage.tsx`, but no failing refetch could be provoked within the cache window.

* Real-model quality (five scripted topics against a real endpoint): no endpoint is configured here; only the scripted stub was used.
* QE-73's "Updated by the assistant" notice (needs a second proposal whose text differs) and QE-142's `aria-busy` on Submit: read from code only.

Observations (not criteria):

* The drafts strip lists every draft; with 19 drafts it is 640 px tall and pushes the table below the fold. Production is bounded by 5 new drafts per day and 30 days of retention, a test machine is not.
* A draft's title is empty ("Untitled draft") until a proposal exists; two drafts in the strip are then hard to tell apart (subject, message count and age are shown).
* A message beyond `max_user_messages` is still accepted (31 of 30 was sent); the cap forces a proposal, it does not block.
