Get started

Link your repo & create API keys

Point the SDK at your qym platform with two environment variables, then mint a project-scoped API key so your evaluation runs stream into the dashboard for shared review.

Everything in qym runs locally without any credentials — see Your first run. You only need to do the setup on this page when you want a run to show up in the platform: live progress, run history, comparisons, traces, and team review. Connecting is two pieces of configuration:

  1. QYM_BASE_URL — the URL of your qym platform deployment.
  2. QYM_API_KEY — a project-scoped key you create once in the platform UI.

When both are present, the SDK creates a platform run at the start of run() and streams events to it; the run's live URL is attached to the result as result.html_url. Without a key, the SDK runs entirely offline and writes artifacts to qym_results/.

There is nothing to "link" at the repo level. qym does not connect to GitHub or any version-control host. Git branch and commit are auto-detected per run from your working directory and recorded for version leaderboards — no integration or OAuth required. "Linking your repo" here simply means setting the two environment variables in the project you run evaluations from.

The two environment variables

Set these wherever you run evaluations — your shell, a .env file in the working directory, or your CI configuration. 

# The qym platform deployment to stream runs to.
QYM_BASE_URL=https://qym.example.com

# A project-scoped API key (created in the steps below).
QYM_API_KEY=your-project-api-key
Variable Required for streaming Default Notes
QYM_BASE_URL Yes http://localhost:8000 Public base URL of your platform. The SDK strips a trailing slash automatically, so https://qym.example.com/ and https://qym.example.com behave identically.
QYM_API_KEY Yes none The raw token returned when you create a project key. Platform streaming activates only when this is set.

Streaming is opt-out by default but key-gated. The SDK config field live_mode defaults to 'platform', but live UI/streaming only actually turns on when an API key is present (from QYM_API_KEY or config.platform_api_key). No key means no platform run is created — the evaluation still completes locally.

Loading a .env file

The SDK loads a .env file only from the current working directory, and only if you have python-dotenv installed. It deliberately does not walk parent directories, so it will never pick up an unrelated .env from a sibling repo or from site-packages. Keep your .env in the directory you launch evaluations from.

Create a project-scoped API key

API keys in qym are always bound to exactly one project. They are created from a logged-in browser session in the platform UI — a key cannot create another key, so the very first key always comes from the UI.

Step 1 — Pick or create a project

In the platform, open the project you want runs to land in (or create one). Each project has its own runs, datasets, members, and keys. The key you make next can only ever write to this project.

Step 2 — Generate the key

From the project's settings, create a new API key. Behind the UI this is a single authenticated request: 

POST /v1/projects/{project_id}/api-keys
Content-Type: application/json

{"name": "ci-runner"}

The request body is optional. If you omit name, the key is named default. The response returns the new key, with the raw token shown exactly once: 

{
  "id": "key_...",
  "prefix": "AbCdEfGh",
  "token": "AbCdEfGh...the-full-secret..."
}
Field What it is
token The full secret. This is the value you set as QYM_API_KEY. It is never returned again — only its hash is stored.
prefix The first 8 characters of the token, kept for display and lookup in the keys list. Not secret on its own.
id The key's database identifier, used to revoke it later.

Copy the token immediately. The raw token is generated with secrets.token_urlsafe(32) (a ~43-character URL-safe string with no qym_ prefix) and is shown only in this one response. The platform stores a PBKDF2-SHA256 hash, not the token, so it cannot show it to you again. If you lose it, revoke the key and create a new one.

Step 3 — Set it in your environment

Copy the token value into your environment, alongside the base URL:

export QYM_BASE_URL=https://qym.example.com
export QYM_API_KEY=AbCdEfGh...the-full-secret...

Step 4 — Verify the connection

The CLI ships a connectivity check that confirms the SDK can reach the platform and authenticate:

qym config check

Or confirm from Python by running any evaluation — when a key is configured, the result carries the live run URL: 

from qym import Evaluator, CsvDataset

result = Evaluator(
    task=my_task,
    dataset=CsvDataset("qa.csv", input_col="question", expected_col="answer"),
    metrics=["exact_match"],
).run(show_tui=False)

print(result.html_url)  # https://qym.example.com/projects/<slug>/runs/<run_id>

A populated result.html_url means the run reached the platform. See Your first run for the full task/dataset/metrics walkthrough.

How keys authenticate

The SDK sends every ingestion request with the token as a bearer credential:

Authorization: Bearer <token>

The platform looks the key up by its 8-character prefix, then verifies the full token against the stored PBKDF2 hash. The principal it builds is bound to the key's project, so a run created with this key always writes into that one project.

Situation HTTP status Detail message
No Authorization: Bearer header 401 Missing Bearer API key
Unknown or revoked token 401 Invalid API key
The key's user is disabled 403 User disabled
Key not bound to a project (during run create) 403 API key is not bound to a project

Per-key "scopes" are not access control. When a key is created the platform records a default scope set (such as runs:write, datasets:read), but scope enforcement is intentionally disabled: any valid, non-revoked key has full access to its project. Treat a key as all-or-nothing for its project — do not rely on scopes to restrict what a key can do.

Key management actions

Action Endpoint
Create a key POST /v1/projects/{project_id}/api-keys
List a project's keys (prefixes only) GET /v1/projects/{project_id}/api-keys
Revoke a key DELETE /v1/projects/{project_id}/api-keys/{key_id}

These endpoints all require a logged-in UI session (not a bearer key). Listing shows each key's prefix, name, creator, and scopes — never the secret. Revoking sets a revoked_at timestamp; a revoked key immediately fails authentication with Invalid API key.

Self-signed or internal certificates

If your platform is served over HTTPS with an internal or self-signed certificate, point the SDK at the issuing CA so streaming and qym config check can verify the connection: 

# Trust an internal CA bundle (PEM).
QYM_PLATFORM_CA_BUNDLE=/path/to/internal-ca.pem

For local troubleshooting only, you can disable certificate verification entirely:

# Local/dev only — do not use in production.
QYM_PLATFORM_SSL_VERIFY=false
Variable Effect Fallback variable
QYM_PLATFORM_CA_BUNDLE Path to a PEM CA bundle used to verify the platform's certificate. QYM_CA_BUNDLE
QYM_PLATFORM_SSL_VERIFY Set to a falsey value (0, false, no, off) to skip verification. QYM_SSL_VERIFY

The platform-specific variable wins when both are set; otherwise the SDK falls back to the generic name. With neither set, Python's default verified TLS context is used (including standard variables such as SSL_CERT_FILE).

Platform-dataset downloads use the process trust store. The current QymDataset fetch path does not apply QYM_PLATFORM_CA_BUNDLE or the verify toggle. For a private certificate, install its CA into Python's/system trust store (for example through SSL_CERT_FILE) as well.

One key, two superpowers

The same QYM_BASE_URL + QYM_API_KEY pair does double duty:

Stream runs to the platform

With a key set, every run() creates a platform run and streams progress, items, metrics, and traces for shared review — no code changes beyond the environment variables.

Resolve platform datasets

A bare dataset string that is not a local .csv/.jsonl file is resolved as a platform dataset using the same base URL and key. Without credentials it raises DatasetNotFoundError. See Using datasets.

Judge metrics use a separate key. LLM-as-judge metrics authenticate to your model provider with QYM_JUDGE_API_KEY (falling back to OPENAI_API_KEY) — not QYM_API_KEY. The platform key only governs streaming and platform datasets. See LLM-as-judge metrics.

Keeping keys safe

  • Never commit a token. Keep it in an untracked .env file or your secrets manager, and reference it via the environment.
  • Use a distinct key per environment. A separate key for local, CI, and each service makes revocation surgical — revoke one without disrupting the others.
  • Rotate by create-then-revoke. Create the replacement key, deploy it, then revoke the old one so there is no gap.
  • Keep keys out of metadata. Do not put secrets in run metadata or task metadata — that data is stored and displayed in the platform.
