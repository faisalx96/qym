Using datasets & reaching data in code

A dataset is the set of test items qym evaluates: each item carries an input for your task, an optional expected_output for metrics, and metadata for slicing results. This page shows every way to bring those items into a run — a local CSV, a JSONL file, an in-memory list, or a versioned dataset stored on the qym platform — and the exact rules each loader follows.

The dataset item model

No matter where items come from, every loader yields the same row type — a frozen CsvDatasetItem (the name is generic despite the Csv prefix; CSV, JSONL, in-memory, and platform datasets all reuse it). Each item has four fields you care about:

FieldTypePurpose
idstrStable item identity for resume, comparison, and review. Auto-generated if you don't supply one.
inputAnyThe value passed into your task function. Can be a string, a dict, or any JSON value.
expected_outputAny (default None)The reference answer metrics compare against. Built-in comparison metrics need it.
metadatadict (default {})Tags used for filtering, grouping, and analysis. Reaches metrics as metadata / item_metadata.

Your task receives only item.input. Metrics receive output (what the task returned), expected (item.expected_output), input_data (item.input), and the item metadata. For the full task/metric I/O contract see Task & metric I/O structure.

The four dataset sources

qym's public package exports exactly four dataset classes — import them from the top-level package:

from qym import CsvDataset, JsonlDataset, InMemoryDataset, QymDataset

CsvDataset

A local .csv file. Column names are configurable, so existing spreadsheets don't need renaming. Best for offline and air-gapped evaluation.

JsonlDataset

A local .jsonl file, one JSON object per line. Fixed keys (no column remapping). Best for nested/structured inputs.

InMemoryDataset

A list of Python dicts built in code. Best for generated tests and programmatic evals — nothing touches disk.

QymDataset

A versioned dataset stored on the qym platform, referenced by name plus a version or alias. Best for shared, reviewed regression sets.

Every dataset object exposes the same small interface: get_items() returning a list of items, a size property, len(...), and a name attribute. There is no shared base class — datasets are duck-typed, so you can pass any object with get_items().

Local CSV datasets

Point CsvDataset at a file and map your columns. The full constructor signature (all column-mapping args are keyword-only):

CsvDataset(
    path,                              # str | Path to a .csv file
    *,
    input_col="input",                 # str or list[str] holding task input(s)
    expected_col="expected_output",    # column holding the reference answer (or None)
    id_col=None,                       # column holding a stable item id (optional)
    metadata_cols=None,                # list of columns to collect into metadata
    name=None,                         # dataset name (defaults to the file's basename)
)

Example — map your own column names:

from qym import CsvDataset, Evaluator

dataset = CsvDataset(
    "datasets/qa.csv",
    input_col="question",
    expected_col="answer",
    id_col="id",
    metadata_cols=["difficulty", "domain", "source"],
)

evaluator = Evaluator(
    task=my_task,
    dataset=dataset,
    metrics=["exact_match"],
)
results = evaluator.run()

A matching CSV:

id,question,answer,difficulty,domain,source
qa-001,What is 2+2?,4,easy,math,smoke
qa-002,What is qym?,An evaluation framework,medium,evals,docs

When errors are raised

CsvDataset validates eagerly at construction and lazily on first read:

  • At construction it raises CsvDatasetSchemaError immediately if the path suffix is not .csv (case-insensitive) — message "Custom dataset must be a .csv file" — or if the file does not exist ("CSV file not found").
  • On first get_items() it validates the header. input_col is always required; expected_col and id_col are required only when set (non-None); every name in metadata_cols must exist. A missing column raises CsvDatasetSchemaError("Missing required column", ...); a file with no header row raises "CSV has no header row".

Items are loaded once and cached, so column errors surface the first time the run reads the dataset.

Multiple input columns

input_col can be a list when one CSV row needs to feed several task arguments. qym builds item.input as a dict keyed by the CSV column names:

id,sql_prompt,sql_context,sql
case-1,List all users,CREATE TABLE users(id INT);,SELECT * FROM users;
dataset = CsvDataset(
    "datasets/text2sql.csv",
    input_col=["sql_prompt", "sql_context"],
    expected_col="sql",
    id_col="id",
)

If your task uses the same names, qym unpacks them directly:

def task(sql_prompt, sql_context):
    return generate_sql(sql_prompt, sql_context)

If the task uses cleaner parameter names, pass input_mapping to Evaluator. The mapping direction is CSV column name → task parameter name:

def task(question, schema):
    return generate_sql(question=question, schema=schema)

result = Evaluator(
    task=task,
    dataset=dataset,
    metrics=[valid_sql],
    input_mapping={
        "sql_prompt": "question",
        "sql_context": "schema",
    },
).run()

The original dict remains the dataset input shown in artifacts and the UI. During task and metric calls, input_data uses the mapped names. Both original names (sql_prompt, sql_context) and mapped names (question, schema) remain available as individual metric arguments.

Without input_mapping, a single-column CSV preserves the scalar metric input for backward compatibility. With input_col="question", input_data stays scalar while question resolves to the same value. When input_mapping renames the column, metric input_data becomes a dict under the mapped name; for example, {"question": "What is AI?"}. Original and mapped names remain available as individual metric arguments and judge placeholders.

JSON-in-cell parsing rule

CSV cells are parsed with deliberately minimal magic. The rule (verified in _parse_cell):

  • A cell is JSON-parsed with json.loads only if its first non-whitespace character is { or [.
  • Every other value is kept as a string, verbatim — there is no numeric or boolean coercion. 42 stays the string "42"; true stays "true".
  • Empty or whitespace-only cells become the empty string "".
  • A {...} or [...] cell containing invalid JSON raises CsvDatasetSchemaError("Invalid JSON value: ...") with the file, row, and column attached.

This lets a single CSV mix scalar and structured inputs. Here the second row's input is a JSON object, so the task can accept dict input:

id,input,expected_output,metadata
case-1,What is 2+2?,4,{"difficulty": "easy"}
case-2,"{""question"": ""What is qym?"", ""context"": ""LLM eval""}",An evaluation framework,{"difficulty": "medium"}

Quote your JSON cells. In CSV, embedded double-quotes must be doubled ("") and the whole cell wrapped in quotes, as in case-2 above. A JSON value reaches the task exactly as the parsed dict/list, so a task like def task(question, context) can unpack it by key.

Item IDs

If you set id_col, the raw id is used as-is (an empty id value raises CsvDatasetSchemaError("Empty id value")). If you omit it, qym generates a deterministic id of the form csv_<fingerprint>__NNNN, where the fingerprint is a hash of the item's input, expected output, and metadata, and NNNN is a 4-digit counter that disambiguates duplicate rows. These ids are stable across reloads and row reordering — but prefer an explicit id_col for any dataset you will review, resume, or compare.

Local JSONL datasets

Use JsonlDataset when your items are naturally nested. Each non-blank line must be a JSON object. Unlike CSV, the keys are fixed — there is no column remapping:

JsonlDataset(path, *, name=None)   # path must end in .jsonl
KeyRequiredNotes
inputYesThe task input (any JSON value).
expected_output or expectedNoexpected is accepted as an alias for expected_output.
metadataNoA dict; defaults to {}.
item_id or idNoEither is accepted as the item id; if neither is present an id ds_<fingerprint>__NNNN is generated.
 
{"id": "case-1", "input": {"question": "What is 2+2?", "context": "math"}, "expected_output": "4", "metadata": {"difficulty": "easy"}}
{"id": "case-2", "input": "What is qym?", "expected": "An evaluation framework"}

Construction raises CsvDatasetSchemaError if the suffix isn't .jsonl ("JSONL dataset must be a .jsonl file") or the file is missing ("JSONL file not found"). A non-object line raises "JSONL line must be an object" with the row number. Blank lines are skipped.

In-memory datasets

InMemoryDataset takes a list of dicts directly — ideal for generated test cases or quick experiments where you don't want a file on disk:

from qym import InMemoryDataset, Evaluator

dataset = InMemoryDataset(
    [
        {"id": "q1", "input": "What is 2+2?", "expected_output": "4", "metadata": {"domain": "math"}},
        {"id": "q2", "input": "Capital of Japan?", "expected": "Tokyo"},
    ],
    name="smoke-set",
)

results = Evaluator(task=my_task, dataset=dataset, metrics=["exact_match"]).run()

Per-dict keys: item_id/id (falls back to item_<index> if absent), input, expected_output/expected, and metadata. The constructor signature is InMemoryDataset(items, *, name="in-memory", version=None).

Platform datasets (by name + version/alias)

A QymDataset pulls a versioned dataset from a qym platform deployment over HTTP. Reference it by name and select a specific version or a moving alias:

QymDataset(
    dataset_name,
    *,
    version=None,        # exact version label, e.g. "v3"
    alias=None,          # moving alias, e.g. "production"
    platform_url=None,   # defaults to env QYM_BASE_URL
    api_key=None,        # defaults to env QYM_API_KEY
    project_slug=None,
)

Alias resolution: if you pass neither version nor alias, the alias defaults to "production". With credentials set in the environment, you usually only pass the name:

from qym import QymDataset, Evaluator

# Uses QYM_BASE_URL + QYM_API_KEY from the environment; resolves to the
# "production" alias unless you pass version= or alias=.
dataset = QymDataset("qa-regression")                  # production alias
dataset = QymDataset("qa-regression", version="v3")    # pinned version
dataset = QymDataset("qa-regression", alias="staging") # named alias

results = Evaluator(task=my_task, dataset=dataset, metrics=["exact_match"]).run()

Items are fetched lazily on first read via GET /v1/datasets/{name}/versions/{version-or-alias}/items with Authorization: Bearer <token>, paginating until the platform reports no more pages. Credentials are required: if platform_url or api_key is missing, the constructor raises DatasetNotFoundError right away (see the gotcha below). For how to set QYM_BASE_URL / QYM_API_KEY and create a key, see Link your repo & create API keys.

Passing a dataset as a string

You can hand Evaluator a plain string instead of a dataset object. qym resolves it through resolve_dataset, which checks the filesystem first:

String valueResolves to
An existing .csv file pathCsvDataset(path) (default column mapping)
An existing .jsonl file pathJsonlDataset(path)
An existing file with any other extensionraises CsvDatasetSchemaError("Unsupported dataset file extension")
A string that is not an existing fileQymDataset(string) — a qym platform dataset name
 
from qym import Evaluator

# Existing local file -> CsvDataset
Evaluator(task=my_task, dataset="datasets/qa.csv", metrics=["exact_match"]).run()

# Not a file on disk -> resolved as a platform dataset name (needs creds)
Evaluator(task=my_task, dataset="qa-regression", metrics=["exact_match"]).run()

When the string is a platform name, dataset_version and dataset_alias from your config choose the version/alias:

Evaluator(
    task=my_task,
    dataset="qa-regression",
    metrics=["exact_match"],
    config={"dataset_version": "v3"},   # or {"dataset_alias": "staging"}
).run()

A typo'd file path turns into a credentials error. Because any non-file string is treated as a platform dataset name, a misspelled local path like "datsets/qa.csv" is not reported as a missing file — it's sent to the platform resolver. Without credentials that surfaces as a confusing DatasetNotFoundError rather than a "file not found". When you mean a local file, pass an explicit CsvDataset/JsonlDataset or double-check the path.

This string is resolved against the qym platform — there is no Langfuse involvement anywhere in dataset loading. The deprecated langfuse_client constructor argument is ignored.

Choosing a dataset via the CLI

qym run create exposes the same sources through flags. You must provide exactly one of --dataset or a local file flag (--dataset-file / --dataset-csv) — supplying both, or neither, exits with a usage error.

FlagMeaning
--dataset NAMEA qym platform dataset name (or a local dataset path that exists).
--dataset-version VERSIONPlatform dataset version to pin.
--dataset-alias ALIASPlatform dataset alias to use.
--dataset-file PATHA local .csv or .jsonl file.
--dataset-csv PATHA local CSV file (equivalent to --dataset-file for CSVs).
--csv-input-colCSV column for input (default input).
--csv-expected-colCSV column for expected output (default expected_output; an empty string means "no expected column").
--csv-id-colCSV column for the item id (optional).
--csv-metadata-colsComma-separated CSV metadata columns.
 
qym run create \
  --task-file agent.py --task-function my_task \
  --dataset-csv datasets/qa.csv \
  --csv-input-col question \
  --csv-expected-col answer \
  --csv-metadata-cols difficulty,domain,source \
  --metrics exact_match

A local file ending in .jsonl is loaded as a JsonlDataset and the --csv-* column flags are ignored (JSONL keys are fixed). Anything else local is loaded as a CsvDataset with your column mapping. For the full command and flag reference see the CLI reference.

Writing good datasets

Metric quality is bounded by dataset quality — a clean run on a weak dataset still produces misleading evidence. A short checklist:

  • One behavior per item. Mixing task types in one dataset makes aggregate metrics incoherent — split by task instead.
  • Stable, explicit ids. Use an id_col (CSV) or id/item_id (JSONL) so resume and comparison stay aligned across reruns.
  • Specific expected outputs. Deterministic metrics like exact_match can only score well against precise reference answers; loosen with a fuzzy or judge metric when the answer is open-ended.
  • Metadata for the slices you actually review. Good fields: domain, difficulty, source, language, prompt_version, risk_level. Avoid fields that are unique per row (unless they are identifiers) — they make breakdowns noisy.
  • Keep a small smoke subset for fast local checks before running the full regression set.

RAG and tool fields live inside input. Metrics receive input_data = item.input. If a metric or judge needs a context, schema, or question, those must be keys inside the item's input dict. In CSV, either put a JSON object in one input cell (see the JSON-in-cell rule above) or pass multiple columns with input_col=[...].

Missing expected outputs

expected_output is optional everywhere — but built-in comparison metrics (exact_match, contains, fuzzy_match, correctness) compare against it. If your dataset has no expected column, those metrics receive None and will score everything as failing. Either add an expected column, or choose metrics that don't need a reference (for example an LLM judge that scores relevance from the input alone). See the Built-in metrics tour for which metrics need what.
