Handling common errors

Most failures in qym map to a handful of clear, named exceptions. This page lists every error you are likely to hit, the exact message it produces, why it happens, and the one-line fix — plus how to reproduce a failure in the smallest possible way.

Triage in three steps

Before reading the catalog, classify the failure. This tells you which layer to look at and stops you from debugging the platform when the bug is in your task.

  1. Local SDK — task import fails, CSV won't load, a metric crashes, an item errors. Reproduce with a tiny local CSV and show_tui=False (or --no-progress).
  2. Provider / judge config — a judge metric raises before scoring, or LLM calls error. Check your judge env vars and model name.
  3. Platform connectivity — the run runs fine locally but no run appears in the dashboard. Check QYM_BASE_URL / QYM_API_KEY and look for a stderr warning.

Smallest reproduction wins. A five-row CSV with one deterministic metric (exact_match) separates task bugs from platform or provider bugs faster than anything else. Add the platform and judges back only after the local path is green.

Where qym's exceptions live

The SDK's named exceptions are defined in qym.utils.errors — they are not re-exported from the top-level qym package, so import them from there if you want to catch them:

from qym.utils.errors import (
    QymError,              # base class for all qym errors (alias: LLMEvalError)
    DatasetNotFoundError,  # dataset couldn't be resolved locally or on the platform
    CsvDatasetError,       # loading/parsing a CSV dataset failed
    CsvDatasetSchemaError, # CSV doesn't match the expected schema (carries file/row/column)
    MetricError,           # a metric computation failed
    TaskExecutionError,    # task execution failed
)

Two task-related exceptions live in qym.core.evaluator instead, because they are raised while normalizing a task's return value: InvalidTaskOutputError and TaskExecutionTimeoutError.

Task output errors

InvalidTaskOutputError: dict returns must use the envelope

qym treats a plain (non-dict) return value as the visible output. A dict return is reserved for qym's task-output envelope, which must have exactly the keys output and metadata — and metadata must itself be a dict. Anything else raises InvalidTaskOutputError (this is non-retryable; the item fails). The message lists the offending keys:

InvalidTaskOutputError: Task returned a dict. Dict task outputs must use qym's envelope {"output": <visible output>, "metadata": <dict>} (missing keys: metadata; unexpected keys: answer).
# Returns {"answer": "Paris"} -> raises InvalidTaskOutputError
def bad_task(question):
    return {"answer": call_llm(question)}

# Fix 1: return the value plainly
def task_plain(question):
    return call_llm(question)

# Fix 2: to surface a dict as the output, wrap it in the envelope
def task_envelope(question):
    return {"output": call_llm(question), "metadata": {}}

Custom metrics see the whole envelope. When a task returns the envelope, qym stores only output as the visible output, but a custom metric receives the full envelope as its output argument — so read output["output"] and output["metadata"]. Built-in metrics auto-unwrap. See Custom metrics.

Task returned None

If your task has no return statement it returns None, which is scored like any other output (usually 0 against exact_match). This is not an exception — it's a silent logic bug. Make sure every code path returns the value you intend.

Dataset errors

DatasetNotFoundError: a string that isn't a local file

When you pass a string as the dataset, qym first checks whether it's an existing local .csv or .jsonl file. If it is not, the string is interpreted as a qym platform dataset name, which needs platform credentials. With no credentials it raises at construction time, before any items run:

DatasetNotFoundError: Dataset 'my-dataset' is not a local file and qym platform credentials are missing. Set QYM_BASE_URL and QYM_API_KEY, or pass CsvDataset/JsonlDataset.

A typo'd path looks like a credentials error. Because any non-file string falls through to "platform dataset", a mistyped local path (e.g. "datsets/qa.csv") surfaces as this DatasetNotFoundError about missing credentials — not a "file not found" error. Double-check the path first, or pass an explicit CsvDataset(...) so a bad path fails loudly.

from qym import Evaluator, CsvDataset

# Unambiguous: a bad path raises a CSV error, not a platform-credentials error
data = CsvDataset("datasets/qa.csv", input_col="question", expected_col="answer")
result = Evaluator(task, data, metrics=["exact_match"]).run(show_tui=False)

To reference a real platform dataset by name, set both credentials (see Link your repo & create API keys):

export QYM_BASE_URL=https://qym.example.com
export QYM_API_KEY=<platform-api-key>

CsvDatasetSchemaError: structural CSV problems

A CsvDataset validates the file extension and existence the moment you construct it; column and JSON-cell problems surface when items are first loaded. The error carries a file, and where relevant a row and column, appended in parentheses. Common variants:

MessageCause
Custom dataset must be a .csv fileThe path's suffix is not .csv.
CSV file not foundThe .csv path doesn't exist (raised at construction).
CSV has no header rowThe file is empty or has no header line.
Missing required columnAn input_col / expected_col / id_col / metadata column isn't in the header.
Invalid JSON value: …A cell starts with { or [ but isn't valid JSON.

Only cells that begin with { or [ are parsed as JSON; everything else stays a string. If you intended a literal value that happens to start with a brace, that's the source of Invalid JSON value.

Metric errors

"Metric 'X' not found"

Passing a metric name the registry doesn't recognize raises a ValueError. The message lists every available name (custom-registered names first, then built-ins, sorted):

ValueError: Metric 'contains_expected' not found. Available metrics: conciseness, contains, correctness, correctness_llm, exact_match, faithfulness, faithfulness_llm, fuzzy_match, hallucination, relevance, response_time, token_count, tool_calling, toxicity

The dependency-free code metrics are:

exact_match, contains, fuzzy_match, response_time, token_count, correctness, faithfulness

The registry name is contains, not contains_expected. The function is named contains_expected internally, but it is registered under "contains". Likewise, the code metric faithfulness is a token-overlap heuristic; the LLM judge is the separate name faithfulness_llm.

The seven LLM-judge names (relevance, faithfulness_llm, correctness_llm, conciseness, hallucination, toxicity, tool_calling) are registered regardless of whether openai is installed. A missing client raises ImportError only when a judge executes. To inspect the registry:

qym metric list

A metric that hangs: the metric_timeout wall

Each metric attempt has a wall-clock budget, metric_timeout, defaulting to 60.0 seconds. qym retries a timed-out attempt up to metric_max_retries times (default 2). If the last attempt also times out, the metric is recorded like every other metric failure: score 0 plus an error message, with no special timeout label. The error counts as 0 in the run mean (on the platform and in the local summary), or is left out of it for a lower-is-better metric, and lowers metric success rate.

config = {
    "metric_timeout": 180.0,
    "metric_max_retries": 1,
}  # use metric_timeout=None to disable the cap and timeout retries
result = Evaluator(task, data, metrics=[slow_metric], config=config).run(show_tui=False)

See Configs & options for the full timeout and concurrency reference.

LLM-as-judge errors

ImportError: judges need the openai client

The judge metrics depend on the optional openai package at execution time. Install it directly; there is no qym[judges] package extra:

pip install openai

RuntimeError: missing judge configuration

A judge needs a model name and an API key. If either is missing when the judge runs, JudgeConfig.validate() raises a RuntimeError that names exactly what's missing and how to set it:

RuntimeError: LLM judge metrics require configuration. Missing: QYM_JUDGE_MODEL, QYM_JUDGE_API_KEY (or OPENAI_API_KEY)
export QYM_JUDGE_MODEL=gpt-4o-mini       # required: there is no default model
export QYM_JUDGE_API_KEY=<provider-key>   # required (falls back to OPENAI_API_KEY)
export QYM_JUDGE_BASE_URL=https://api.openai.com/v1  # optional (falls back to OPENAI_BASE_URL)

Judge input error: a prompt field is missing

Judge prompts are validated before an LLM request is made. If a prompt references a field that the metric input does not provide, qym raises JudgeInputError and prints one colored terminal message with the judge metric name, the expected fields, the fields or type it received, and an input_mapping example. The LLM is not called with an unresolved placeholder.

Judge input error: hallucination
Expected: context
Received: question

Fix the dataset input or map the existing CSV column to the required judge name, for example input_mapping={"source_text": "context"}. For a single-column CSV, qym uses the declared input_col as the metric input key automatically; a mapping is only needed when that column name differs from the judge's required field. As a guide, relevance needs input["question"]; faithfulness_llm needs input["context"] and input["question"]; tool_calling needs input["question"], input["tool_definitions"], and input["tool_calls"]. See Multiple input columns for mapping and LLM-as-judge & pairwise judging for the per-judge field list.

Platform & connectivity

No run appears in the dashboard

Live streaming to the platform turns on only when QYM_API_KEY is set in the same process that launches the run. If creating the run fails (bad URL, unreachable host, auth, certificate), qym does not crash your evaluation — it logs a warning to stderr and keeps running locally:

Platform live UI disabled: failed to create run at https://qym.example.com/v1/runs (ConnectionError: ...)

Things to check, in order:

  • QYM_API_KEY and QYM_BASE_URL are exported in the shell (or .env) that runs the script — not just your interactive shell.
  • The keys are valid and the host is reachable. Validate connectivity with the CLI: qym config show then qym config check.
  • Set QYM_PLATFORM_DEBUG=1 to surface the underlying streamer errors instead of the single summarized warning.

Self-signed or internal HTTPS certificates

If your deployment uses an internal CA, point qym at the bundle so TLS verification succeeds:

export QYM_PLATFORM_CA_BUNDLE=/path/to/internal-ca.pem
# For local development only, you can disable verification entirely:
# export QYM_PLATFORM_SSL_VERIFY=false

Reading failed rows in your results

Individual item failures don't stop the run — the rest of the dataset still completes. Failed items are encoded in the saved artifacts so you can find them quickly:

  • A task that raised is written with the output column set to ERROR: <message>, and each metric score set to N/A.
  • A metric that returns a dict containing an error key is scored 0.0 for that item. Like a failed task, it counts as 0 in the run mean, or is left out of it for a lower-is-better metric; the error count is shown beside the mean. The local summary (get_metric_stats, summary()) and the platform apply this same rule.
  • The saved path is in result.last_saved_path; per-item rows live under qym_results/<task>/<model>/<date>/.

To pull just the failures of a stored run from the CLI:

qym run failed <run_id>

A minimal reproduction template

When something fails and you're not sure which layer is at fault, collapse it to this: a few-row CSV, a deterministic metric, no TUI, no platform. If this passes, the bug is in your real task, dataset, judge config, or platform setup — not in qym's core loop.

from qym import Evaluator, CsvDataset

data = CsvDataset("smoke.csv", input_col="question", expected_col="answer")

def task(question):
    return question  # echo: deterministic, no external calls

result = Evaluator(task, data, metrics=["exact_match"]).run(show_tui=False)
print(result.total_items, result.success_rate)

Or the CLI equivalent:

qym run create \
  --task-file smoke_task.py \
  --task-function task \
  --dataset-csv smoke.csv \
  --csv-input-col question \
  --csv-expected-col answer \
  --metrics exact_match \
  --no-progress

Still stuck? Capture your qym version, the exact command or snippet, the dataset type, the metric list, whether QYM_BASE_URL/QYM_API_KEY were set, and the run ID — then revisit Your first run to confirm the happy path works on your machine.
