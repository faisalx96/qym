API overview & conventions

The qym platform is a FastAPI service. The SDK and CLI talk to it over HTTP, and so can you. This page covers what the API is for, how it is organized, where to find the machine-readable schema, and the cross-cutting conventions — auth, identifiers, request and response shapes, pagination, errors, and idempotency — that every endpoint follows.

When to use the HTTP API

Most users never call the API directly. The CLI and the Python SDK already wrap it: qym run create and Evaluator(...).run() create a run and stream events for you. Reach for raw HTTP when:

  • You are integrating from a language other than Python, or from a service that cannot embed the SDK.
  • You are building operational tooling around projects, runs, datasets, or review — dashboards, schedulers, CI gates.
  • You need a behavior the CLI does not expose, or you want full control over the request payload.

If the CLI covers your case, prefer it — it handles auth, retries, NDJSON batching, and finalization that you would otherwise reimplement.

The SDK is the reference client. If you are unsure how an endpoint is meant to be called, the SDK's platform client is a working example: it creates a run with POST /v1/runs, then streams NDJSON events to POST /v1/runs/{run_id}/events. The HTTP contracts on this page are exactly what it uses.

The machine-readable schema

The service generates an OpenAPI schema and serves an interactive explorer. Treat these as the source of truth for exact request and response models — this documentation explains the conventions and the load-bearing behavior, but the generated schema is always in sync with the running build.

PathWhat it isAuth
GET /openapi.jsonThe OpenAPI specification — the stable, machine-readable contract. Point your client generators at this.None
GET /api-docsSwagger UI, an exploratory browser for trying endpoints. Good for discovery, not for learning the conventions.None

Both are registered by the framework with no auth dependency, so anyone who can reach the deployment can read the schema. ReDoc is disabled. The service also serves a static human docs portal at /docs/, which is distinct from /api-docs (Swagger) and /openapi.json (the spec).

The schema's version field is not the release version. The OpenAPI document reports title: "qym-platform" and a hardcoded version: "0.1.0", which does not track the package release. Do not use the spec's version to detect the deployed build — use it only to discover endpoints and models.

Base URL and health

Every example on these pages uses https://qym.example.com as the deployment's base URL. Substitute your own host. The same value is what the SDK and CLI read from the QYM_BASE_URL environment variable.

To check that a deployment is up without authenticating, hit the health endpoint:

curl https://qym.example.com/healthz
{ "ok": true, "service": "qym-platform", "env": "dev" }

It is unauthenticated and always returns the service name and the configured environment.

URL surface: /v1 vs /api

The API is split across two path prefixes, but not along an "ingestion vs review" line. The split is roughly "the documented v1 surface" versus "analysis, corrections, and legacy dashboard JSON".

PrefixCarriesExamples
/v1/...Run ingestion, dataset CRUD and versioning, project / member / API-key management, and run review actions.POST /v1/runs, POST /v1/runs/{id}/events, POST /v1/runs:upload, GET /v1/datasets, POST /v1/projects/{id}/api-keys, POST /v1/runs/{id}/approve
/api/...LLM root-cause analysis, corrections, and the legacy dashboard read JSON the web UI consumes.POST /api/runs/{id}/analyze, GET /api/corrections, GET /api/runs, GET /api/runs/{id}

Don't read "review" into the prefix. Run review actions (submit / approve / reject) live under /v1, while the legacy read JSON the dashboard polls lives under /api. The CLI's connectivity check (qym config check) deliberately uses the legacy GET /api/runs path, so a failure there can indicate routing rather than auth.

Routes are mounted in a deliberate order — analysis before the run routes, because some run routes use a catch-all path parameter that would otherwise swallow analysis URLs. You don't need to think about this when calling specific endpoints; it only matters that paths are matched most-specific-first.

Authentication, in one paragraph

Machine clients send a project-scoped API key as a Bearer token: Authorization: Bearer <token>. Humans in the dashboard authenticate with a browser session. The two are not interchangeable — ingestion needs a key, and project/member/key administration and run review need a session. Keys are always bound to exactly one project, and although a key records a list of scopes, those scopes are not enforced: any valid, non-revoked key has full access to its project. Isolate access with separate projects, not with scopes.

curl https://qym.example.com/v1/runs \
  -H "Authorization: Bearer <your-token>"

The full mechanics — creating and revoking keys, the token format, error strings, and the deployment auth modes — are on the Authentication page.

Identifiers are the scoping handles

Almost every operational workflow is keyed on two identifiers, and most endpoints take one or both as path parameters or filters:

  • Project — referenced by its UUID (project_id) or by its URL slug. List endpoints that span projects typically require one of project_id or project_slug. Your API key already pins a project, so calls made with a key are auto-scoped to it.
  • Run — referenced by its run_id (returned when you create a run). Items within a run carry an item_id you assign in your event payloads.

Datasets are addressable by id, by name/slug, or by a version reference (a numeric version or an alias). When no version is given, qym resolves the production alias by default. See Datasets & data access for the SDK side of this.

Request and response shapes

The API speaks JSON throughout, with two deliberate exceptions for ingestion.

OperationContent typeBody shape
Most reads and writesapplication/jsonA single JSON object.
Streaming run eventsapplication/x-ndjsonNewline-delimited JSON: one complete event object per line. Not a JSON array.
Uploading a finished artifactmultipart/form-dataA file part plus form fields. Only .csv and .json files are accepted; any other extension is rejected with 400 Unsupported file type (use .csv or .json).

Creating a run returns the run's id and a link to its live page in the dashboard:

{
  "run_id": "...",
  "live_url": "https://qym.example.com/projects/<project-slug>/runs/<run-id>"
}

When the project has a slug the live_url uses the /projects/{slug}/runs/{run_id} form; otherwise it falls back to /run/{run_id}. The artifact-upload endpoint always returns the /run/{run_id} form.

Non-finite numbers are coerced to null. Both the SDK and the platform sanitize JSON before it is stored: NaN and Infinity become null so the payload is valid JSON and acceptable to the database. Don't rely on a metric score round-tripping as NaN — read it back as null.

Pagination and filtering

List endpoints page with limit and offset query parameters and return rows in a sorted order you can control with a sort parameter. Defaults and bounds vary by endpoint and are enforced server-side; for example, the run list defaults to 50 rows (max 200), sorted newest-first. Read endpoints also accept filter parameters such as status, owner, task, dataset, model, and free-text query, and dataset-spanning lists require a project handle. Consult the Endpoint reference (or /openapi.json) for the exact parameters, defaults, and ceilings of each list.

Page with offset, don't fetch everything. limit is capped per endpoint, so to walk a large result set you advance offset by limit until a short page comes back. The SDK's platform dataset reader does exactly this, paging items 1000 at a time.

Error responses

Errors use standard HTTP status codes with a JSON body of the form { "detail": "..." }. The detail strings are stable but human-facing — branch on the status code, and use the detail for diagnostics. The codes you will encounter most:

StatusMeaningTypical cause
400Bad requestMalformed body, unsupported upload type, or an invalid request payload.
401UnauthenticatedMissing or invalid Bearer key (Missing Bearer API key / Invalid API key), or no session where one is required.
403ForbiddenAuthenticated but not allowed: a key not bound to a project (API key is not bound to a project), accessing another project's resource, a disabled user, or a cross-origin write blocked by the same-origin guard.
404Not foundThe run, dataset, project, or key does not exist (or is not visible to you).
410GoneThe target run was soft-deleted on the platform. Create a fresh run.

The CLI maps these onto stable exit codes (for example 404 to not found, 401/403 to auth denied, 409 to conflict) — see the CLI reference.

The run-event envelope

Ingestion is event-sourced. After creating a run you stream events to it; each line of the NDJSON body is one event wrapped in a fixed v1 envelope:

{
  "schema_version": 1,
  "event_id": "<uuid>",
  "sequence": 1,
  "sent_at": "2026-06-20T12:00:00Z",
  "type": "run_started",
  "run_id": "<uuid>",
  "payload": { }
}
FieldTypeNotes
schema_versionliteral 1Must be 1.
event_idUUIDUnique per distinct event; reuse the same id only when retrying that exact event.
sequenceinteger ≥ 1Monotonic per stream, starting at 1.
sent_atdatetimeUTC ISO-8601 (the SDK emits a trailing Z).
typestringOne of the 11 event types below.
run_idUUIDMust match the run in the URL path, or the line is rejected.
payloadobjectTyped per event type.

The eleven valid event types are: run_started, item_started, item_attempt_started, item_attempt_finished, metric_scored, item_completed, item_failed, run_completed, run_heartbeat, metadata_update, and span_completed. A run is finalized by a run_completed event whose payload carries a final_status of COMPLETED, FAILED, or STOPPED (default COMPLETED). The full field-by-field payloads are on the Run ingestion page.

These are platform wire events. Do not confuse them with the SDK's in-process progress events (run_start, item_start, item_complete, run_complete, etc.) delivered to local observers. Those are a separate, local vocabulary covered in Progress & observers.

Idempotency and partial batches

Event ingestion is built to be retried safely. Idempotency is keyed on the pair (run_id, event_id): if an event with that id was already stored, it is skipped rather than applied twice. Each line gets its own verdict, so one bad line never fails the rest of its batch:

{ "ok": true, "applied": 12, "skipped": 1, "rejected": 1,
  "rejected_events": [{ "line": 3, "event_id": "…", "sequence": 3,
                        "type": "metric_scored", "error": "…" }] }
  • applied — events newly written.
  • skipped — duplicates whose (run_id, event_id) was already present.
  • rejected / rejected_events — lines that were not stored and never will be (bad JSON or envelope, a mismatched run_id, a payload that fails its schema, a reused sequence, a value the database refuses), with the reason for the first 100.

When every line of a request is rejected the answer is 422 with the same body, "ok": false and a detail.

Rejected lines are reported, not retried. Resending them unchanged is refused again; retry only network errors, 408, 429 and 5xx. Rejected events do not hold the run's completion: the run completes and is flagged Incomplete (run_metadata.ingest_incomplete) with the events it is missing.

Run status vocabulary

A run carries a single workflow status. These are the only values the platform uses; map any UI label back to one of them rather than inventing synonyms.

StatusMeaning
RUNNINGCreated and accepting events; not yet finalized.
COMPLETEDFinalized by a run_completed event with final_status: COMPLETED (also the status of uploaded artifacts).
FAILEDFinalized with final_status: FAILED (any unrecognized final status maps here).
STOPPEDFinalized with final_status: STOPPED, e.g. an interrupted run; also where stale runs are reconciled to.
DRAFT / SUBMITTED / APPROVED / REJECTED / PENDINGReview-workflow states a run moves through after execution.

Always send a terminal event. A run that never receives run_completed stays RUNNING until stale-run recovery reconciles it to STOPPED. The SDK sends the terminal event synchronously to avoid this; if you stream events yourself, finalize explicitly. Periodic run_heartbeat events keep a long run from looking stale.

Same-origin guard (session mode)

When the deployment runs in a session-based auth mode, a middleware blocks cross-origin state-changing requests (POST/PUT/PATCH/DELETE) from the browser unless they carry a Bearer header. A request whose Origin or Referer does not match the configured base URL gets 403 Cross-origin request blocked; one with neither header gets 403 Missing same-origin headers. Bearer API-key calls bypass this guard entirely, so server-to-server clients are unaffected — it only protects browser sessions. A misconfigured QYM_BASE_URL behind a proxy is the usual cause of spurious blocks.
