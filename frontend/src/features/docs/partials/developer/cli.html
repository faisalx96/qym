DEVELOPER / API

CLI reference

The qym command-line interface runs evaluations and inspects platform runs from a shell, CI job, or agent — no Python glue required. It is a thin wrapper over the SDK: every run command builds the same Evaluator, dataset, and config objects you would write by hand.

The CLI is built with Typer and uses a noun-verb structure: a top-level noun (run, metric, analyze, config, dataset) followed by a verb. Two legacy top-level commands (dashboard, submit) remain for convenience. Running qym with no arguments prints help.

SDK vs CLI. Use the SDK for application code, services, custom observers, and direct result access. Use the CLI for automation boundaries — CI steps, shell scripts, and agents that want predictable JSON. If a run is unclear, reproduce it in Python first.

Every command is listed below with its purpose. Detailed flags follow for the commands that take options.

Global options

These options are defined on the app callback and apply to every subcommand. Typer requires them before the subcommand, but the CLI automatically hoists --json and --no-color to the front, so agents may place them anywhere on the line.

OptionEffect
--jsonEmit machine-readable JSON to stdout; all human-readable text goes to stderr.
--no-colorDisable Rich color in console output.

stdout is clean under --json. Status lines, progress, and tables are written to stderr at all times. With --json, stdout contains only the JSON document — safe to pipe into jq or capture in CI.

qym run create

The primary command. It loads your task function from a file, builds a dataset, constructs an Evaluator, and runs it. Required flags for a single run: --task-file, --task-function, a dataset input, and --metrics. If any are missing, the CLI exits 2 with Missing required arguments: ....

Task and metrics flags

FlagDefaultMeaning
--task-file—Python file containing the task function. Required (single run).
--task-function—Name of the function to evaluate inside the task file. Required (single run).
--metrics—Comma-separated metric names, e.g. exact_match,fuzzy_match. Required (single run).
--model—Model name, or comma-separated list. Multiple models trigger a multi-model run.
--samples1Evaluate every item k times as sequential passes inside one logical run. Use --config '{"report_k":3}' when the reported k should be smaller than the collected sample count.
--task-nameauto-derivedOverride the auto-derived task name (sets config.task_name).

Dataset flags

Provide exactly one of: --dataset (platform/string dataset) or a local file (--dataset-file/--dataset-csv). Supplying both, or neither, exits 2 with Provide exactly one of --dataset or --dataset-file/--dataset-csv.

FlagDefaultMeaning
--dataset—A qym platform dataset name, or a local dataset path. A bare string that is not an existing local file resolves to a platform dataset (requires QYM_BASE_URL + QYM_API_KEY).
--dataset-version—Platform dataset version (sets config.dataset_version).
--dataset-alias—Platform dataset alias (sets config.dataset_alias).
--dataset-file—Local .csv or .jsonl file. A .jsonl path builds a JsonlDataset; anything else builds a CsvDataset.
--dataset-csv—Local CSV path. Equivalent to --dataset-file for CSVs.
--csv-input-colinputCSV column used as the task input. (CSV datasets only.)
--csv-expected-colexpected_outputCSV column used as the expected output. An empty string disables expected output.
--csv-id-col—CSV column used as a stable item ID.
--csv-metadata-cols—Comma-separated CSV columns carried as item metadata.

A typo'd path is not a local-file error. If you pass --dataset ./data/qa.csv and the file does not exist, the string falls through to platform dataset resolution and surfaces a DatasetNotFoundError (or a credentials error) rather than "file not found". Use --dataset-csv/--dataset-file for local files so a missing path fails loudly.

Config, platform, and run flags

FlagDefaultMeaning
--config—JSON string merged into the EvaluatorConfig, e.g. '{"max_concurrency":4}'. Invalid JSON exits 2.
--platform-urlQYM_BASE_URLOverride the platform base URL (sets config.platform_url).
--platform-api-keyQYM_API_KEYOverride the platform API key (sets config.platform_api_key).
--resume-from, --run-file—Checkpoint CSV to resume from (sets config.resume_from). The two spellings are aliases.
--runs-config—Multi-run YAML/JSON config. Switches the command into multi-run mode (see below).
--output—Save the single-model result to a JSON file. Ignored (with a warning) for multi-model runs.
--git-branchauto-detectedOverride the recorded git branch metadata.
--git-commitauto-detectedOverride the recorded git commit hash metadata.

Output and UI flags

FlagDefaultMeaning
--quiet, -qoffPrint only the final summary (success rate plus each metric mean) instead of the full per-item summary.
--no-progressoffDisable the progress bar.
--no-uioffDisable the local results table / web UI output.
--ui-port0Port for the local web UI; 0 means auto-select.
--no-openoffDo not open the browser automatically when a UI URL is available.

No --concurrency or --no-tui flag. Concurrency is set through --config (for example '{"max_concurrency":8}'). To suppress local rendering, use --no-progress and/or --no-ui. There is also a hidden, deprecated --live-mode flag — do not use it; platform streaming turns on automatically when both QYM_BASE_URL and QYM_API_KEY are present.

Multi-run mode (--runs-config)

When --runs-config is provided, qym run create ignores --task-file/--dataset/--model and instead loads a list of run specs from the YAML/JSON file. All specs run via the MultiModelRunner and auto-save as CSV. If any run is interrupted, the CLI prints a Resume with: qym run create --resume-from <path> ... hint and exits 1.

qym run create --runs-config runs.yaml

Examples

Local CSV run (no credentials)

The offline-first happy path: a local CSV plus a code metric. Nothing is sent to the platform.

qym run create \
  --task-file eval_task.py \
  --task-function answer_question \
  --dataset-csv datasets/qa.csv \
  --csv-input-col question \
  --csv-expected-col answer \
  --csv-id-col id \
  --csv-metadata-cols topic,source \
  --metrics exact_match,fuzzy_match \
  --task-name support-rag \
  --config '{"run_name":"support-rag-smoke","max_concurrency":4,"max_retries":1}'

Platform dataset run

A bare --dataset name resolves to a platform dataset. Streaming to the platform turns on automatically because both env vars are set.

export QYM_BASE_URL=https://qym.example.com
export QYM_API_KEY=<your-token>

qym run create \
  --task-file eval_task.py \
  --task-function answer_question \
  --dataset support-smoke \
  --dataset-alias production \
  --metrics exact_match \
  --config '{"run_name":"support-smoke"}'

JSON automation

Place --json anywhere; the result object lands on stdout as JSON. A single-model run emits one object; a multi-model run emits an array.

qym --json run create \
  --task-file eval_task.py \
  --task-function answer_question \
  --dataset-csv datasets/qa.csv \
  --metrics exact_match \
  > result.json

Resume from a checkpoint

qym run create \
  --task-file eval_task.py \
  --task-function answer_question \
  --dataset-csv datasets/qa.csv \
  --metrics exact_match \
  --resume-from qym_results/checkpoints/support-rag.csv

CLI to SDK mapping

Each run create flag maps to an SDK construct. Reproducing a CLI run in Python is mechanical:

--dataset-csv + --csv-* flags -> CsvDataset(input_col=..., expected_col=..., id_col=..., metadata_cols=[...])
--dataset-file (*.jsonl)       -> JsonlDataset(path)
--dataset (bare string)        -> resolved by Evaluator (platform dataset or local path)
--metrics a,b                  -> metrics=["a", "b"]
--model "x,y"                  -> Evaluator(model=["x", "y"])  # list -> multi-model
--config '{...}'               -> EvaluatorConfig fields (merged dict)
--task-name                    -> config.task_name
--platform-url                 -> config.platform_url
--platform-api-key             -> config.platform_api_key
--resume-from                  -> config.resume_from
--dataset-version/-alias       -> config.dataset_version / config.dataset_alias

See Configs & options for the full EvaluatorConfig field reference and Datasets for dataset construction.

Inspecting runs

These read-only commands query the platform over HTTP. They authenticate with QYM_API_KEY when set; list/get can run unauthenticated against an open deployment, but most endpoints require a key.

qym run list

Lists recent runs, sorted newest-first, then truncated to --limit. Filters are applied client-side.

FlagDefaultMeaning
--limit50Maximum runs to return.
--task—Substring filter on task name.
--model—Substring filter on model name.
--status—Exact (case-insensitive) status filter.
--user—Substring filter on the run owner's id, email, or display name.

qym run get / failed / compare

  • qym run get <run_id> — prints the run name, dataset, status, item count, and metric averages. With --json, dumps the full run document.
  • qym run failed <run_id> — shows items that have an error or any zero metric score. The human table caps at 50 rows; use --json for all of them.
  • qym run compare <run_id> <run_id> ... — side-by-side success rate and metric averages. Requires at least two run IDs, otherwise exits 2.
qym run list --task support-rag --status COMPLETED --limit 10
qym run get a1b2c3d4
qym run failed a1b2c3d4 --json | jq '.failed_items[].item_id'
qym run compare a1b2c3d4 e5f6a7b8

qym metric list

Prints every metric registered in the SDK (built-ins plus anything registered at import time), each with the first line of its docstring. The dependency-free code metrics are exact_match, contains, fuzzy_match, response_time, token_count, correctness, and faithfulness. The seven judge names are also registered; executing one requires pip install openai and judge-provider configuration.

qym --json metric list | jq -r '.metrics[].name'

See Metrics for signatures and return-type contracts.

qym analyze

  • qym analyze run <run_id> — triggers AI root-cause analysis on the run's item-metric targets via POST /api/runs/{run_id}/analyze. Accepts --concurrency (default 20, range 1–20) controlling parallel analysis requests. Reports the count analyzed plus a category breakdown.
  • qym analyze summary <run_id> — aggregates already-recorded root-cause categories (from corrections or item metadata) for the run; it does not start new analysis.
qym analyze summary a1b2c3d4 --json

qym config

Two commands for verifying your environment before a run.

  • qym config show — prints the resolved platform_url (from QYM_BASE_URL), whether QYM_API_KEY is set, the TLS-verify setting, and the CA-bundle path. Reads only environment; makes no network call.
  • qym config check — makes a live request to the platform. On success it prints Connected to <url> (and warns if no API key is set). A connection failure reports connection_failed and exits 1; an auth failure reports auth_denied and exits 4.
qym config show
qym config check --json

qym dataset

Manage platform datasets and their versions, aliases, and items. Every dataset command requires an API key (via --api-key or QYM_API_KEY); without one it exits 4 with Missing API key. Provide --api-key or set QYM_API_KEY. All commands accept --project, --api-key, and --platform-url.

CommandKey optionsWhat it does
dataset list--projectList datasets in the project.
dataset get <dataset>—Fetch one dataset.
dataset upload--name, --file, --version (v1), --publish, --production, --input-col, --expected-col, --id-col, --metadata-cols, --labelsUpload a file as a new dataset version. --production sets the production alias.
dataset download <dataset>--output, --version (production)Download a dataset version to a file.
dataset version list <dataset>—List versions.
dataset version create <dataset>--version, --from (production)Create a version, optionally branching from a ref.
dataset version publish <dataset> <version>--productionPublish a version; optionally move the production alias.
dataset version compare <dataset> <version>--base (required)Diff a version against a base.
dataset alias set <dataset> <alias> <version>—Point an alias at a version.
dataset item list <dataset>--version (production), --limit (100)List items in a version.
dataset item runs <dataset> <item_id>--version (production)List runs that touched a dataset item.
 
qym dataset upload --name support-smoke --file datasets/qa.csv \
  --version v2 --publish --production \
  --input-col question --expected-col answer --id-col id

qym dataset version list support-smoke
qym dataset download support-smoke --output snapshot.csv --version v2

Legacy commands

qym dashboard

Opens the platform dashboard at the resolved QYM_BASE_URL (or --platform-url). Pass --no-open to print the URL without launching a browser. Under --json it emits {"dashboard_url": "..."}.

qym submit

Uploads a saved results file to the platform via POST /v1/runs:upload. All three of --file, --task, and --dataset are required; --model and --api-key are optional.

FlagRequiredMeaning
--fileYesPath to the results file (.csv or .json).
--taskYesTask name to record.
--datasetYesDataset name to record.
--modelNoModel name (defaults to empty).
--api-keyNoAPI key; falls back to QYM_API_KEY. Missing key exits 4.
 
qym submit --file qym_results/run.csv --task support-rag --dataset support-smoke --model gpt-4o-mini

Upload accepts .csv and .json only. The /v1/runs:upload endpoint rejects .xlsx with a 400. Convert to CSV or JSON before submitting. See Run ingestion for the full upload contract.

Exit codes

Exit codes are semantic, so CI and agents can branch on them. They come from the ExitCode enum.

CodeNameMeaning
0SUCCESSCommand completed successfully.
1FAILUREGeneral failure (load error, interrupted run, HTTP 5xx, connection failure, multi-run errors).
2USAGE_ERRORBad invocation (missing/conflicting flags, invalid --config JSON, <2 IDs for compare). Also returned by run create when a run's success rate is below 50%.
3NOT_FOUNDRequested resource not found (HTTP 404, or a missing file for submit).
4AUTH_DENIEDAuth failed or missing (HTTP 401/403, or no API key where one is required).
5CONFLICTResource conflict (HTTP 409).

Exit 2 is overloaded. Besides usage errors, qym run create exits 2 when a completed run has a success rate below 50% (printing Warning: Success rate below 50% for runs: ...). In CI, treat exit 2 from a completed run as a quality gate rather than a malformed command.

JSON output contract

With the global --json flag, structured output is written to stdout and humans get stderr. The shapes are stable:

  • Success — the command's data document. A single-model run create emits the result dict; multi-model and multi-run emit an array of result dicts.
  • Error — an object {"error": "<type>", "message": "...", "suggestion": "..."} (suggestion omitted when absent). Error types include usage_error, not_found, auth_denied, connection_failed, and failure.
{
  "error": "auth_denied",
  "message": "Missing API key. Provide --api-key or set QYM_API_KEY.",
  "suggestion": "Check QYM_API_KEY or use 'qym config check' to validate auth."
}

Because errors are written to stdout under --json (not stderr), always check the exit code and parse the error field rather than assuming stdout is a success payload.

Behavior notes & gotchas

  • Streaming is automatic. If both QYM_BASE_URL and QYM_API_KEY resolve (and you did not pass the deprecated --live-mode), the run streams to the platform with live_mode="auto". With no key, runs stay local.
  • Multi-model returns a list. Passing --model "a,b" produces multiple results; --output only supports a single model and is skipped (with a warning) otherwise.
  • Legacy argv is rewritten. qym --task-file ... is rewritten to qym run create --task-file ..., and qym resume --run-file X becomes qym run create --resume-from X. New scripts should use the noun-verb form directly.
  • Connectivity uses the read API. config check probes /api/runs; a clean connection plus a valid (or absent) key returns success.
