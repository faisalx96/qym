SDK GUIDE

Repeat runs & pass@k

LLM outputs vary between attempts. samples=n evaluates every dataset item n times inside one logical run; optional report_k=k publishes unbiased Pass@k and Pass^k estimates from that larger pass pool. Every pass remains available for analysis, review, resume, and comparison.

One repeat experiment, one run. Use samples=n instead of launching n duplicate runs. A repeat experiment has one run ID, one dashboard row, one checkpoint, and pass-aware results.

Quick start

from qym import Evaluator

result = Evaluator(
    task=my_task,
    dataset="my-dataset",
    metrics=["correctness"],
    samples=9,                    # collect 9 executions per item
    report_k=3,                   # publish Pass@3 and Pass^3 from all 9
).run()

mean = result.get_metric_stats("correctness")
print(mean["mean"])
print(mean["ci_low"], mean["ci_high"])        # clustered bootstrap 95% CI

group = result.group_stats("correctness")
print(group["k"], group["report_k"])          # 9, 3
print(group["pass_at_k"], group["pass_hat_k"])

print(result.pass_at(5, "correctness"))       # estimate any 5 of the 9
print(result.pass_hat(5, "correctness"))      # estimate all 5 of the 9

The CLI accepts --samples 9; pass report_k through --config or a run config. Multi-run entries accept samples and report_k in their evaluator configuration.

How it executes

The SDK runs the dataset as n sequential passes: all items finish pass 1 before pass 2 begins. Task retries remain inside their pass. The checkpoint stores one row per item × pass, so resume continues from the missing execution instead of repeating completed work.

The platform stores per-pass output, score, judge metadata, latency, trace, status, and retry information while retaining a reduced run-level score for compatibility. Each pass follows the run-mean rule: a pass whose task or scorer failed contributes 0, or is left out for a lower-is-better metric (direction="minimize"), whose best value is 0. An item's score is the mean over its counted passes, and the run mean is the mean over items. The SDK's get_metric_stats(), group_stats() and summary apply the same rule, so they match the platform.

Collected attempts and reported k

Let n be stored attempts for an item, c the attempts meeting the threshold, and k the requested report_k. qym averages these exact subset probabilities across items:

EstimatePer-item valueMeaning
Pass@k1 - C(n-c, k) / C(n, k)Probability that at least one of k attempts passes.
Pass^kC(c, k) / C(n, k)Probability that all k attempts pass.

This is the mean over every possible k-pass subset, not a random subsample. When report_k is omitted, k equals the available pass count and the estimates reduce to the observed “any passed” and “all passed” results. report_k changes only Pass@k and Pass^k; averages, maxima, consistency, and reliability still use all stored attempts.

Leave estimator headroom. samples must be at least report_k; collecting at least 2 × report_k is recommended. The Runs view flags estimates made from a thinner pass pool as high-noise.

The repeat metrics

Pass/fail follows the metric's direction: score >= threshold, or score <= threshold for a lower-is-better metric, and an errored pass never passes. The threshold defaults to the metric's pass_threshold, else 0.2 for a lower-is-better metric and 0.8 otherwise; it can be changed per call or in the platform analysis. For a lower-is-better metric max_at_k takes each item's lowest (best) score, and errored passes are left out of avg_at_k and max_at_k (they are None when every pass errored).

MetricQuestion it answers
Pass@kCan at least one of k attempts succeed?
Pass^kWill all k attempts succeed?
avg_at_kWhat is the mean over all stored item × attempt scores?
max_at_kWhat is the mean of each item's best stored score?
consistencyHow strongly do repeated pass/fail outcomes agree?
reliabilityAmong items that pass at least once, how often do they pass?

Read Pass@k with Pass^k. A high Pass@k can coexist with a low Pass^k: the system can succeed without being dependable. Pass^k and Consistency make that instability visible.

Curves and uncertainty

All attempts are retained, so result.pass_at(k) and result.pass_hat(k) work for any k <= samples without re-running. One samples=10 experiment therefore yields the full Pass@k and Pass^k curves.

result = Evaluator(task, dataset, metrics=["correctness"], samples=10).run()

for k in range(1, 11):
    print(k, result.pass_at(k), result.pass_hat(k))

get_metric_stats() reports a clustered bootstrap interval for the repeat-run mean: it resamples items and keeps each item's attempts together (the mean over items of each item's mean over its passes, as on the platform). The platform's repeat curves use deterministic 95% item-bootstrap intervals when at least 20 eligible items are available. Curves are cached by run, metric, and threshold, then invalidated when stored scores change.

Platform review workflow

  • The Runs table keeps the experiment as one ordinary row with an ×n tag. Expanding it reveals the group summary and real per-pass rows with their own status, scores, latency, and deep links.
  • Repeat Run Analysis lets you select a metric and threshold, inspect estimator-labelled Pass@k/Pass^k tiles, follow the performance curve, filter from the pass-count distribution, and open a pass from the sweep table.
  • Item rows stay compact until expanded. A repeat item then shows independently toggleable pass output cards; each card carries its execution verdict, latency, trace, metric scores, and editable score controls.
  • Opening a metric aligns its per-pass judge explanation or other structured detail beneath the visible outputs. Older runs without pass-scoped metadata fall back explicitly to the run-level detail.
  • A completed pass can be selected as an execution reference such as <file_path>::pass3 and used in an execution-balanced cohort comparison.

Requirements & caveats

  • Use stochastic generation. A deterministic task returns the same output every pass and cannot reveal run-to-run variation.
  • Keep item IDs stable. Passes and cohort comparisons align by item identity.
  • Budget for n executions. samples=9 means nine task calls and nine metric evaluations per item before retries.
