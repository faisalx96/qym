SDK GUIDE

Multi-model, multi-run & group analysis

One execution rarely settles a question. qym combines multi-model evaluation, multi-run specs, native repeat runs, and offline group-analysis helpers. The same item-aligned math powers estimator-aware Pass@K metrics and noise-aware cohort comparisons in the platform.

This page covers, in order:

  • Multi-model — same task, same dataset, same metrics, only the model changes (model=[...]).
  • Multi-run — tasks, datasets, metrics, or configs differ between runs (Evaluator.run_parallel(...) / RunSpec).
  • Group analysis — compute Pass@K, Pass^K, Avg@K, Max@K, consistency, reliability, and comparison noise over EvaluationResult objects (analyze_group_runs / compare_group_runs).

Align by item ID. Every comparison and group metric on this page aligns runs by dataset item identity, not row position. Give each dataset row a stable id (see Datasets) so runs line up correctly across models and repetitions.

Choosing the right mode

ModeUse whenEntry pointReturns
Multi-model Only the model changes. Task, dataset, metrics, and config are identical. Evaluator(..., model=[...]).run() list[EvaluationResult]
Multi-run Tasks, datasets, metrics, configs, or model groups differ between runs (e.g. prompt A vs prompt B). Evaluator.run_parallel(runs=[...]) list[EvaluationResult]
Repeat run (for Pass@k) Same exact config run k times to measure stability/flakiness. Evaluator(..., samples=k).run() — see Repeat runs & pass@k. Duplicating the same spec k times is deprecated (the SDK warns). EvaluationResult (one logical run)

The first two produce a list of EvaluationResult, which is exactly the input the group-analysis helpers expect. A repeat run (samples=k) reports its group metrics directly via result.group_stats() — no post-hoc grouping needed.

Multi-model runs

Pass a list of model labels to model=. qym creates one run per model, all sharing the same task, dataset, metrics, and config.

from qym import Evaluator


def answer(question: str, model_name: str = "gpt-4o-mini") -> str:
    return call_llm(model=model_name, prompt=question)


results = Evaluator(
    task=answer,
    dataset=dataset,
    metrics=["exact_match", "contains"],
    model=["gpt-4o-mini", "gpt-4.1-mini"],
    config={"run_name": "qa-model-compare"},
).run(show_tui=False, max_parallel_runs=2)

for r in results:
    print(r.run_name, r.success_rate)

List vs single result. A multi-model run returns a list. Internally, run() only takes the multi-model path when more than one model is given (the check is len(models) > 1). So model=["gpt-4o-mini"] — a one-element list — runs as a single model and returns a single EvaluationResult, not a list. Use two or more entries when you want list semantics.

Routing the model into your task

qym injects the model into your task function when the function declares a parameter named model_name or model. If your task hardcodes a provider model and ignores that parameter, every model run will silently call the same model — the comparison looks like it ran but tells you nothing.

# qym fills model_name for each run in the list
def answer(question: str, model_name: str = "gpt-4o-mini") -> str:
    return call_llm(model=model_name, prompt=question)

# Equivalent: name the parameter `model`
def answer(question: str, model: str = "gpt-4o-mini") -> str:
    return call_llm(model=model, prompt=question)

Provider-prefixed model names

You can pass provider-prefixed IDs such as openai/gpt-4o-mini or qwen/qwen3-235b. qym strips the provider prefix for display, run IDs, and artifact paths (so the run shows gpt-4o-mini), while the full prefixed name is preserved for routing into your task (delivered through model / model_full). This is what lets OpenRouter-style identifiers work for the API call while keeping platform displays clean.

Controlling parallelism with max_parallel_runs

ValueBehavior
None (default)All model runs execute in parallel.
1Sequential — one model run at a time.
NAt most N model runs active concurrently.

Concurrency multiplies. Each run uses its own max_concurrency (default 10; see Configs & options). Running models in parallel multiplies the in-flight item calls: parallel runs × max_concurrency. Four models at max_concurrency=10 can produce up to 40 simultaneous provider calls. Cap it with max_parallel_runs, a lower max_concurrency, or both before you hit rate limits.

The CLI equivalent

From the command line, pass comma-separated model names to a single --model option. See the CLI reference for the full flag set.

qym run create \
  --task-file tasks.py --task-function answer \
  --dataset-csv datasets/qa.csv \
  --metrics exact_match,contains \
  --model gpt-4o-mini,gpt-4.1-mini \
  --no-ui

Multi-run specs (run_parallel)

Use Evaluator.run_parallel(...) when runs differ in more than just the model — different tasks, datasets, metric sets, or config values. Each run is described by a dict (or a RunSpec), and they all execute together under one shared dashboard.

The verified signature is:

Evaluator.run_parallel(
    runs,                       # Sequence[dict | RunSpec]
    show_tui=True,
    auto_save=False,            # note: defaults False here, unlike run()
    save_format="csv",
    max_parallel_runs=None,
    observer=None,
) -> list[EvaluationResult]

auto_save differs from run(). run_parallel(...) defaults auto_save=False (and so does arun()), whereas run() defaults auto_save=True. If you want artifacts written automatically, pass auto_save=True — or set a per-run output_path (see below), which is saved regardless.

The run dict shape

Each run definition accepts these keys (mapped to a RunSpec internally):

KeyRequiredMeaning
nameYesStable run key. Required on RunSpec; becomes the run identifier.
taskYesThe callable (or supported framework object) being evaluated.
datasetYesA dataset object, a local .csv/.jsonl path, or a platform dataset name. See the Datasets page for string-resolution rules.
metricsYesList of built-in metric names and/or metric callables. A comma-separated string is also accepted and split into a list.
configNoA dict (or EvaluatorConfig) of run config such as run_name, max_concurrency, task_name.
display_nameNoHuman-readable label for the dashboard / TUI.
metadataNoNon-secret labels (e.g. prompt_version). Keep secrets out.
output / output_pathNoFile path to save this run's artifact to. The format is inferred from the extension (.csv or .json).
modelsNoA list here is expanded into one run per model before execution.
 
from qym import Evaluator

results = Evaluator.run_parallel(
    runs=[
        {
            "name": "baseline",
            "display_name": "Baseline prompt",
            "task": baseline_task,
            "dataset": dataset,
            "metrics": ["exact_match"],
            "config": {"task_name": "support-rag", "max_concurrency": 4},
            "metadata": {"prompt_version": "v1"},
            "output_path": "qym_results/baseline.csv",
        },
        {
            "name": "candidate",
            "display_name": "Candidate prompt",
            "task": candidate_task,
            "dataset": dataset,
            "metrics": ["exact_match", "relevance"],
            "config": {"task_name": "support-rag", "max_concurrency": 4},
            "metadata": {"prompt_version": "v2"},
            "output_path": "qym_results/candidate.csv",
        },
    ],
    show_tui=False,
    max_parallel_runs=2,
)

Using a typed RunSpec

RunSpec is exported from qym and is the typed form of a run dict. Its required field is name; task, dataset, and metrics are also required, while config defaults to an empty EvaluatorConfig and metadata to an empty dict.

from qym import Evaluator, RunSpec
from qym.core.config import EvaluatorConfig

results = Evaluator.run_parallel(
    runs=[
        RunSpec(
            name="baseline",
            task=baseline_task,
            dataset=dataset,
            metrics=["exact_match"],
            config=EvaluatorConfig(task_name="support-rag", max_concurrency=4),
            metadata={"prompt_version": "v1"},
        ),
    ],
)

Multi-model is multi-run under the hood. When you call Evaluator(..., model=[...]).run(), qym builds one run dict per model and delegates to run_parallel(...). That is why both modes return a list and share the same dashboard, observer events, and max_parallel_runs semantics.

Progress for wrappers: the run_matrix event

Both multi-model and multi-run executions emit a run_matrix progress event before any individual run starts, so a wrapper UI can create pending rows up front. Attach a callback via observer=ProgressCallbackObserver(...) (the progress_callback= shortcut lives on Evaluator(...), not on run_parallel(...)). See Progress, observers & wrappers for the full event vocabulary.

from qym import Evaluator, ProgressCallbackObserver, ProgressSnapshot


def on_progress(snapshot: ProgressSnapshot) -> None:
    if snapshot.event == "run_matrix":
        for row in snapshot.run_matrix or []:
            create_pending_row(
                run_id=row["run_id"],
                display_name=row["display_name"],
                model=row.get("model"),
                metrics=row["metrics"],
                total_items=row.get("total_items"),  # None if dataset not yet resolved
            )
        return
    if snapshot.event == "run_start":
        patch_row(
            run_id=snapshot.run_id,
            qym_url=(snapshot.run_info or {}).get("qym_url"),
            platform_run_id=(snapshot.run_info or {}).get("platform_run_id"),
        )


results = Evaluator.run_parallel(
    runs=runs_config,
    observer=ProgressCallbackObserver(on_progress),
)

Each matrix row carries: run_id, display_name, task, dataset, model, metrics, total_items (when the dataset can be resolved up front, otherwise None), status (initially "pending"), and qym_url / platform_run_id (both null in the matrix). Platform URLs are patched in later through each run's own run_start event, because the platform run is only created when that run begins.

Group run analysis

Once you have a list of EvaluationResult objects — from a multi-model run, a multi-run batch, or K repetitions of the same config — the group-analysis helpers compute the same cohort statistics the platform dashboard shows, entirely in Python and offline. They are exported at the top level:

from qym import (
    analyze_group_runs,
    compare_group_runs,
    GroupRunAnalysis,
)

How scores are read

For each run, the helpers read every item's score for the requested metric out of result.results[item_id]["scores"][metric], normalize it to a number, and then aggregate over the union of item IDs across the runs in the group. Score normalization (verified from parse_score_value) is:

Raw valueNormalized score
bool True / False1.0 / 0.0
int / float (finite)the number itself
object with a .score attribute (e.g. MetricResult)recurses into .score
dict with an "error" key0.0
dict with a "score" keyrecurses into "score"
strings "true"/"yes"/"y" or ✓1.0
strings "false"/"no"/"n" or ✗0.0
percent string like "82%"0.82
None, empty, or "n/a"/"na"/"none"/"null"None (excluded for that item)

Missing scores are excluded; errors count as 0. If an item has no score in a given run (missing or None), that run is simply not counted for that item. Failed items count as a 0.0 score — but only when the requested metric is among that run's declared metrics (result.metrics). Erroring on a metric the run never declared does not silently inject zeros.

analyze_group_runs — statistics for one group

Verified signature (all arguments after results are keyword-only):

analyze_group_runs(
    results,                    # Sequence[EvaluationResult]
    *,
    metric: str,                # required
    threshold: float = 0.8,
    track_distribution: bool = False,
    report_k: Optional[int] = None,
) -> dict

k is the number of executions supplied. Set report_k below that count to publish Pass@k and Pass^k as unbiased estimates from the complete execution pool. For an item with n usable scores and c passes, the helper uses 1 - C(n-c, k) / C(n, k) and C(c, k) / C(n, k). Omitting report_k preserves the observed any/all behavior.

from qym import Evaluator, analyze_group_runs

results = Evaluator(
    task=answer,
    dataset=dataset,
    metrics=["correctness"],
    model=["gpt-4o-mini", "gpt-4.1-mini", "gpt-4o"],
).run(show_tui=False)

summary = analyze_group_runs(
    results,
    metric="correctness",
    threshold=0.8,
    report_k=2,
)

print(summary["pass_at_k"], summary["pass_hat_k"], summary["avg_at_k"])

The returned dict contains (verified field names):

KeyMeaning
metric, threshold, report_kEcho of the analysis inputs.
kNumber of runs in the group (len(results)).
total_itemsItems that had at least one usable score across the group.
total_score_count, total_score_sumCount and sum of all included item×run scores.
failed_countNumber of error rows counted across the group.
pass_at_kPass@K — mean probability that at least one of k selected executions passes. With no report_k, this is the observed fraction with any pass.
pass_hat_kPass^K — mean probability that all k selected executions pass. With no report_k, this is the observed fraction where all usable executions pass.
avg_at_k / avg_scoreAvg@K — mean over all included item×run scores. (Both keys carry the same value.)
max_at_kMax@K — mean of the best score per item.
consistencyAverage agreement across runs (see formula below). None if no item had >1 score.
reliabilityAverage pass frequency for solvable items (see below). None if no item had >1 score and a pass.
avg_latency, median_latencyLatency stats in milliseconds over scored item×run pairs.
min_score, stddev_scoreMin and population standard deviation over all included scores.
correct_distributionHistogram of pass counts per item (length k+1), only when track_distribution=True; otherwise None.
itemsPer-item breakdown (scores, passes, attempts, per-item consistency/reliability, etc.).

The metric definitions

These are the exact formulas the helper computes per item, then averages. Let score_count be the usable execution count, pass_count the number scoring >= threshold, fail_count = score_count - pass_count, and k_eff the smaller of report_k and score_count. Without report_k, k_eff = score_count.

MetricPer itemReported as
Pass@K (pass_at_k)1 - C(score_count-pass_count, k_eff) / C(score_count, k_eff)mean of per-item subset probabilities
Pass^K (pass_hat_k)C(pass_count, k_eff) / C(score_count, k_eff)mean of per-item subset probabilities
Avg@K (avg_at_k)—total_score_sum / total_score_count
Max@K (max_at_k)max(scores)mean of per-item max
Consistency2 * max(pass_count, fail_count) / score_count - 1 (only for items with score_count > 1)mean over multi-run items
Reliabilitypass_count / score_count (only items with score_count > 1 and at least one pass)mean over those items

Reading the two stability metrics. Consistency ranges from 0 (a perfect 50/50 split — maximally flaky) to 1 (every run agrees). Reliability is simply how often a solvable item actually passes, so it focuses on items the system can get right but doesn't always. A model that always passes or always fails an item is perfectly consistent; reliability tells you, among the items it sometimes gets right, how dependable it is.

Threshold matters. The default threshold is 0.8. Pass@K, Pass^K, consistency, and reliability all depend on it — a score at or above the threshold counts as a pass. For boolean metrics like exact_match (which normalize to 1.0/0.0) the threshold is effectively a yes/no line. For graded judge scores, set it to the bar you actually care about.

The GroupRunAnalysis wrapper

GroupRunAnalysis is a thin convenience class over a list of results, useful when you want to call several metrics or compare without re-passing the same list.

from qym import GroupRunAnalysis

group = GroupRunAnalysis(results)
acc = group.metric("correctness", threshold=0.8)
overlap = group.metric("contains", threshold=1.0)

# compare_to(other, *, metric, threshold=0.8)
delta = group.compare_to(other_results, metric="correctness", threshold=0.8)

The wrapper exposes the historical defaults. Call analyze_group_runs or compare_group_runs directly when you need report_k or a non-default confidence level.

Execution-balanced cohorts in the platform

The Runs view balances cohort sides by execution count, not row count. An ordinary run contributes one execution, a repeat run with samples=9 contributes nine, and an expanded completed pass contributes one. This allows one repeat experiment to be compared fairly with nine ordinary runs or with any other nine-execution mix.

Selecting a pass creates a reference such as <file_path>::pass3. Compare loads the base repeat run and slices its output, scores, judge metadata, latency, and trace to that pass before analysis. A whole run and one of its own passes cannot overlap across cohort sides. Exact execution references must be disjoint and execution-balanced; different passes from the same repeat run may appear on opposing sides.

compare_group_runs — comparing two groups

Use this to compare a baseline cohort against a candidate cohort (for example, prompt v1 across 3 seeds vs prompt v2 across 3 seeds). It uses stricter cohort semantics than analyze_group_runs.

compare_group_runs(
    left_results,               # Sequence[EvaluationResult] (baseline)
    right_results,              # Sequence[EvaluationResult] (candidate)
    *,
    metric: str,                # required
    threshold: float = 0.8,
    report_k: Optional[int] = None,
    confidence: float = 0.95,
) -> dict

Eligibility is all-or-nothing. An item is eligible only when every execution on both sides has a non-null score. Missing or null scores remove the item from the comparison. A declared-metric execution error is normalized to 0, so it remains eligible and counts as a failure.

from qym import compare_group_runs

comparison = compare_group_runs(
    baseline_results,
    candidate_results,
    metric="correctness",
    threshold=0.8,
    report_k=2,
    confidence=0.95,
)

print(comparison["deltas"]["pass_at_k"])      # candidate minus baseline
print(comparison["noise"]["pass_at_k"])
print(comparison["summary"]["improved_count"])
print(comparison["buckets"]["b_sweeps_a"]["item_ids"])

The returned dict includes (verified):

KeyMeaning
metric, threshold, k, report_k, confidenceInputs, published k, confidence level, and the left execution count.
eligible_itemsItems scored by every run on both sides.
left_run_count, right_run_countRuns per side.
left, rightAggregates per side: pass_at_k, pass_hat_k, avg_at_k, consistency, reliability, avg_attempts.
deltasright - left for pass_at_k, pass_hat_k, avg_at_k, consistency, reliability.
noisePer-metric delta, luck-band half_width, two-sided p_value, and verdict. Reliability is None because its conditional item set makes this band invalid.
summaryimproved_count, regressed_count, unchanged_count (by per-item pass-count move), and avg_attempts_delta.
bucketsFour swing buckets (see below), each with count, percentage, and item_ids.
itemsPer-item rows, sorted so the biggest swings toward the candidate appear first.

Noise bands, p-values, and verdicts

The observed delta alone does not distinguish a real change from favorable executions. For each paired item, qym pools the two cohorts under a no-change hypothesis and estimates how far the right-minus-left metric could move through execution luck. Pass@k, Pass^k, and Consistency use exact binomial estimator variance; Avg@k uses pooled within-item score variance.

FieldInterpretation
half_widthThe symmetric luck band at confidence; the default display is ±half_width at 95%.
p_valueTwo-sided normal probability of a delta at least this extreme under the no-change model.
improvedThe delta is above the positive edge of the luck band.
regressedThe delta is below the negative edge of the luck band.
within_noiseThe delta remains inside the band; it is not distinguishable from execution luck at this confidence level.

The platform's Sweep view shows the corresponding Improved, Regressed, or Within noise verdict for its primary metric, plus each metric's band and p-value. “Within noise” means insufficient evidence of change, not proof that both cohorts are equal.

Swing buckets

For each eligible item, compare_group_runs classifies it into one of four buckets when the result is unambiguous (all runs on a side agree). "A" is the left/baseline group, "B" is the right/candidate group:

BucketConditionRead it as
a_sweeps_bBaseline passes on every run; candidate fails on every run.Regression the candidate introduced.
b_sweeps_aCandidate passes on every run; baseline fails on every run.Clean win for the candidate.
both_passEvery run on both sides passes.Solidly solved either way.
both_failEvery run on both sides fails.Hard item neither side solves.

Items that are mixed (some runs pass, some fail) fall into none of the four buckets — they still appear in items with a move value (right_pass_count - left_pass_count) and feed the improved/regressed/unchanged summary counts.

End-to-end: compare two models with Pass@K

A complete pattern: run the same task across several models, then compute and compare group statistics offline.

from qym import Evaluator, analyze_group_runs, compare_group_runs

baseline = Evaluator(
    task=baseline_task,
    dataset=dataset,
    metrics=["correctness"],
    model=["model-a", "model-b", "model-c"],
    config={"run_name": "baseline"},
).run(show_tui=False)            # -> list[EvaluationResult]

candidate = Evaluator(
    task=candidate_task,
    dataset=dataset,
    metrics=["correctness"],
    model=["model-a", "model-b", "model-c"],
    config={"run_name": "candidate"},
).run(show_tui=False)

base_stats = analyze_group_runs(baseline, metric="correctness", threshold=0.8)
cand_stats = analyze_group_runs(candidate, metric="correctness", threshold=0.8)

print("baseline  pass@k:", round(base_stats["pass_at_k"], 3))
print("candidate pass@k:", round(cand_stats["pass_at_k"], 3))

diff = compare_group_runs(baseline, candidate, metric="correctness", threshold=0.8)
print("pass@k delta:", round(diff["deltas"]["pass_at_k"], 3))
print("regressions:", diff["buckets"]["a_sweeps_b"]["item_ids"])

Use native repeats for new stability experiments. Group helpers can still analyze separate historical results, regardless of whether they came from models, prompts, or earlier repetitions. For a new same-config experiment, prefer samples=n: it preserves all executions inside one logical run and exposes result.group_stats() directly.

Common pitfalls

PitfallSymptomFix
Hardcoded model in the taskmodel=[...] runs but every model gets identical scores.Accept a model_name (or model) parameter and route the API call through it.
Unstable item IDsGroup metrics look noisy; compare_group_runs reports few eligible_items.Give every dataset row a stable id so runs align by identity, not row order.
One-element model listExpected a list, got a single EvaluationResult.Multi-model needs >1 model. Use 2+ entries, or wrap the single result in a list yourself.
Mismatched metric names across runsanalyze_group_runs(metric=...) finds no scores for some runs.Keep the metric you analyze in every run's metrics list, under the same name.
Balanced rows, unequal executionsThe platform will not open the cohort.Balance execution units: a repeat row contributes its samples; a selected pass contributes one.
Provider throttlingTimeouts and sporadic failures under multi-model load.Lower max_parallel_runs and/or per-run max_concurrency.
Forgotten artifactsrun_parallel produced no saved files.run_parallel defaults auto_save=False — pass auto_save=True or set output_path per run.
