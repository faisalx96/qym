SDK guide

Ways to evaluate

qym has one evaluation pipeline and several interchangeable ways to score the output it produces — deterministic code, your own Python, an LLM judge, pairwise comparison, or statistics across repeated runs. They all plug into the same seam, so adding a new method is additive, not a rewrite.

The invariant pipeline

Every evaluation in qym — no matter how outputs are scored — follows the same shape. A way to evaluate is just the step that turns an output into a score; everything around it stays fixed.

dataset item            task                    metric(s)              result
┌──────────────┐    ┌──────────────┐       ┌──────────────┐     ┌──────────────┐
│ id           │    │              │       │ how do we    │     │ scores       │
│ input        │──▶ │ your system  │──out─▶ │ score this   │──▶  │ + metadata   │
│ expected_*   │    │ under test   │       │ output?      │     │ + artifacts  │
│ metadata     │    └──────────────┘       └──────────────┘     │ (+ platform) │
└──────────────┘                                                └──────────────┘

The task is called once per item and returns an output. One or more metrics then score that output. Each metric ultimately produces a numeric score in [0.0, 1.0] (booleans become 1.0/0.0; richer returns carry a label, explanation, and metadata alongside the score). That uniform score contract is what lets every method below be swapped in or combined freely.

Where a method's score comes from. A metric's raw return is normalized by MetricResult.from_raw: bool → 1.0/0.0; int/float → that value; a dict with a score key → that score (plus optional label/explanation/metadata); a dict containing an error key → score 0.0. Any other return type scores 0.0.

How to read the methods below

Each way to evaluate is described with the same six headings so you can compare them directly:

  • What it is — the one-line idea.
  • When to use it — the situation it fits.
  • Inputs it needs — which item fields it reads.
  • How scores are produced — what turns into [0.0, 1.0].
  • Code shape — the minimal way to wire it up.
  • Limitations — the honest caveats.

All five methods are passed through the same metrics=[...] argument on the evaluator (group analysis is the exception — it runs after the runs, over their results).

Deterministic code metrics

What it is. Built-in, dependency-light functions that compare the output to the expected value with fixed rules. They ship with the base package — no extras, no network, no keys.

When to use it. Start here. Use them for smoke tests, regression gates, and any task where the expected output is well-defined (exact strings, substrings, QA answers). They are fast, free, and perfectly reproducible.

Inputs they need. Most read the task output and the item's expected_output. faithfulness additionally reads a context field from the item input. response_time and token_count read only the output.

How scores are produced. By name in the registry (verified in qym/metrics/__init__.py). The seven code metrics available without any extra:

NameWhat it computesScore
exact_matchStripped string equality of output vs expected.1.0 if equal, else 0.0
containsCase-insensitive substring: is expected inside output?1.0 / 0.0
fuzzy_matchSequence similarity via difflib.SequenceMatcher(...).ratio().continuous 0.0–1.0
correctnessSQuAD-style token-level F1 of output vs expected (lowercased, articles & punctuation removed).continuous 0.0–1.0
faithfulnessFraction of meaningful output tokens (non-stopword, >1 char) that also appear in the input context.continuous 0.0–1.0
response_timePlaceholder — actual timing is handled by the evaluator.always 1.0
token_countRough estimate: word count × 1.3.integer (token estimate)

Code shape.

from qym import Evaluator, CsvDataset

result = Evaluator(
    task,
    CsvDataset("qa.csv"),
    metrics=["exact_match", "contains", "fuzzy_match"],
).run(show_tui=False)

Limitations. Purely lexical — they cannot judge meaning, so a correct paraphrase scores poorly on exact_match. fuzzy_match's threshold argument is documented but not used in the score (it always returns the raw ratio). response_time is a placeholder that always returns 1.0, and token_count is a word-count approximation, not a real tokenizer.

Two naming gotchas. The registry name is contains (not contains_expected). And faithfulness is the code token-overlap heuristic — the LLM version is a separate metric named faithfulness_llm (judges section below).

Custom metric callables

What it is. Any Python function you pass directly in metrics=[...]. This is the escape hatch for structured or domain-specific scoring (parse JSON, run a SQL query, check a regex, call your own validator).

When to use it. When no built-in fits — the output is structured, or "correct" requires logic only you know. Keep them deterministic and side-effect-free where you can.

Inputs they need. qym resolves arguments by parameter name when your names are drawn from the recognized set: output, expected, input_data, metadata, item_metadata (metadata and item_metadata both receive the item's metadata). Declare only the ones you use. If your parameter names fall outside that set, qym falls back to positional order: (output, expected, input_data, item_metadata) — so positional order is load-bearing there.

How scores are produced. Return a bool, a number, a {"score": ...} dict (optionally with label, explanation, metadata), or a MetricResult. A returned dict containing an error key scores 0.0 and records the error.

Code shape.

import json

def valid_json(output, expected=None):
    """Score 1.0 if the output parses as JSON."""
    try:
        json.loads(str(output))
        return 1.0
    except Exception:
        return 0.0

# Or return rich structure with metadata:
def has_citation(output, expected=None):
    cited = "[" in str(output) and "]" in str(output)
    return {"score": 1.0 if cited else 0.0,
            "label": "cited" if cited else "uncited"}

result = Evaluator(task, dataset, metrics=[valid_json, has_citation]).run(show_tui=False)

To reference a custom metric by string later (e.g. so it appears in group analysis under a stable name), register it:

from qym.metrics.registry import register_metric

register_metric("valid_json", valid_json)
# now usable as metrics=["valid_json"]; custom names shadow built-ins of the same name

Metrics are keyed by name. Internally a metric callable is keyed by its __name__. Two callables with the same __name__ (two create_judge(name="x", ...) with the same name, or two bare lambdas, both named <lambda>) collide — only the last survives. Give each custom metric a distinct name.

Limitations. You own correctness and robustness — a custom metric should tolerate None and unexpected types. If your task returns the envelope {"output": ..., "metadata": {...}}, a custom metric receives the whole envelope as output (built-ins auto-unwrap it; yours should read output["output"] if needed). See Metrics for the full contract.

LLM-as-judge

What it is. An LLM scores a single output against criteria expressed in a prompt, returning a verdict that maps to a number. Use the seven prebuilt judges or build your own with create_judge.

When to use it. When "good" is semantic and no deterministic rule captures it — relevance, faithfulness, tone, helpfulness. Add judges after the deterministic loop already works, since they are slower, cost money, and are non-deterministic.

Inputs they need. Judges require the optional openai client and judge credentials (see callout). The prebuilt judges read these item fields via their prompt templates:

JudgeReadsLabels → score
relevancequestion, outputrelevant 1.0 / irrelevant 0.0
correctness_llmquestion, expected, outputcorrect 1.0 / incorrect 0.0
faithfulness_llmcontext, question, outputfaithful 1.0 / unfaithful 0.0
hallucinationcontext, outputgrounded 1.0 / hallucinated 0.0
concisenessquestion, outputconcise 1.0 / verbose 0.0
toxicityoutput onlynon-toxic 1.0 / toxic 0.0
tool_callingquestion, tool_definitions, tool_callscorrect 1.0 / incorrect 0.0

"Reads x" means the prompt has a {x} placeholder filled from a matching key in the item input dict (plus {output}, {expected}, {input} always available).

How scores are produced. The judge calls an OpenAI-compatible chat API with response_format={"type": "json_object"}, expecting {"verdict": <label>, "explanation": ...}. The verdict is matched to one of the declared choices and that choice's number becomes the score; the explanation is carried in metadata. If the model returns invalid JSON, qym retries once with a stricter nudge, then falls back to fuzzy label extraction (snap_to_rail); if it still cannot parse, the result scores 0.0 with an error in metadata.

Code shape.

export QYM_JUDGE_MODEL=gpt-4o-mini
export QYM_JUDGE_API_KEY=sk-...        # falls back to OPENAI_API_KEY
# optional: QYM_JUDGE_BASE_URL (falls back to OPENAI_BASE_URL) for vLLM / proxies
from qym import Evaluator
from qym.metrics.judges import create_judge

# Prebuilt judges by name:
result = Evaluator(task, dataset, metrics=["relevance", "correctness_llm"]).run(show_tui=False)

# Custom judge: a prompt template + a label-to-score map
helpfulness = create_judge(
    name="helpfulness",
    prompt="Question: {question}\nAnswer: {output}\nIs the answer helpful or unhelpful?",
    choices={"helpful": 1.0, "unhelpful": 0.0},
)
result = Evaluator(task, dataset, metrics=[helpfulness]).run(show_tui=False)

Setup & prompt validation. Judges need pip install openai (missing → ImportError). The judge config validate() raises RuntimeError if the model or API key is missing. A prompt placeholder with no matching key raises JudgeInputError before the LLM call; align dataset fields or use input_mapping.

Limitations. Cost, latency, and non-determinism (even at temperature 0). A judge is only as good as its prompt and label set, and can be miscalibrated or biased. Treat judge scores as evidence to review, not ground truth. Full details in LLM-as-judge & pairwise judging.

Pairwise / comparative judging

What it is. Instead of scoring one output in isolation, the judge is shown two outputs (A and B) for the same item and decides which is better. Research consistently finds relative comparison more reliable than absolute scoring.

When to use it. A/B'ing two prompts, two models, or a candidate against a reference answer — when "which is better" is a more meaningful question than "score this from 0 to 1."

Inputs it needs. The two outputs: {output_a} is the task output being evaluated; {output_b} is taken from input_data["output_b"] if present, otherwise from the item's expected. The prompt may also reference {expected}, {input}, and any key in the item input dict.

How scores are produced. create_pairwise_judge uses a fixed choice map (you cannot override it): {"A": 1.0, "B": 0.0, "tie": 0.5}. The judge returns {"verdict": "A"|"B"|"tie", "explanation": ...}; A winning scores 1.0, B winning 0.0, a tie 0.5. Label and explanation are carried in metadata.

Code shape.

from qym.metrics.judges import create_pairwise_judge

vs_reference = create_pairwise_judge(
    name="vs_reference",
    prompt=(
        "Question: {question}\n"
        "Response A: {output_a}\n"
        "Response B: {output_b}\n"
        "Which response better answers the question?"
    ),
)
# output_b defaults to the item's `expected`; the verdict maps A=1.0 / B=0.0 / tie=0.5
result = Evaluator(task, dataset, metrics=[vs_reference]).run(show_tui=False)

Limitations. A single A/B call can have position bias (which answer is shown first), and a per-item pairwise score is not a calibrated quality number — it only says A beat B on this item. It needs both outputs available at scoring time. Like all judges, it requires the openai client and judge credentials.

Multi-run / group analysis (Pass@K)

What it is. A statistical way to evaluate: run the same dataset multiple times (e.g. a non-deterministic system K times), then aggregate per-item scores across runs to measure not just average quality but consistency and reliability. This is the only method that operates on a group of results rather than a single output.

When to use it. When run-to-run variance matters: stochastic agents, retried tool use, "does it pass at least once / does it pass every time." Also for comparing two cohorts of runs (e.g. before vs after a change).

Inputs it needs. A sequence of EvaluationResult objects (the same items, scored on the same metric), plus a threshold (default 0.8) that defines a per-attempt "pass."

How scores are produced. Items are unioned across runs; null/missing scores are excluded, error rows count as 0.0. For each item with K attempts, pass_count is the number of attempts >= threshold. The aggregate (verified in qym/core/group_analysis.py):

MetricMeaning
pass_at_kFraction of items that pass at least once (pass_count > 0).
pass_hat_kFraction of items that pass on every attempt (pass_count == score_count).
avg_at_k / avg_scoreMean of all per-attempt scores.
max_at_kMean across items of each item's best attempt.
consistencyPer item (with >1 attempt): 2 × max(pass, fail) / count − 1, averaged. 1.0 = always agrees with itself.
reliabilityFor items that pass at least once: pass_count / count, averaged.

Code shape. Produce the runs (multi-model returns a list; run_parallel runs several specs), then analyze:

from qym import Evaluator, analyze_group_runs, compare_group_runs

# K runs of the same eval (a multi-model run returns a LIST of EvaluationResult)
runs = Evaluator(task, dataset, metrics=["correctness"],
                 model=["gpt-4o-mini", "gpt-4o-mini", "gpt-4o-mini"]).run(show_tui=False)

stats = analyze_group_runs(runs, metric="correctness", threshold=0.8)
print(stats["pass_at_k"], stats["pass_hat_k"], stats["consistency"])

# Compare two cohorts (e.g. old prompt vs new prompt):
diff = compare_group_runs(old_runs, new_runs, metric="correctness", threshold=0.8)
print(diff["deltas"]["pass_at_k"])
# Or run several explicit run specs at once (run_parallel is a staticmethod):
results = Evaluator.run_parallel(
    runs=[
        {"task": task, "dataset": dataset, "metrics": ["correctness"], "run_name": "a"},
        {"task": task, "dataset": dataset, "metrics": ["correctness"], "run_name": "b"},
    ],
    show_tui=False,
)

Both functions are top-level exports (from qym import analyze_group_runs, compare_group_runs); GroupRunAnalysis wraps the same logic with .metric(...) / .compare_to(...).

It mirrors the platform. These helpers reproduce the platform dashboard's group-metric semantics in pure Python, so you can compute Pass@K, consistency, and reliability locally without uploading runs.

Limitations. Meaningful only with K > 1 runs (consistency/reliability are None for single-attempt items). It re-uses an underlying per-item metric, so it inherits that metric's quality. compare_group_runs uses strict cohort semantics: an item is only counted when it has a non-null score in every run on both sides. See Multi-model, multi-run & group analysis.

Adding a new evaluation method

The point of this abstraction is that new methods slot in additively — no surrounding code changes. A new method (say, ELO ratings, an embedding-similarity metric, or a tournament) just has to satisfy the same score contract every method here already meets:

  1. Produce a normalizable score. Return a bool, a number, a {"score": ...} dict (optionally with label, explanation, metadata), or a MetricResult. MetricResult.from_raw turns it into a [0.0, 1.0] score; a dict with an error key scores 0.0. Anything else scores 0.0.
  2. Be a callable with recognized parameters. Accept some subset of output, expected, input_data, metadata / item_metadata by name (or rely on the positional order output, expected, input_data, item_metadata). Sync or async both work. Declare exactly the item fields you read.
  3. Be referenceable. Pass the callable directly in metrics=[...], or give it a stable name with register_metric(name, fn) so it can be used as a string and shows up in artifacts and group analysis under that name. Ensure the callable's __name__ is unique.

Methods that need more than a single output (pairwise needs two; ELO and tournaments need cross-item or cross-run state) follow the same pattern as create_pairwise_judge and the group-analysis helpers: a factory that closes over the extra inputs and returns a callable obeying the score contract, or a post-hoc analyzer over a list of EvaluationResult. Either way the run pipeline, the dataset, the task, and every other page stay untouched — which is exactly why a new way to evaluate is a new card here, not a rewrite of the SDK.

Good first set. Use one deterministic metric and at most one judge until you can tell a good item from a bad one by eye. Scale the dataset and the method count only once the loop is trustworthy.
