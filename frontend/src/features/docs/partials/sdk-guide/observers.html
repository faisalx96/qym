SDK GUIDE

Progress, observers & wrappers

When you embed qym inside another Python system — a service, queue worker, notebook, CI harness, scheduler, or internal eval platform — you need to surface progress in your UI. qym gives you two local integration layers for exactly that: a simple progress_callback and a lower-level EvaluationObserver.

Local progress vs. platform wire events. This page is about local progress events — in-process callbacks that drive your own job table, websocket, or cell output. They are a different vocabulary from the platform wire events the SDK streams to qym over HTTP (covered in the Developer/API ingestion docs). Don't confuse the two: a ProgressSnapshot with event="item_complete" is not the same as the item_completed wire event.

The two integration layers

Both layers are driven by the same internal observer mechanism, so they see the same lifecycle. Pick by how much structure you want.

LayerUse it whenHow you wire it
Progress callbackYou want one function that receives structured progress snapshots with counters already computed.Evaluator(..., progress_callback=fn)
ObserverYou want named lifecycle methods, explicit composition, or access to richer per-event arguments.observer=ProgressCallbackObserver(fn) or a subclass of EvaluationObserver

All three of Evaluator, EvaluationObserver, ProgressCallbackObserver, and ProgressSnapshot are top-level exports from qym.

from qym import (
    Evaluator,
    EvaluationObserver,
    ProgressCallbackObserver,
    ProgressSnapshot,
)

Always pass show_tui=False in a wrapper. When qym runs inside a service, worker, notebook, or CI job, your code owns the status display. Disabling the terminal dashboard keeps qym from fighting your output. The web UI — when platform streaming is configured — is unaffected.

Progress callback (the simple path)

For most wrappers, pass a single callback to the Evaluator constructor. It receives an immutable ProgressSnapshot at each lifecycle point, with running counters (completed, failed, in_progress, pending) already maintained for you.

from qym import Evaluator, ProgressSnapshot


def on_progress(snapshot: ProgressSnapshot) -> None:
    jobs.update(
        run_id=snapshot.run_id,
        event=snapshot.event,
        finished=snapshot.finished,        # completed + failed
        failed=snapshot.failed,
        total=snapshot.total_items,
        percent=snapshot.percent_complete,  # 0.0..100.0
    )


result = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=["exact_match"],
    progress_callback=on_progress,
).run(show_tui=False)

Internally the constructor wraps your function in a ProgressCallbackObserver, which is the layer that converts raw lifecycle hooks into snapshots. The two forms below are equivalent on Evaluator(...):

# Shortcut form
Evaluator(..., progress_callback=on_progress)

# Explicit form (same result)
Evaluator(..., observer=ProgressCallbackObserver(on_progress))

ProgressSnapshot is a frozen dataclass. Every field below is verified against the SDK; not all fields are populated on every event — the table notes which events carry which extras.

Computed properties

Two read-only properties save you from recomputing the obvious:

  • snapshot.finished → completed + failed.
  • snapshot.percent_complete → finished / total_items * 100.0, returning 0.0 when total_items is 0 or unknown.

The local event vocabulary

The event field on a ProgressSnapshot takes one of these exact strings. This is the vocabulary your wrapper should branch on:

EventFires when
run_matrixA multi-model or multi-run shape is known, before any run starts. Carries run_matrix + total_runs.
run_startA run is about to begin. run_info now carries platform links if streaming.
item_startAn item begins processing. Carries item_index + payload.
metric_resultA metric finishes computing for an item. Carries metric_name, score, metadata.
item_completeAn item completes successfully. Carries the result dict.
item_errorAn item fails. Carries the error string.
warningqym detects an integration concern (e.g. a sync task at high concurrency). Carries message.
run_completeThe run finishes. Carries result_summary.

The metric event is metric_result, not metric_complete. Older docs and snippets used metric_complete — that string is never emitted. Branch on "metric_result". Likewise, item events are item_complete / item_error (not item_completed, which is a platform wire event).

Typical single-run sequence

run_start
item_start
metric_result      (one per metric, per item)
item_complete      (or item_error on failure)
...
run_complete

For multi-model (model=[...]) or multi-run (run_parallel) evaluations, a single run_matrix event precedes the per-run sequences:

run_matrix
run_start ... run_complete   (run 1)
run_start ... run_complete   (run 2)

Custom observers

Subclass EvaluationObserver when you want named lifecycle methods rather than one callback that branches on event. Every hook has a no-op default, so override only the ones you need. Hooks always receive run_id as a keyword argument.

HookSignatureFires when
on_run_matrix(matrix_id, runs, total_runs)A multi-model / multi-run shape is known.
on_run_start(run_id, run_info, total_items, metrics)A run is starting.
on_item_start(run_id, item_index, payload=None)An item begins processing.
on_metric_result(run_id, item_index, metric_name, score, metadata=None)A metric finishes for an item.
on_item_complete(run_id, item_index, result)An item completes successfully.
on_item_error(run_id, item_index, error)An item fails.
on_warning(run_id, message)qym detects a performance/integration warning.
on_run_complete(run_id, result_summary)A run finishes.

The hook is on_run_complete and its last argument is result_summary — a dict, not an EvaluationResult. It contains success_rate, total_items, metrics, and run_metadata. For the full result object, return value from run() is the source of truth.

from qym import Evaluator, EvaluationObserver


class JobObserver(EvaluationObserver):
    def on_run_matrix(self, run_id, matrix_id, runs, total_runs):
        for row in runs:
            jobs.create_pending(
                matrix_id=matrix_id,
                run_id=row["run_id"],
                display_name=row.get("display_name"),
                model=row.get("model"),
                total_items=row.get("total_items"),
            )

    def on_run_start(self, run_id, run_info, total_items, metrics):
        jobs.mark_running(
            run_id=run_id,
            total_items=total_items,
            metrics=metrics,
            qym_url=(run_info or {}).get("qym_url"),
        )

    def on_item_complete(self, run_id, item_index, result):
        jobs.record_item(run_id=run_id, item_index=item_index, status="complete")

    def on_item_error(self, run_id, item_index, error):
        jobs.record_item(run_id=run_id, item_index=item_index, status="error", error=str(error))

    def on_run_complete(self, run_id, result_summary):
        jobs.mark_complete(run_id=run_id, success_rate=result_summary["success_rate"])


result = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=["exact_match"],
    observer=JobObserver(),
).run(show_tui=False)

Hooks receive run_id as a keyword. The dispatcher always injects run_id=..., so a custom hook's signature must accept it — either name it first (as above) or absorb it with **kwargs. on_run_matrix gets both run_id (the matrix id) and matrix_id.

Multi-run & multi-model wrappers

The progress_callback= shortcut exists only on the Evaluator(...) constructor. For Evaluator.run_parallel(...) (multi-run), pass an observer instead:

from qym import Evaluator, ProgressCallbackObserver, ProgressSnapshot


def on_progress(snapshot: ProgressSnapshot) -> None:
    if snapshot.event == "run_matrix":
        for row in snapshot.run_matrix or []:
            jobs.create_pending(
                run_id=row["run_id"],
                display_name=row.get("display_name"),
                model=row.get("model"),
                total_items=row.get("total_items"),
            )
        return

    if snapshot.event == "run_start":
        info = snapshot.run_info or {}
        jobs.attach_platform_link(
            run_id=snapshot.run_id,
            qym_url=info.get("qym_url"),
            platform_run_id=info.get("platform_run_id"),
        )
        return

    jobs.update_progress(
        run_id=snapshot.run_id,
        event=snapshot.event,
        percent=snapshot.percent_complete,
    )


results = Evaluator.run_parallel(
    run_specs,
    observer=ProgressCallbackObserver(on_progress),
    show_tui=False,
)

The run_matrix row shape

The run_matrix event lets you pre-create pending rows in your UI before any run starts. Each row is a dict with these keys:

{
  "index": 0,
  "run_id": "qa-gpt-4o-mini-260621-1000",
  "display_name": "qa [gpt-4o-mini]",
  "task": "answer-question",
  "task_file": null,
  "task_function": null,
  "dataset": "qa.csv",
  "model": "gpt-4o-mini",
  "metrics": ["exact_match"],
  "total_items": 100,
  "status": "pending",
  "qym_url": null,
  "platform_run_id": null
}

At the run_matrix stage, qym_url and platform_run_id are always null — they are populated later, per run, in the run_start snapshot's run_info once the platform assigns them.

A multi-model run() returns a list. When you pass model=[...], Evaluator(...).run() returns a List[EvaluationResult] — one per model — not a single result. run_parallel() always returns a list. Handle both shapes in your wrapper (see the Multi-model & group analysis page).

A realistic service wrapper

This pattern ties it together: local job progress for your own UI, platform streaming for a shared review link, durable artifacts for evidence, and non-secret correlation IDs in run_metadata.

import os
from qym import CsvDataset, Evaluator, ProgressSnapshot


def launch_eval(job):
    dataset = CsvDataset(
        job.dataset_path,
        input_col="question",
        expected_col="answer",
        id_col="id",
        metadata_cols=["domain", "difficulty"],
    )

    def on_progress(snapshot: ProgressSnapshot) -> None:
        if snapshot.event == "run_matrix":
            for row in snapshot.run_matrix or []:
                jobs.create_pending_child(job.id, row)
            return

        update = {
            "qym_run_id": snapshot.run_id,
            "event": snapshot.event,
            "finished": snapshot.finished,
            "completed": snapshot.completed,
            "failed": snapshot.failed,
            "total": snapshot.total_items,
            "percent": snapshot.percent_complete,
        }
        if snapshot.event == "run_start":
            info = snapshot.run_info or {}
            update["qym_url"] = info.get("qym_url")
            update["platform_run_id"] = info.get("platform_run_id")
        if snapshot.event == "item_complete":
            update["last_item_ms"] = (snapshot.result or {}).get("total_time_ms")

        jobs.update(job.id, **update)

    result = Evaluator(
        task=job.task,
        dataset=dataset,
        metrics=["exact_match", "relevance"],
        model=job.models,
        config={
            "run_name": job.name,
            "task_name": job.task_name,
            "max_concurrency": job.max_concurrency,
            "timeout": 300,
            "output_dir": "qym_results/jobs",
            # Platform streaming (optional) for a shared review link:
            "platform_url": os.environ.get("QYM_BASE_URL"),
            "platform_api_key": os.environ.get("QYM_API_KEY"),
            # Non-secret correlation IDs only:
            "run_metadata": {
                "job_id": job.id,
                "owner": job.owner,
                "prompt_version": job.prompt_version,
            },
        },
        progress_callback=on_progress,
    ).run(show_tui=False, max_parallel_runs=job.max_parallel_runs)

    # result is a list when job.models has more than one model.
    results = result if isinstance(result, list) else [result]
    jobs.finish(
        job.id,
        result_count=len(results),
        artifact_paths=[r.last_saved_path for r in results],
    )
    return result

For the platform side of this wrapper — how QYM_BASE_URL / QYM_API_KEY are resolved and what appears in the shared dashboard — see Configs & options. To read durable results off EvaluationResult, see Results, artifacts & tracing.

Rules for reliable wrappers

Callbacks and hooks run inside the evaluation process, in the hot path. Treat them accordingly.

  • Keep callbacks fast and non-blocking. If publishing progress to another service can block, enqueue the update locally and let a separate worker publish it. A slow callback throttles the whole run.
  • Treat progress as status, not as results. Progress events are for live UI; the authoritative evidence is the returned EvaluationResult (or the saved artifacts), not the snapshots.
  • Exceptions in your callback are swallowed. The dispatcher catches and logs failures so a buggy observer can't crash a run — which also means a silently failing callback won't surface loudly. Test it.
  • Branch defensively on event. New event names may be added; default to a generic "update" path rather than assuming an exhaustive set.
  • Use run_metadata for correlation IDs (job id, owner, prompt version) so you can join qym runs back to your own records.
  • Never put secrets in metadata, item metadata, callback logs, or artifact paths. All of these may be persisted to disk and streamed to the platform.
  • Always show_tui=False when your wrapper owns the display.
