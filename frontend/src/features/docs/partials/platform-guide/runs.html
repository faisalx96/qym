PLATFORM GUIDE

Runs, selection & cohorts

The Runs page is the project ledger: filter it to a comparable slice, open a run for evidence, or select whole runs and individual repeat passes for comparison.

Read and narrow the table

Search runs (press /) finds a run by the name the table shows, its run name, or the start of its run ID. The search is part of the page address, so a reload, the Back button, or a shared link keeps it. The time control limits runs to today, the last 7 or 30 days, or a Range of two dates (both included).

Use the toolbar to filter by task, dataset and version, model, status, or owner. Columns shows and hides every column: the run columns (run name, status, task, model, dataset, owner, date, analysis, experiment, version, duration), metrics, and system fields. A hidden frozen column leaves no gap: the frozen columns close up around it. With the run name hidden, Select still shows its checkboxes, and unchecking everything keeps the run name so the table is never empty. Its Frozen columns section chooses which of run name, status, task, model, dataset, owner, and date stay in place while the table scrolls sideways: all of them by default. Unfreeze some to see more scores on a narrower screen; the choice is remembered in this browser, and Reset to default freezes them all again. When the frozen columns would take more than about half of the table's width, the rightmost ones (date first, then owner, dataset and so on, never the run name) scroll with the table until the rest fit, and the section names them. Your choice is not changed: a wider window freezes them again. Click a column heading to sort (or Tab to it and press Enter); the run name is a link to its detail page, so middle-click, Open in new tab, and Copy link work as anywhere else.

Share or bookmark a view

The search, filters, the time range, the sort, and the page are part of the address: ?q=…&task=…&model=…&dataset=…&status=…&owner=…&range=week&sort=model-asc&page=2 (range is today, week, month for 30 days, or custom with a from date, a to date or both). Copy the URL to send a teammate the same view, bookmark it, or open it in a new tab. A model name alone covers its standard and reasoning variants. Browser Back from a run returns to the same page, sort, and scroll position, and shows the rows you left at once while it refreshes them. Charts and Models keep their filters in the address the same way. A run opened from this list carries the list's search, filters, time range and sort (?list=…), so the up and down arrows in its header step to the previous and next run in this order, across pages.

Each row shows workflow status, run identity, task, model, dataset, code version, metric means, latency, owner, date, duration, and available actions. Running repeat evaluations also show current pass progress. A finished run tagged Incomplete completed without all of its data: some items never arrived, or the platform rejected some of its events. Hover the tag for the reason; the run page lists what is missing. An item whose failure event was rejected still counts as a task error when its final attempt failed; an item with no outcome at all shows as Not received and is left out of Execution success and of the means.

The numbers above the table

The top bar (and each project card on Overview) sums the runs in scope: All runs in the project, or Filtered runs while filters are active. Hover a number for its definition.

  • Runs — runs in scope.
  • Execution success — the share of item executions that ran without a task error. A repeat run counts each item once per pass, judged by that pass's last attempt. Metric (scorer) errors do not lower it; they count in runs with errors. An item of a completed run whose outcome never reached the platform (Not received on the run page) is left out. It replaces the older Avg Success, so it can differ from earlier releases.
  • Runs with errors — runs with at least one task or metric error.
  • Models and Items — distinct model names (reasoning and standard variants count once) and items evaluated (a repeat run counts each item once).

Expand a repeat row

A repeat evaluation is one row marked with its pass count (×k / k passes). It represents one run in which every dataset item was executed k times. Open its chevron to reveal:

  • one member row per completed or active pass, with that pass's metric means, latency, errors, item count, date, and duration;
  • queued pass ranges while a live run is still progressing;
  • best-across-pass highlights where a unique best metric or latency exists; and
  • a Group metrics strip with metric and pass-threshold controls.

Click a completed pass row to open the run through a pass lens. That view uses the selected pass's output, score, latency, status, and trace rather than the run's reduced values.

The parent row is reduced; member rows are executions. For a repeat run, each item metric on the parent is the mean across stored passes. Expand it when variance matters.

Select mode

Check rows, use the table's select-all checkbox for the current page, or focus a row and press x. The status bar then offers the actions allowed for that selection:

ActionRule
CompareSelect at least two references. On the Compare page, Copy link copies the comparison with its metric, item filter, winner, search, sort, page, tab, and open item; Export HTML downloads it as a standalone file. Each output's run name opens that item in its run.
CohortLock the current selection as Cohort A, then build an execution-balanced Cohort B.
SubmitEvery selected run must be in COMPLETED, FAILED, or REJECTED, and yours unless you are a project manager or admin. A confirmation lists the runs and takes an optional comment; the runs are submitted together in one request, so either all of them are submitted or none is.
DeleteEvery selected run must be deletable by you: owner, project manager, or platform admin.
ClearLeave selection or cancel cohort mode. Esc does the same.

The selection, and a locked Cohort A, stay until you clear them: open a run or Compare and come Back, go to another page of the project and return to Runs, or reload, and the same runs are still checked. Each project keeps its own selection in this browser tab. Signing out clears it, with the tab's saved filters, so whoever signs in next in that tab starts clean; a reload keeps it. A run deleted in the meantime drops out of it, and so does a pass reference (checked or in Cohort A) once its run's passes have changed. The pager stays in the status bar next to the selection actions, so you can move between pages with runs selected; in a narrow window it takes a second row there.

Select an individual pass

Expand a repeat row and check a completed pass to create a pass reference. It addresses one execution rather than the whole run and can join a normal comparison or a cohort. The parent checkbox follows the visible scope: collapsed, it selects the repeat run; expanded, it selects all available passes. Selecting the whole run removes its selected pass references, and selecting a pass removes its whole-run reference.

Compare runs against a baseline

Compare opens with one card per run and a Per-Run Averages table. Columns are labelled by model and start date (gpt-4o · Sep 28), or, when every run uses the same model, by the part of the run names they do not share. Hover a heading for the full run name. The table scrolls sideways inside its card with the metric column pinned, so many runs never squeeze it.

  • Baseline — the first run (Cohort A's first run for a cohort) unless you pick another. Every other column shows its change against it on each metric, the mean change over the items both runs scored (so a partial run is not compared on items it never ran): green when better, red when worse (by the metric's declared direction; a metric without one is never colored), muted when the change is within noise.
  • Noise band — ± the 95% band of the mean per-item difference over the items both runs scored. A change inside it is within noise. Hover the change for the p-value and the number of paired items.
  • ↑ / ↓ counts — how many items improved or regressed against the baseline. Click one to show exactly those items in the item list (a banner names the filter; Clear removes it).
  • Each pass / Run average — a repeat run shows one column per pass under its run heading, or one column with the mean over its passes (Avg@k).

The baseline and column choice are kept in the link (baseline, columns=runs). When the runs used different datasets or dataset versions, a notice says so: score changes can then come from the data, and only items present in both runs are paired. On a run page, Compare with previous opens the run next to the previous finished run of the same task, model and dataset, as the baseline; the button shows the change in the run's primary metric (the two run means, not tested for noise).

Review workflow

An owner submits a finished run (a project manager or admin can submit it on the owner's behalf); a project manager or admin approves or rejects it and can later withdraw that decision. Submitting always asks for confirmation first, with an optional comment kept in the review history. Managers and admins can also transfer a run to another project member from its row actions. The row shows the new status and its next actions as soon as the action succeeds; if an action is refused, the message says why (for example, that the run is already submitted). While a run is submitted or approved its scores cannot be edited or reset on the run or Compare page, and its passes cannot be deleted. While a run is submitted, approved, or rejected its results are frozen: late events from the evaluation client cannot change its scores or move it back to running. Withdrawing a decision returns the run to its execution result, so a failed run stays failed. The run page lists every submission, decision, and withdrawal with who made it, when, and the comment.

How cohort accounting works

Cohorts compare equal numbers of executions, not equal numbers of rows:

Selected referenceExecution units
Classic run1
Whole repeat run with samples=kk
One completed pass from a repeat run1
  1. Select the references for Cohort A and click Cohort.
  2. Select Cohort B until its execution counter equals Cohort A.
  3. Click Open Cohort.

The two sides must be disjoint. A whole repeat run cannot face one of its own passes because that execution is already included. Two different passes from the same repeat run may sit on opposite sides.

Do not balance cohorts by row count. One ×8 repeat row contributes eight executions. Match it with eight classic runs, eight individual pass references, or another mix totaling eight.

Keyboard shortcuts

These single keys work on the Runs page when no field, menu, or dialog has focus, and never with Ctrl, Cmd, or Alt held. Press ?, or Shortcuts at the right of the status bar (while runs are selected in a narrower window, the button makes room for the pager; ? still works), to list them. To stop letter and number keys from acting at all (for example with speech input), turn off Single-key shortcuts in that list; the choice is remembered in this browser and also applies to the trace viewer's j, k, and /. Esc keeps working, and the Shortcuts button turns them back on.
