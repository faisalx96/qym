Authentication

qym authenticates HTTP callers two ways: ingestion clients (the SDK, the CLI, and your own scripts) present a project-scoped API key as a Bearer token, while people working in the dashboard authenticate through a browser session. This page covers how keys are created, formatted, and verified, and which endpoints accept which credential.

The two credential types

Every authenticated endpoint expects exactly one of these. They are not interchangeable: a Bearer API key will not authorize a dashboard-only action, and a browser session cannot stream a run.

API key (Bearer token)

For machine clients: the SDK, the CLI, and direct HTTP. Always bound to a single project. Used for run ingestion and the project-scoped read API. Sent as Authorization: Bearer <token>.

Browser session

For humans in the dashboard. Established by the deployment's configured auth mode (none, reverse-proxy headers, or OIDC). Required for project administration, key management, and run review actions.

Rule of thumb. If a request comes from your code, use an API key. If it represents a person clicking in the dashboard (creating projects, managing members, approving runs), it needs a session.

Authenticating with an API key

API keys are verified by the require_api_key_principal dependency. The client sends the token in the standard HTTP Authorization header:

curl https://qym.example.com/v1/runs \
  -H "Authorization: Bearer <your-token>" \
  -H "Content-Type: application/json" \
  -d '{"task_name": "qa-eval", "model": "gpt-4o-mini"}'

The header is parsed strictly. The scheme must be the word bearer (case-insensitive), followed by a single space and the token. Anything else is treated as no credential.

How verification works

  1. The token is split on the first space; the scheme must be bearer or the request is rejected.
  2. The first 8 characters of the token form a non-secret prefix used to look up the key row in the database.
  3. A row is only considered if its revoked_at is null (revoked keys never match).
  4. The full token is verified against the stored hash with a constant-time comparison.
  5. The owning user must still exist and be active.

On success the request runs as a Principal carrying the key's user, auth_type="api_key", the recorded scopes, and the project_id the key is bound to.

Authentication errors

These are the exact responses the API-key path returns. Match on the status code; the detail strings are stable but human-facing.

StatusdetailCause
401Missing Bearer API keyNo Authorization header, or it is not a well-formed Bearer <token>.
401Invalid API keyNo active key matches the prefix, or the token fails hash verification (wrong, revoked, or mistyped token).
403User disabledThe key verified, but its owning user is missing or deactivated.

A revoked key reads as Invalid API key. Revocation does not produce a distinct error — the lookup simply skips revoked rows, so the token looks invalid. If a previously working key suddenly returns 401, check whether it was revoked before assuming it was typed wrong.

API keys are project-scoped

Every API key belongs to exactly one project, fixed at creation time. The key's project_id rides along on the authenticated Principal, and ingestion endpoints use it directly: a run created with a key is filed under that key's project, and reading another project's run with the wrong key is denied.

There is no global or cross-project API key. To send runs to two projects, create one key per project.

Per-key scopes are stored but not enforced. Keys record a scope list (e.g. runs:write, datasets:read) for forward compatibility, but the platform's scope check is intentionally a no-op today. Any valid, non-revoked key has full access to its project. Do not rely on scopes as an access-control boundary — use separate projects to isolate access.

Creating and managing API keys

Key management lives under each project and requires a browser session (these endpoints use require_ui_principal, not a Bearer key). You create keys in the dashboard for a project you can access; the snippets below show the underlying HTTP calls.

Create a key

POST /v1/projects/{project_id}/api-keys

{
  "name": "ci-pipeline",
  "scopes": ["runs:write", "runs:read", "datasets:read", "datasets:write", "datasets:delete"]
}

Both fields are optional. name defaults to "default"; scopes defaults to the full set shown above (and, as noted, is recorded but not enforced). The response is the only time the raw token is returned:

{
  "id": "...",
  "prefix": "AbCdEfGh",
  "token": "AbCdEfGh...the-full-token..."
}

The token is shown once. Only a one-way hash is stored — the platform cannot show or recover the token again. Copy it immediately into your secret store. If you lose it, revoke the key and create a new one.

List keys

GET /v1/projects/{project_id}/api-keys returns metadata only — never the token. Each entry includes id, name, prefix, project_id, the creator, the stored scopes, created_at, and revoked_at (null while active). Use the prefix to recognize which key is which.

Revoke a key

DELETE /v1/projects/{project_id}/api-keys/{key_id} sets revoked_at on the key. Revocation takes effect immediately on the next request. Who may revoke:

  • A platform admin, or
  • The creator of the key, or
  • A manager of the key's project.

Anyone else gets 403 Access denied. Revoking an already-revoked key returns 400 API key already revoked.

When a key stops working

A key acts for its creator inside its project, so every request also checks that the creator can still use the project:

  • Removing the creator from the project revokes their keys for it. A key whose creator is no longer a member (and not an admin) returns 403 API key owner is no longer a member of this project.
  • While the project is archived, its keys return 409. They work again once an admin unarchives the project.
  • Disabling the creator's account returns 403 User disabled.

Token format and storage

PropertyValue
Generationsecrets.token_urlsafe(32) (URL-safe base64 of 32 random bytes, ~43 characters)
PrefixFirst 8 characters of the token. Stored in the clear for lookup and display; not secret.
FormatNo qym_ prefix or any other marker — it is an opaque random string.
At restHashed with PBKDF2-HMAC-SHA256 (600,000 iterations, random 16-byte salt). The raw token is never stored.
HeaderAuthorization: Bearer <token>

Do not try to fingerprint keys by shape. Because tokens carry no fixed prefix, you cannot detect a leaked qym key by pattern-matching alone. Treat the whole string as a secret, keep it out of logs and source control, and identify keys by their 8-character prefix instead.

Using a key from the SDK and CLI

The SDK and CLI read the key and the platform URL from environment variables — you rarely pass the token in code. Set both, and runs stream to the platform automatically.

# .env or your shell
QYM_BASE_URL=https://qym.example.com
QYM_API_KEY=AbCdEfGh...the-full-token...
VariablePurposeDefault
QYM_BASE_URLPlatform base URL the client talks to. A trailing slash is stripped.http://localhost:8000
QYM_API_KEYThe Bearer token created above.(none)

Verify connectivity and credentials before a real run:

qym config check

No key needed for local CSV runs. Streaming to the platform is optional. You can run an evaluation entirely offline and results still save to qym_results/ — see Results, artifacts & tracing. The API key only matters once you want runs to appear in the dashboard.

Self-signed or internal CA certificates

If your deployment serves HTTPS with an internal or self-signed certificate, point SDK streaming and CLI HTTP calls at your CA bundle so TLS verification succeeds:

QYM_PLATFORM_CA_BUNDLE=/path/to/internal-ca.pem

The client falls back to QYM_CA_BUNDLE if QYM_PLATFORM_CA_BUNDLE is unset. As a last resort for local troubleshooting only, disable verification with QYM_PLATFORM_SSL_VERIFY=false (it falls back to QYM_SSL_VERIFY). Never disable verification in production. The current QymDataset download path uses Python's default trust store instead, so private CAs must also be installed there.

Browser session authentication (deployment auth modes)

Dashboard requests are authenticated by the require_ui_principal dependency, whose behavior is set by the deployment's auth_mode setting. This is chosen by whoever operates the platform, not by API callers.

auth_modeBehavior
noneLocal/dev: no identity required. Every request runs as a stable dev@local admin user. The default.
proxy_headersA trusted reverse proxy injects the user's identity via X-User-Email (or X-Email). With auto_provision_users on (the default), an unknown but proxy-asserted email is created on first sight.
oidcNative Google, GitHub, and/or self-hosted GitLab sign-in when their client credentials are configured. Unauthenticated dashboard requests get 401 Not authenticated. Generic OIDC, SAML, and other SSO providers are not implemented.

Set QYM_AUTH_LOCAL_ENABLED=true to add email/password signup and login alongside proxy_headers or oidc. Any session-enabled configuration requires QYM_AUTH_SESSION_SECRET. Session cookies are HTTPS-only outside dev, test, and local environments, and browser state-changing requests must pass the platform's same-origin check.

Sessions are also recorded on the server, and a cookie authenticates only while its session exists. Signing out ends the session on the server, so a copy of the cookie stops working too; changing or resetting a password, or disabling a user, ends all of that user's sessions; every sign-in starts a new session. A session ends after 14 days without activity. Dashboard pages and API responses are sent with Cache-Control: no-store, so the browser does not show them again from its cache after sign-out.

Self-hosted GitLab sign-in needs QYM_AUTH_GITLAB_URL (the GitLab issuer, for example https://gitlab.example.com), QYM_AUTH_GITLAB_CLIENT_ID, and QYM_AUTH_GITLAB_CLIENT_SECRET. Create a confidential GitLab OAuth application with the scopes openid, email, and profile and the redirect URI <QYM_BASE_URL>/v1/auth/callback/gitlab. A malformed QYM_AUTH_GITLAB_URL stops the platform at startup.

Provider sign-in links accounts by verified email. A first provider sign-in joins the existing account with the same verified email. For GitLab, this trusts the instance's email verification: enable it only when users cannot set an unconfirmed email (email confirmation on, or emails managed by LDAP or admins). Otherwise a GitLab user could claim another person's account, including an admin's.

Forgotten passwords. With email/password sign-in on, an admin opens Admin → Users → Edit and chooses Reset Password (POST /v1/admin/users/{user_id}/reset-password). The response shows a temporary password once. The user signs in with it and must choose a new password (POST /v1/auth/password/change) before a session is created. A temporary password works once; a later reset replaces it. A reset also signs the user out of every browser, whatever they signed in with.

First-admin bootstrap depends on the auth path:

  • Proxy headers: when no user exists, send X-Admin-Bootstrap: <QYM_ADMIN_BOOTSTRAP_TOKEN> with X-User-Email.
  • OIDC or local password: sign in first, then call POST /v1/auth/bootstrap-admin with {"bootstrap_token": "..."}. It promotes the current user only while no active admin exists.

An API key cannot stand in for a session. Endpoints that manage projects, members, API keys, or run review require require_ui_principal — a Bearer key will not satisfy them. Conversely, run ingestion requires an API key and will not accept a session. Choose the credential that matches the endpoint.

Security checklist

  • Store the token in a secret manager. It is shown once and only its hash is kept server-side.
  • Use one key per environment. A separate key for CI, local, and prod makes targeted revocation possible.
  • Rotate by create-then-revoke. Create the replacement, deploy it, then revoke the old key — revocation is immediate.
  • Isolate access with projects, not scopes. Scopes are not enforced; project boundaries are the real control.
  • Keep tokens out of URLs and logs. Always send them in the Authorization header; identify keys by their prefix.
  • Verify TLS. Configure QYM_PLATFORM_CA_BUNDLE for internal CAs rather than disabling verification.
