Developer / API

Run ingestion

Push evaluation runs into the platform over HTTP — either by streaming live events as work happens, or by uploading a finished results file. This is the wire protocol the Python SDK uses internally, documented here for non-Python clients and custom harnesses.

If your evaluation runs in an environment where the qym SDK can execute, prefer the SDK: it already handles run creation, retries, heartbeats, final status, OpenTelemetry spans, and local artifacts. Reach for this HTTP API when you are evaluating from a language the SDK does not cover, or when you have results produced by another tool that you want to land in the platform for review and comparison.

Every endpoint on this page lives under the /v1 prefix and requires a project-scoped API key. Set up a key first — see Link your repo & create API keys.

Two ingestion paths

There are two ways to get a run into the platform, and which one you use depends only on whether the run is live or already finished.

PathEndpointsUse when
Stream events POST /v1/runs then POST /v1/runs/{run_id}/events You want a live run in the platform while work executes — incremental items, metric scores, traces, and heartbeats. This is what the SDK uses.
Upload artifact POST /v1/runs:upload The run already finished elsewhere or ran offline, and you have a saved .csv or .json results file to ingest after the fact.

Authentication

All ingestion requests authenticate with a project-scoped API key passed as a bearer token:

Authorization: Bearer <token>

The token is the raw secret returned once when you create a key. It has no qym_ prefix — it is a ~43-character URL-safe string. The platform looks up the key by its 8-character prefix and verifies the full token against a stored hash, then binds the request to exactly one project.

SituationHTTP statusDetail message
No Authorization: Bearer header401Missing Bearer API key
Unknown or revoked token401Invalid API key
The key's user is disabled403User disabled
Key not bound to a project403API key is not bound to a project

Keys are always project-bound. A run created with a key always writes into that key's project. Per-key "scopes" are stored but not enforced — treat any valid key as full access to its one project. See API keys for the full key lifecycle.

Step 1 — Create the run

Start by creating the run record. This returns the run_id you address all subsequent events to, and a live_url for the run in the dashboard.

POST /v1/runs
Authorization: Bearer <token>
Content-Type: application/json

Request body (CreateRunRequest). Only task and dataset are required; everything else is optional.

FieldTypeRequiredNotes
taskstringYesName of the task being evaluated.
datasetstringYesDataset name or label shown for the run.
external_run_idstringNoYour own stable identifier for the run (e.g. a CI build id).
modelstringNoModel identifier under evaluation.
metricsstring[]NoMetric names recorded for the run. Defaults to [].
metric_specsobjectNoMetric name to immutable score schema. Set score_type to boolean, percentage, count, or number so the platform validates and formats values without inference. Set direction to maximize or minimize for colors, Pass/Fail, winners and verdicts (omit it and the metric is shown neutrally; send "schema_version": 2, because a schema 1 maximize on a legacy metric is read as the old SDK default), and "primary": true on the one metric views should open on.
dataset_idstringNoLink the run to a platform dataset by id.
dataset_version_idstringNoPin to a specific dataset version. Takes precedence over dataset_alias.
dataset_aliasstringNoResolve a dataset version by alias. Defaults to production when a dataset is found but no version is pinned.
run_metadataobjectNoArbitrary JSON metadata for the run. Defaults to {}.
run_configobjectNoConfig snapshot. For repeat runs, set samples=k; optional report_k controls the reported subset estimator. Defaults to {}.
 
{
  "external_run_id": "qa-smoke-001",
  "task": "qa_task",
  "dataset": "qa.csv",
  "model": "gpt-4o-mini",
  "metrics": ["exact_match"],
  "run_metadata": {"team": "search"},
  "run_config": {"max_concurrency": 10, "samples": 3, "report_k": 2}
}

The response includes the run id, dashboard URL, and protocol capability flags:

{
  "run_id": "2c2a0c9d-1c66-4e7f-9c03-2f04c9d1a0a3",
  "live_url": "https://qym.example.com/projects/search-team/runs/2c2a0c9d-1c66-4e7f-9c03-2f04c9d1a0a3",
  "supports_pass_events": true,
  "supports_metric_specs": true
}

supports_pass_events tells a client it may send pass-aware fields and pass_completed. supports_metric_specs confirms the typed metric schema is accepted. Check these flags when a custom client may talk to an older platform.

The run is created immediately in RUNNING status. The shape of live_url depends on the project:

  • When the project has a slug: {base_url}/projects/{slug}/runs/{run_id}
  • Otherwise: {base_url}/run/{run_id}

Here base_url is the platform's configured public URL (server setting, default http://localhost:8000; a trailing slash is stripped). If you passed dataset_id or dataset_alias and a matching platform dataset exists, the run is linked to the resolved dataset version at this point.

Step 2 — Stream events as NDJSON

Once you have a run_id, post events to it. The body is newline-delimited JSON (NDJSON): one complete JSON object per line. It is not a JSON array — do not wrap the lines in [ ].

POST /v1/runs/{run_id}/events
Authorization: Bearer <token>
Content-Type: application/x-ndjson

Each line is a complete event envelope. You can send one event per request or batch many lines into a single request — the platform processes them in order, line by line.

{"schema_version":1,"event_id":"5d8f7d2e-7a9f-4e3a-8b15-0b4f9c2b4c0e","sequence":1,"sent_at":"2026-06-21T12:00:00Z","type":"run_started","run_id":"2c2a0c9d-1c66-4e7f-9c03-2f04c9d1a0a3","payload":{"task":"qa_task","dataset":"qa.csv","model":"gpt-4o-mini","metrics":["exact_match"],"started_at":"2026-06-21T12:00:00Z"}}

Response: applied, skipped and rejected

Each line gets its own verdict. One bad line never fails the rest of its batch: the response says what happened to every line.

{"ok": true, "applied": 198, "skipped": 1, "rejected": 1,
 "rejected_events": [{"line": 7, "event_id": "5d8f7d2e-…", "sequence": 7,
                      "type": "item_completed", "error": "latency_ms: Field required"}]}
FieldMeaning
appliedEvents that were stored and had their side-effects applied (new or updated items, scores, spans, status changes).
skippedEvents whose (run_id, event_id) was already seen — deduplicated, no double-apply.
rejectedLines that were not stored and never will be: invalid JSON or envelope, a run_id that does not match the URL, a payload that fails its type schema or the run's metric spec, a new event_id that reuses a stored sequence, or a value the database refuses (text longer than its column, a NUL character).
rejected_eventsThe first 100 rejected lines: 1-based line, event_id, sequence, type and the error.

A request in which every line is rejected returns 422 with the same body plus "ok": false and a detail. Batch-level problems keep their own status codes (below).

Do not resend rejected lines unchanged. They are refused again. Retry only network errors, 408, 429 and 5xx; a 422 means every line was refused. Rejected events do not hold the run's completion: send run_completed as usual (the SDK reports its count in summary.rejected_events). The run completes and is flagged in run_metadata.ingest_incomplete, which the run page and the runs list show as Incomplete.

The event envelope

Every event — regardless of type — is a JSON object with the same seven top-level fields, validated by the RunEventV1 model. Type-specific data goes in payload.

FieldTypeRule
schema_versionintegerMust be 1.
event_idUUID stringGlobally unique. This is the idempotency key.
sequenceinteger≥ 1, strictly increasing per run.
sent_atRFC 3339 timestampClient send time. Informational; used to advance the run's last-event clock.
typestring enumOne of the 12 event types below.
run_idUUID stringMust match the {run_id} in the URL, or the line is rejected (listed in rejected_events).
payloadobjectType-specific. Schema is selected by type.

These are the platform wire events. Do not confuse them with the local SDK progress events (run_start, item_start, metric_result, item_complete, run_complete) surfaced to in-process observers. Those never leave the SDK; the events on this page are the HTTP protocol. See Progress & observers for the local vocabulary.

Event types

There are 12 event types. A typical streamed run uses a subset — run_started, per-item lifecycle events, metric_scored, optional pass_completed, and run_completed. The rest cover retries, traces, heartbeats, and mid-flight metadata.

TypeWhen to emitKey payload fields
run_startedOnce, at run start.task, dataset, metrics, started_at; optional metric_specs, model, external_run_id, total_items, run_metadata, run_config, dataset_id/dataset_version_id/dataset_alias.
item_startedWhen processing of a dataset item begins.item_id, index (≥ 0), input; optional pass_number (default 1), expected, item_metadata, dataset_item_pk.
item_attempt_startedAt the start of each attempt (for retried items).item_id, attempt_number (≥ 1); optional pass_number (default 1), index, trace_id, trace_url, task_started_at_ms.
item_attempt_finishedAt the end of each attempt.item_id, attempt_number, status (completed or failed); optional pass_number (default 1), successful output, latency_ms, error, trace_id/trace_url, is_last_attempt.
metric_scoredOnce per metric per item and pass.item_id, metric_name; optional pass_number (default 1), score_numeric, typed score_value, score_raw, meta, label, explanation. Repeat runs persist label, metadata, and explanation per pass.
item_completedWhen an item execution finishes successfully.item_id, output, latency_ms; optional pass_number (default 1), is_final_pass (default true), index, item_metadata, task_metadata, trace_id/trace_url, task_started_at_ms, retry_count.
item_failedWhen one item execution fails terminally.item_id, error; optional pass_number (default 1), index, latency_ms, trace_id/trace_url, task_started_at_ms, retry_count.
pass_completedAfter every item in one repeat pass has reached a terminal state.pass_number, total samples, and optional aggregate metrics. This is the durability barrier for live pass status.
run_completedOnce, at the very end.ended_at, final_status (COMPLETED / FAILED / STOPPED); optional summary.
run_heartbeatPeriodically during long runs.heartbeat_at.
metadata_updateTo merge metadata mid-flight.extra (merged into run metadata); plus optional langfuse_url, langfuse_dataset_id, langfuse_run_id.
span_completedPer OpenTelemetry span, for native trace viewing.trace_id, span_id, name; optional parent_span_id, kind, duration_ms, status, attributes, events, links, timing fields.

Recommended event order

A minimal, correct stream for a single successful item looks like this:

run_started
item_started
item_attempt_started     (optional — only if you model attempts/retries)
item_attempt_finished    (optional)
metric_scored            (one per metric)
item_completed
pass_completed           (repeat runs: once after each complete pass)
run_completed

For an item that fails, emit item_failed in place of item_completed. For long-running work, interleave run_heartbeat events. Emit span_completed events whenever a trace span closes if you want native trace data in the dashboard.

Repeat-run protocol

A repeat evaluation is one run with run_config.samples=k, not k independent runs. Process passes sequentially. Put the same 1-based pass_number on every item, attempt, score, and completion event in that pass, then emit one pass_completed barrier. Set is_final_pass=true only on the final pass's successful item completions.

The platform keeps each pass's final attempt, output, numeric score, label, metadata, error, and judge explanation. The ordinary item score remains a running mean across observed passes for backward-compatible summaries; GET /api/runs/{run_id}/passes and /group-metrics expose the lossless pass view and repeat estimators.

run_started            run_config.samples = 3
  pass 1 item/score events (pass_number = 1)
pass_completed         pass_number = 1, samples = 3
  pass 2 item/score events (pass_number = 2)
pass_completed         pass_number = 2, samples = 3
  pass 3 item/score events (pass_number = 3, is_final_pass = true)
pass_completed         pass_number = 3, samples = 3
run_completed

Resilient ingestion

The platform is forgiving about missing lifecycle events so a dropped or out-of-order event does not corrupt the run:

  • If item_completed or item_failed arrives for an item that never had an item_started, the item is created from the completion event (using its index if provided, else 0).
  • item_completed clears any prior error on the item; item_failed records the error string.
  • Any of the item or metric events will mark the run RUNNING again if it was prematurely marked terminal.
  • When the task returned an output envelope {"output": ..., "metadata": ...}, send the envelope's metadata as task_metadata; the platform nests it under item_metadata.task_metadata.

Idempotency & ordering

The protocol is designed so a client can retry safely after a network error without duplicating data.

Idempotency

  • Generate a fresh event_id (UUID) for every distinct event.
  • On retry of the same event after a failure, reuse the same event_id — the platform deduplicates on (run_id, event_id) and counts the repeat as skipped.
  • Re-sending an event with a new event_id would create a duplicate; never reuse an event_id for a different event.

Ordering

  • sequence must increase per run, starting at 1. Do not reset it mid-run.
  • The platform applies events line by line in the order received and is tolerant of minor reordering for live UI; the deduplication key, not sequence, is what prevents double-application.

Heartbeats & long runs

For runs that take a while between item updates, emit run_heartbeat so the platform can tell an active-but-quiet run apart from an abandoned one:

{"schema_version":1,"event_id":"...","sequence":42,"sent_at":"2026-06-21T12:01:00Z","type":"run_heartbeat","run_id":"2c2a0c9d-1c66-4e7f-9c03-2f04c9d1a0a3","payload":{"heartbeat_at":"2026-06-21T12:01:00Z"}}

A heartbeat keeps the run in RUNNING and advances its last-event clock. When a live run is later read after QYM_RUN_STALE_TIMEOUT_SECONDS without an event, the platform lazily marks it STOPPED with reason lease_timeout. A later valid event marks it RUNNING again.

Finalizing the run

Always send exactly one run_completed to close the run. Its final_status maps directly to a stored run status:

final_statusStored statusMeaning
COMPLETEDCOMPLETEDThe run finished normally.
FAILEDFAILEDThe run ended in failure.
STOPPEDSTOPPEDThe run was deliberately stopped.

Any final_status value outside this set is stored as FAILED. On a successful finalize, the platform also computes and persists trace statistics from any span_completed events received for the run. You can attach last-minute run metadata by putting a run_metadata object inside the summary payload — it is merged into the run's metadata.

No finalize means an abandoned run. If you never send run_completed, the run remains live until a read detects the expired lease and marks it STOPPED. Always finalize, even on failure paths — send run_completed with FAILED.

Uploading a finished run

If a run already completed elsewhere, skip the streaming protocol and upload its saved results file. This creates a run in COMPLETED status and ingests every item and score in one request.

POST /v1/runs:upload
Authorization: Bearer <token>
Content-Type: multipart/form-data

Send the file plus a few form fields:

Form fieldRequiredNotes
fileYesThe results file. Must be .csv or .json.
taskYesTask name for the run.
datasetYesDataset name for the run.
modelNoModel identifier.
external_run_idNoYour stable run identifier.

Only .csv and .json are accepted. The file type is decided by the filename extension. Any other extension — including .xlsx — is rejected with 400 Unsupported file type (use .csv or .json). An empty file is rejected with 400 Empty upload. To upload spreadsheet results, export them to CSV or JSON first.

JSON upload shape

A JSON upload mirrors the SDK's saved-results structure: top-level metrics, dataset_name, and parallel maps keyed by item id.

{
  "dataset_name": "qa.csv",
  "metrics": ["exact_match"],
  "inputs": {"row_000001": "What is X?"},
  "metadatas": {"row_000001": {"difficulty": "easy"}},
  "results": {
    "row_000001": {
      "output": "X is ...",
      "expected": "X is ...",
      "time": 0.412,
      "trace_id": null,
      "scores": {"exact_match": 1.0}
    }
  },
  "errors": {}
}
  • Each results entry becomes a successful item. time is seconds and is stored as latency_ms (multiplied by 1000).
  • A score may be a scalar (stored as the numeric score) or an object with score and optional metadata.
  • Each errors entry becomes a failed item; its error string is recorded.

CSV upload shape

A CSV upload is the same artifact the SDK writes to qym_results/. The platform infers metrics from column names and reconstructs items row by row.

  • Metric columns are named <metric>_score; the metric list is derived from those headers (ignoring __meta__ columns).
  • Per-metric metadata columns are <metric>__meta__<key>. A __meta__json column is parsed as a JSON object and merged.
  • An output cell beginning with ERROR: marks the row as a failed item; the text after ERROR: becomes the error, and that metric's score defaults to 0.0. A score cell of N/A or empty is treated as no numeric score.
  • Run-level columns on the first row are honored: run_name (used as external_run_id if not supplied), dataset_name, and JSON-encoded run_metadata / run_config.
  • Stable item ids come from the item_id column; positional-looking ids are replaced with a content fingerprint so re-uploads line up across runs.

Both upload formats return the same shape as a streamed run create:

{"run_id": "...", "live_url": "https://qym.example.com/run/..."}
