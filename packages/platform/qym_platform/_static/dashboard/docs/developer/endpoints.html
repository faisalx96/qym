Developer / API

Endpoint reference

A grouped, verb-prefixed reference for the qym platform HTTP API: read run data, manage datasets and their versions, provision projects and keys, run the review workflow, trigger analysis, and drive product evals. Every path, method, query parameter, and error string on this page is copied from the platform source.

Prefer the SDK and CLI first. This page covers the raw HTTP surface for cases where the CLI and SDK do not give enough control. For ingesting runs (creating a run, streaming events, uploading an artifact) see Authentication for keys and the ingestion guide for the wire contract. The schema of every endpoint is also served live at /openapi.json with a Swagger UI at /api-docs.

Conventions

The platform exposes two path families, and the split is not "ingestion vs review":

  • /v1/... carries ingestion, datasets, projects, project API keys, members, product evals, and the run review actions (submit / approve / reject).
  • /api/... carries the dashboard read JSON (run lists, run detail, compare, spans), analysis, and corrections.

Authentication differs by family. Ingestion, datasets, and product-eval endpoints accept a project-scoped API key as Authorization: Bearer <token>. Almost everything else (run review, analysis, corrections, project/member/key management, the read JSON) is resolved by a logged-in UI session (the require_ui_principal dependency) and is not callable with a Bearer key alone. Where an endpoint accepts either, it is called out below.

The placeholder host on this page is https://qym.example.com. Substitute your deployment's QYM_BASE_URL.

API-key "scopes" are stored but not enforced. A project key is created with a full scope set, but the platform's scope check is a no-op for these endpoints: any valid, unrevoked key has full access to its bound project. Do not treat scopes as access control. Cross-project access is the real boundary — a key is permanently bound to one project.

Read API: runs, items & comparison

These are the dashboard-facing read endpoints under /api. They require a UI session and enforce per-run visibility (can_view_run). There is no GET /v1/runs public read endpoint — run reads go through /api/runs (or the dataset-scoped listing under /v1/datasets, below).

Datasets

Dataset endpoints live under /v1/datasets and accept either a project API key (Bearer) or a UI session — the dataset_principal dependency tries the Bearer key first, then falls back to session auth. A Bearer key pins the project automatically; with a session you select the project via the project_slug query param (or the first accessible project is used).

Versions & aliases

A dataset is a container of immutable, published versions. The platform assigns a stable sequential identifier such as v3; version_name is optional display text and does not replace that identifier. A version ref resolves by vN or alias; the special ref production falls back to the latest published version when no explicit production alias exists. New versions are DRAFT; only drafts can have items edited, and aliases can only point at PUBLISHED versions.

POST /v1/datasets/{dataset_ref}/versionsCreate a draft version. Optionally derive from another via from_version or from_alias (copies items). The next free vN identifier is assigned unless an available explicit vN is requested; free text becomes the display name.
GET /v1/datasets/{dataset_ref}/versions/{version_ref}Get one version's metadata (status, item count, content hash, aliases, run count).
PATCH /v1/datasets/{dataset_ref}/versions/{version_ref}Update display name and description. The assigned vN identifier is immutable.
POST /v1/datasets/{dataset_ref}/versions/{version_ref}:publishPublish a draft. Rejects an empty version with 400 Cannot publish an empty dataset version and duplicate item ids with 409 Duplicate item_id: <id>. Optional body set_alias points an alias at it on publish. Audited (dataset.version_published).
POST /v1/datasets/{dataset_ref}/aliases/{alias_name}Point an alias at a published version. Body: version. Returns 409 Aliases can only point to published versions otherwise. Moving production (here, on publish, or with an upload's set_alias) needs a project manager, except the dataset's creator setting its first production alias; otherwise 403. Every move is audited with the old and new version (dataset.alias_moved).
GET /v1/datasets/{dataset_ref}/lineageVersions (each with change_counts: added / modified / deleted / unchanged against its parent; stored once a version and its parent are published) plus the change log (created / published / alias_set / uploaded events) oldest first, each with created_at and the actor who made it.
GET /v1/datasets/{dataset_ref}/versions/{version_ref}:compareDiff two versions. Required query base; optional include_diffs=1 to include full before/after item payloads. Summary counts added / removed / changed / unchanged. Every list is ordered by when the change happened (oldest first); changed entries and item payloads carry changed_at and changed_at_source (revision, or version when only the head version's creation time is known). With include_diffs=1&limit=N (1–500) the bodies of one list (kind: changed default, added, removed, unchanged) are returned a page at a time from offset, with a page object (total, next_offset). A paged response carries summary, page and that page's rows only (field_diffs, added_items, removed_items or unchanged_items); the full added / removed / changed / unchanged lists and timestamps are left out. Without limit everything is returned as before.
GET /v1/datasets/{dataset_ref}/runsRuns that used this dataset, with per-run eval_score, version_label, and items_count. Query version, limit (default 50, 1–500), offset.

Upload & download

Method & pathPurpose
POST /v1/datasets:uploadCreate a dataset, or add a version to one, from an uploaded file (multipart). Send format (csv, jsonl, or json); without it, .jsonl files are JSONL, .json files are a JSON array (or JSONL when not an array), and everything else is CSV. See the form fields below.
GET /v1/datasets/{dataset_ref}/versions/{version_ref}:downloadDownload a version as JSONL (application/x-ndjson), one object per line with item_id / input / expected_output / metadata / labels.

Upload form fields (all Form values): name (required), file (required), project_slug, optional version / version_name, description, tags, labels, publish (default false), set_alias, format, encoding (CSV only: utf-8, utf-16, windows-1256, windows-1252, iso-8859-6), create_only, and dataset_ref. When version is empty, the next vN is assigned. Which dataset receives the file: with dataset_ref (id, slug, or name) the file becomes a new version of exactly that dataset; with create_only=true a new dataset is always created and an existing name returns 409; otherwise (the SDK default) the upload appends to the dataset with the same name or slug, or creates it. A different name that only shares the slug returns 409, so unrelated datasets are never merged. CSV column mapping uses either the single-column input_col (default input) / expected_col (default expected_output), or the multi-column input_cols / expected_cols (comma-separated; an empty expected_cols genuinely means "no expected output"), plus id_col, metadata_cols, and label_cols. A missing referenced column returns 400 Missing column: <col>; CSV with no input column returns 400 At least one input column is required.

CSV compatibility. Uploads auto-detect comma, semicolon, tab, or pipe delimiters and accept UTF-8 and UTF-16. Files that are not UTF-8 are read as Windows-1256 (Arabic Excel exports), Windows-1252, or ISO-8859-6, whichever produces readable text; pass encoding to choose explicitly. Saving as "CSV UTF-8" avoids guessing. A cell whose first non-whitespace character is { or [ becomes structured data when it contains valid JSON; otherwise its original text is preserved. JSON and JSONL are strict and UTF-8: every record must be a JSON object, and invalid records are all reported with their line or item number instead of being skipped.

# Upload a CSV and publish it as v1, pointing the production alias at it
curl -s -X POST "https://qym.example.com/v1/datasets:upload" \
  -H "Authorization: Bearer $QYM_API_KEY" \
  -F "name=Support QA" \
  -F "version=v1" \
  -F "publish=true" \
  -F "set_alias=production" \
  -F "input_col=question" \
  -F "expected_col=answer" \
  -F "file=@qa.csv"

Projects, members & API keys

Project, member, and key management endpoints are under /v1/projects and require a UI session (require_ui_principal) — they are not callable with a Bearer key. Member mutations require manager/admin rights. Any project member can list or create project keys; revocation is limited to the key owner, a project manager, or an admin.

Admin project operations

Under /v1/admin, admin only (403 Admin only).

  • POST /v1/admin/projects — create a project as admin.
  • PATCH /v1/admin/projects/{project_id} — rename / re-slug / toggle is_active.
  • POST /v1/admin/projects/{project_id}/archive and POST /v1/admin/projects/{project_id}/unarchive — hide or restore a project (is_active). Archiving never deletes anything. While archived, the project is read-only: its API keys return 409, admins and its members still read it (by id, and by slug: runs list, dashboard, datasets, settings, category catalog), and every change (review actions, score edits, deletes and restores, analysis, datasets, settings, new API keys) returns 409 “Project is archived; unarchive it to make changes” with the header X-Qym-Project-State: archived. A non-member still gets 404 Project not found for its slug. Revoking a key and removing a member stay possible. Trash purging of its deleted runs pauses until the unarchive.
  • GET /v1/admin/projects/{project_id}/unarchive-preview — the API keys an unarchive turns back on: not revoked, owner active and still a member (or an admin). Returns active_api_key_count and the newest ten in active_api_keys (id, name, prefix, creator, created_at).
  • GET /v1/admin/projects/{project_id}/archive-preview — runs still in progress (running_count and the newest few in running_runs), which lose their remaining results if the project is archived now.
  • GET /v1/admin/projects/{project_id}/deletion — what a delete would remove (counts), plus archived, can_delete and blocked_reason.
  • DELETE /v1/admin/projects/{project_id}?confirm=<name or slug> — permanently delete a project with its datasets, API keys, members, LLM connections and analysis settings. Requires confirm (400 without it). Runs are never deleted with a project: one that still has runs, including runs in Trash, returns 409.
  • GET /v1/admin/users, POST /v1/admin/users, PUT /v1/admin/users/{user_id}, and DELETE /v1/admin/users/{user_id} — user administration.
  • POST /v1/admin/users/{user_id}/reset-password — issue a one-time temporary password (400 when email/password sign-in is off). The user must choose a new password at the next sign-in. Creates a password login for provider-only users. Signs the user out of every browser, whatever they signed in with. Audited as user.password_reset; the password itself is never stored or logged.

Organization-tree and mutable platform-settings APIs are not part of the current surface.

Run review workflow

Review actions are under /v1/runs/{run_id}/... and require a UI session — they cannot be driven with a Bearer key. The workflow advances a run's status through the states described in Run status values below. Each action locks the run and checks its state inside the lock: acting on a state that has already changed returns 409 with the current status in the detail and the X-Qym-Run-Status header. Every transition is appended to the run's review history and written to the audit log; a withdrawn decision stays on record.

Method & pathPurpose & guard
POST /v1/runs/{run_id}/submitThe owner, a project manager or an admin submits a run for review; a manager or admin submitting someone else's run is recorded as on behalf of the owner (on_behalf_of in the review history). Body: optional comment. Allowed only from COMPLETED, FAILED, or REJECTED, else 409. Anyone else → 403. Moves status to SUBMITTED.
POST /v1/runs/submitBulk submit. Body: run_ids (up to 500) and optional comment. One transaction: each run is checked under its lock with the single-run rules, and the first run that fails refuses the whole request (its name in the detail) with nothing submitted.
POST /v1/runs/{run_id}/ownerTransfer a run to another active project member. Body: user_id. Project managers and admins only. Audited as run.owner_transferred.
POST /v1/runs/{run_id}/approveManager/admin approves a SUBMITTED run. Body: optional comment. Wrong state → 409; insufficient rights → 403 Only a project manager or admin can approve. Moves to APPROVED.
POST /v1/runs/{run_id}/rejectManager/admin rejects a SUBMITTED run. Body: optional comment. Moves to REJECTED.
POST /v1/runs/{run_id}/unapproveWithdraw the approval of an APPROVED run. The run returns to its execution outcome (COMPLETED or FAILED). Body: optional comment, kept in the history. Wrong state → 409.
POST /v1/runs/{run_id}/unrejectWithdraw the rejection of a REJECTED run. The run returns to its execution outcome. Body: optional comment. Wrong state → 409.
GET /api/runs/{run_id}/review-historyThe run's review timeline, oldest first: action, from_status, to_status, actor, on_behalf_of, comment, at. Reviews from before history was kept are reconstructed from the approval record (recorded: false).

Run mutation endpoints (also UI session) live under /api/runs:

  • POST /api/runs/update_metric — override one metric score on one item. Requires file_path (the run id), row_index, metric_name, new_score; else 400 file_path, row_index, and metric_name required. Send reset: true instead of new_score to give the score back its original value (409 when it was never edited). The score's metadata records the last edit (last_edit: who, when, from, to) and each edit or reset writes a run.score_edited / run.score_reset audit row. A SUBMITTED or APPROVED run refuses both with 403.
  • DELETE /api/runs/{run_id}/passes/{pass_number} and DELETE /api/runs/{run_id}/passes — delete passes of a repeat run. The run owner, a project manager or an admin only (the run-deletion rule); a SUBMITTED or APPROVED run answers 409.
  • POST /api/runs/update_root_cause — set canonical root_cause_issues records with category, subcategory, and finding. The legacy root_cause, root_causes, root_cause_detail, and root_cause_note fields remain supported, as do solution and solution_note. Requires item_id and run_id. Pass optional metric_name to patch that metric's analysis while preserving the item-level summary.
  • POST /api/runs/delete — soft-delete a run (file_path = run id). The response's purge_after_days is how long an admin can restore it before retention permanently removes it (0 = never).
  • POST /api/runs/restore — restore a soft-deleted run ({"run_id"}), or up to 200 at once ({"run_ids": [...]}, one transaction; runs no longer in Trash or of an archived project come back in skipped with the reason). Admin only.

Run status values

The workflow status enum (RunWorkflowStatus) is exactly:

StatusMeaning
DRAFTCreated but not yet started.
PENDINGQueued / live, awaiting first events (treated as a live status).
RUNNINGActively ingesting events (a live status).
COMPLETEDFinished successfully.
FAILEDFinished with failure.
STOPPEDStopped (e.g. a product eval stop request).
SUBMITTEDSubmitted for review. While a run is SUBMITTED, APPROVED or REJECTED its data is frozen: ingest rejects new data with 409.
APPROVEDReview approved.
REJECTEDReview rejected.

RUNNING and PENDING are the two "live" statuses; GET /api/runs/live filters on exactly these. An invalid value in the status filter on GET /api/runs returns 400 Invalid run status: <value>.

Analysis & corrections

The analysis and correction-bank endpoints are under /api and require a UI session. Analysis uses a project LLM connection plus the project's description, reference documents, and active rule version to diagnose failures by metric; approved corrections can provide evidence when generating project analysis rules, but are not copied into each item's prompt as few-shot examples.

GET /api/correctionsList corrections with filters: project_slug, task, dataset, model, run_name, source, conf_min/conf_max (0–100), status, search, sort (newest default, oldest, confidence = lowest AI confidence first), limit (1–500, default 50) and cursor. Returns one page of summary rows (no revision history; input_preview/expected_preview/output_preview text in place of the snapshots), total, has_more, next_cursor (pass it as cursor for the next page), status stats and facet_counts.
GET /api/corrections/{correction_id}One correction with its full input/expected/output snapshots and revision history.
PUT /api/corrections/{correction_id}Edit a correction.
POST /api/corrections/{correction_id}/approveApprove for rule-generation evidence. Body: optional comment. The project's review rules apply (below). Only a pending correction can be approved (409 otherwise).
POST /api/corrections/{correction_id}/rejectReject. Body: optional comment. Review rules apply. Only a pending correction can be rejected (409 otherwise).
POST /api/corrections/{correction_id}/resetReset to pending. Review rules apply. Only an approved or rejected correction can be reset (409 otherwise).
POST /api/corrections/bulkBulk approve/reject/reset/delete across corrections. Body: ids, action, optional comment, expected_count and expected_status. Every correction is checked against the review rules first; one refusal refuses the whole request. With expected_count the call returns 409 unless exactly that many of the ids are still active; with expected_status (for example pending) it returns 409 if any of them has since left that status. Approve and reject need every selected correction to be pending, reset needs each to be approved or rejected; otherwise the call returns 409 naming how many do not fit. Statuses are checked after the rows are locked, so a decision another reviewer made meanwhile is never overwritten.
DELETE /api/corrections/{correction_id}Remove the active candidate, mark it rejected, and retain its append-only history. Its author may always delete it; anyone else needs the right to decide it.

Review rules are project settings, read on every project payload and set with PATCH /v1/projects/{project_id}/review-rules (managers and admins; body correction_approvers: members or managers, and correction_require_different_reviewer: boolean; audited as project.review_rules_updated). With managers, approve, reject and reset (single, bulk, and the run page's metric-analysis and issue approvals) answer 403 to other members. With a different reviewer required, the author of a correction (the person whose labels differ from the AI's) gets 403. Each correction in GET /api/corrections carries review_block (why the caller may not decide it, or null), the project's review_rules, and self_reviewed (its author decided it). Editing an approved correction creates a pending revision that is reviewed again.

Corrections live only under /api/corrections. There is no /v1 equivalent. These are review tooling, not part of the ingestion contract.

Product evals

The product-eval API is under /v1/product-evals and is the one place that requires a Bearer API key bound to a project (require_api_key_principal); a key not bound to a project returns 403 API key is not bound to a project. It launches preset, server-side evaluations of a product (the default preset is insightor) and returns a unified envelope {"ok", "data", "error"}.

Method & pathPurpose
POST /v1/product-evalsSubmit an asynchronous product eval. Returns 202 with eval_id and job state. Body: preset (default insightor), dataset, run_name, task_name, model, run_count (1–100), runtime inputs (insightor_url, refresh_token, agent_version, image_version, kb_version), and metadata. A config field is rejected with 400; any other unknown field → 400 Unsupported field(s): ...; no worker capacity → 429 queue_full with Retry-After: 30.
GET /v1/product-evals/{identifier}Fetch status by eval_id (prefixed eval_) or aggregate data by physical qym run id. Optional include_items=true applies only to a physical run id. Unknown id → 404 not_found.
POST /v1/product-evals/{identifier}/stopStop by eval_id or run id. Returns the job/run payload with stopped_qym_runs.
GET /v1/product-evals/jobs/{job_id}Compatibility polling from process-local job state; unavailable after restart.
POST /v1/product-evals/jobs/{job_id}/stopCompatibility stop against process-local job state.

run_count=k means one physical qym run with samples=k, not k dashboard runs. The response's runs[] field is a legacy attempt-shaped compatibility view and can include placeholder rows; use top-level status for completion and collect distinct non-null run ids/URLs. New evaluations normally have one physical run and a null qym_compare_url. A completed sampled eval may include compact group_analysis; the run's Samples analysis is the durable, detailed pass view. There is no synchronous submit-and-wait route.

# Submit a product eval and read its id
curl -s -X POST "https://qym.example.com/v1/product-evals" \
  -H "Authorization: Bearer $QYM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"preset": "insightor", "run_name": "nightly", "dataset": "support-qa"}'

# Poll its status (eval id is prefixed eval_)
curl -s "https://qym.example.com/v1/product-evals/eval_abc123?include_items=true" \
  -H "Authorization: Bearer $QYM_API_KEY"

Errors at a glance

Status codes used across these endpoints (exact detail strings vary per endpoint, examples in the tables above):

CodeWhen
400Bad input: missing required field, invalid status filter, empty dataset publish, unsupported product-eval field, missing CSV column.
401Missing or invalid Bearer key on a key-authenticated endpoint (Invalid API key, Missing Bearer API key).
403Authenticated but not allowed: cross-project key, non-owner submit, non-manager member/key mutation, admin-only endpoint, disabled user.
404Resource not found (run, dataset, version, item, project, member, correction, key, eval).
409Conflict: duplicate slug or item id, editing a non-draft version, aliasing a non-published version.
429Product-eval queue full (with a Retry-After header).
