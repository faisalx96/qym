SDK GUIDE

Metrics (deep dive)

A metric is the function that turns one task output into a score. qym accepts plain numbers, booleans, dicts, or a structured MetricResult — and it ships seven code metrics out of the box. This page is the reference for what a metric may return, how qym normalizes and aggregates those returns, and the exact behavior of every built-in.

For writing your own scoring functions, see Custom metrics. For LLM-graded scoring, see LLM-as-judge & pairwise judging. For where these tunables live, see Configs & options.

Declare custom metric score types with Metric(...). Explicit types prevent a raw 0.4 from being mistaken for 40%, and let item views render boolean observations as True or False. Built-in metrics already carry their specifications.

Typed metrics

Wrap a custom callable with Metric directly in the evaluator. This is the recommended API because the score semantics stay visible at the call site:

from qym import Evaluator, Metric

evaluator = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=[
        Metric(is_correct, score_type="boolean", direction="maximize"),
        Metric(similarity, score_type="percentage", direction="maximize", pass_threshold=0.8),
        Metric(empty_output, score_type="boolean", direction="minimize"),
        Metric(token_count, score_type="count", direction="minimize", unit="tokens"),
        Metric(raw_measurement, score_type="number"),
    ],
    primary_metric="similarity",
)

Direction and the primary metric

direction tells the platform which way is better. With "maximize" a higher score is better; with "minimize" (error rates, empty outputs, latency, cost) a lower one is, and a boolean passes when it is False. The platform uses it for score colors, Pass/Fail, the best value and winners in Compare, the Sweep verdict, and the Models ranking. A metric that declares no direction (the default, and every plain callable) is shown neutrally: its values and distributions, without good/bad colors, Pass/Fail, winners or an improved/regressed verdict. Built-in metrics declare theirs.

Direction also decides how errors enter the run mean. A task error, or a metric error, counts as 0 in the mean of a higher-is-better metric and of a metric without a direction. For a lower-is-better metric 0 is the best score, so its errors are left out of its mean instead: the runs list, run page and Compare show how many were left out next to the mean, and every errored item or pass counts as a fail in Pass/Fail, Pass@k and the Sweep. In a repeat run each item is then the mean over its passes without an error.

primary_metric names the run's headline metric (--primary-metric on the CLI). Compare, Sweep, the Models page and the run page open on it; without it they open on the first metric in the order you listed them.

from qym import Metric, MetricSpec

quality_spec = MetricSpec(score_type="percentage", pass_threshold=0.8)
quality = Metric(quality_score, name="quality", spec=quality_spec)

For repeat runs, each boolean pass remains True or False. The reduced item value is a rate, so two true passes out of four display as 50%. This distinction is intentional.

The metric contract

A metric is any Python callable that qym invokes once per task output. Its return value is normalized into a single internal model, MetricResult, before it is recorded. You never have to construct that model yourself — qym wraps whatever you return via MetricResult.from_raw.

Built-in metrics are referenced by string name (metrics=['exact_match']); custom metrics are passed as callables (metrics=[my_metric]) or registered by name. Both go through the same return-value normalization.

Return types

The table below is the exact normalization performed by MetricResult.from_raw (in qym/metrics/result.py). Anything not listed becomes score=0.0 with the raw value stored under metadata.raw.

You returnRecorded scoreNotes
bool1.0 if True, else 0.0Cleanest shape for pass/fail checks.
int / floatfloat(value)Used as the numeric score directly.
dict with a score keyfloat(score)A non-numeric/missing score falls back to 0.0. label, explanation, and metadata are carried through.
dict with an error key0.0Recorded as a metric error: metadata.status = "error" and the message under metadata.error. It counts as 0 in the run mean, or is left out of it for a lower-is-better metric (see Direction above). A reason for a low score belongs in metadata.reason instead.
MetricResultits scorePass-through; the richest shape.
anything else0.0Raw value preserved in metadata.raw. This is the silent-failure case for a metric that returns a string.

Returning a string is a footgun. A metric that returns "pass" does not error — it is silently recorded as 0.0 with the string tucked into metadata.raw. Return a bool, a number, or a dict with a numeric score.

Dict return shape

The dict form is the most common return for code metrics, because it carries diagnostics alongside the score:

def citation_score(output, expected=None):
    has_citation = "[" in str(output) and "]" in str(output)
    return {
        "score": 1.0 if has_citation else 0.0,
        "label": "cited" if has_citation else "uncited",
        "explanation": "Square-bracket citation required.",
        "metadata": {"rule": "square-bracket-citation"},
    }

Only score drives aggregation; label, explanation, and metadata are stored and surfaced in artifacts and the platform item view.

MetricResult

MetricResult is the structured model qym wraps everything into. You can return one directly when you want full control over its fields. Verified fields and defaults from qym/metrics/result.py:

from qym.metrics.result import MetricResult
import json

def json_validity(output, expected=None):
    try:
        json.loads(str(output))
        return MetricResult(
            score=1.0,
            label="valid",
            explanation="Output is valid JSON.",
            metadata={"parser": "json.loads"},
        )
    except Exception as exc:
        return MetricResult(
            score=0.0,
            label="invalid",
            explanation=str(exc),
            metadata={"parser": "json.loads"},
        )

Errored metrics are excluded from aggregation

This is the most important and least obvious behavior. A metric return that contains an error key — whether you returned it deliberately, or qym caught an exception — is recorded as score=0.0 but is not counted in the metric's mean. It is counted as an error instead.

Verified in qym/core/results.py (get_metric_stats): a score dict with an error key increments an errors counter and is skipped; the reported success_rate is then:

success_rate = len(scores) / (len(scores) + errors)

The practical consequences:

  • A metric that raises is caught by qym and recorded as {"score": 0, "error": <traceback>} — so it drops out of the mean but pulls down success_rate.
  • A metric that returns a normal low score (e.g. 0.0 for a failed check) does count toward the mean. This is the difference between "the model scored badly" and "the metric itself failed."
  • If you want a bad output to lower the average, return 0.0; if you want it to register as an infrastructure failure, surface an error key.

Score low output, do not raise. For ordinary "bad answer" cases, return 0.0 — not an exception. Reserve exceptions/error keys for genuine metric failures (a dependency is down, parsing the wrong shape) that you want to triage separately from model quality.

The task-output envelope and what metrics receive

A task may return a plain value (the visible output) or qym's envelope: a dict with exactly the keys output and metadata. Any other dict shape raises InvalidTaskOutputError before metrics run (verified in qym/core/evaluator.py, _normalize_task_output):

Task returned a dict. Dict task outputs must use qym's envelope
{"output": <visible output>, "metadata": <dict>} (missing keys: ...; unexpected keys: ...).

The metadata field must itself be a dict, or you get: Task output envelope field 'metadata' must be a dict.

Crucially, qym passes the full envelope to metrics as their output argument — it does not unwrap it for you. The seven built-ins unwrap it internally (via a private _visible_output helper that detects a dict whose keys are exactly {output, metadata} and returns the inner output). Custom metrics get the whole envelope, which is the entire point: hidden task details (retrieved context, tool traces) ride along in output["metadata"].

def rag_task(question):
    docs = retrieve(question)
    answer = generate_answer(question, docs)
    return {"output": answer, "metadata": {"retrieved_context": docs}}

def grounded_in_context(output, expected=None):
    answer = output["output"]                         # visible output
    docs = output["metadata"]["retrieved_context"]    # hidden task detail
    return 1.0 if all(t in docs for t in key_terms(answer)) else 0.0

Argument resolution

qym inspects your metric's signature and supplies arguments by these recognized names (verified in _resolve_metric_arguments): output, expected, input_data, metadata, item_metadata. Both metadata and item_metadata resolve to the dataset row's metadata (they are the same value).

  • If every parameter name is in that recognized set (or your function takes **kwargs), qym calls it with keyword arguments — order does not matter.
  • If a parameter falls outside that set, qym falls back to positional call order: output, expected, input_data, item_metadata (truncated to your parameter count). In that case, the position of each parameter is load-bearing.

The safe, order-independent signature is therefore one whose names all come from the recognized set:

def my_metric(output, expected=None, input_data=None, item_metadata=None):
    ...

Sync vs async metrics

qym runs synchronous metrics in a thread pool automatically, so a blocking call inside a sync metric does not stall the event loop. An async metric is awaited directly on the loop.

Do not put blocking work in an async metric. qym probes async metrics and emits a warning if one blocks the event loop: Async metric '...' appears to block the event loop ... Fix: remove 'async' from your metric function so qym runs it in a thread pool automatically. Use async only when the metric genuinely awaits an async dependency; otherwise keep it sync.

Timeouts and metric concurrency

Two config fields govern how metrics execute. Verified defaults from qym/core/config.py:

FieldDefaultEffect
metric_timeout60.0 (seconds)Wall-clock cap per metric attempt. Set to None to disable the cap and timeout retries.
metric_max_retries2Retries after a timeout (three total attempts by default). After the final timeout qym records {"score": 0, "error": "metric timeout after 60.0s (3 attempts)"}.
max_metric_concurrency1How many metrics run concurrently per item. Default 1 evaluates an item's metrics serially. Raise it when metrics are independent and slow (e.g. multiple LLM judges).

A timed-out metric records an error key after its retries are exhausted, so per the rule above it is excluded from the metric mean and lowers metric success_rate. It has no special timeout label. Raise the budget for legitimately slow checks, or lower the retry count when fast failure matters more.

from qym import Evaluator
from qym.core.config import EvaluatorConfig

config = EvaluatorConfig(
    metric_timeout=180.0,
    metric_max_retries=1,
    max_metric_concurrency=4,
)
Evaluator(task=my_task, dataset=ds, metrics=["correctness"], config=config).run()

Built-in metric catalog

Exactly seven metrics ship without any extras. These are registered in qym/metrics/__init__.py as builtin_metrics; the names below are the registry keys you pass as strings.

The registry name is contains, not contains_expected. The underlying function is named contains_expected, but it is registered under the key contains. Use metrics=['contains']. Likewise, the built-in faithfulness is a code token-overlap heuristic — the LLM-graded version is the separate judge faithfulness_llm (requires openai when called).

exact_match

Strips both sides, compares as strings. Returns {"score": 0.0, "metadata": {}} when either output or expected is None. Best for IDs, codes, yes/no, single-token answers.

exact_match("Paris", " Paris ")   # -> {"score": 1.0, "metadata": {}}

contains

Returns 1.0 when str(expected).lower() is a substring of str(output).lower(), else 0.0; 0.0 if either is None. Good for "the answer must mention X" checks — but note it is order-insensitive and substring-based, so it can match spuriously inside a longer word.

fuzzy_match

Returns the difflib.SequenceMatcher ratio (character-sequence similarity, not Levenshtein distance, not semantic similarity).

The threshold argument is inert. fuzzy_match accepts threshold=0.8 but the source documents it as "not used in score" — it always returns the raw ratio, never a thresholded pass/fail. To get pass/fail behavior, wrap it in a custom metric and compare the ratio yourself.

response_time and token_count

Both are placeholders. response_time always returns 1.0 regardless of input — actual timing is recorded by the evaluator, not this metric. token_count returns a crude estimate (len(words) * 1.3 as an int), not a real tokenizer count. Treat both as scaffolding, not measurement.

correctness

SQuAD-style F1 over normalized tokens. Normalization lowercases, removes the articles a/an/the, strips punctuation, and collapses whitespace; F1 is computed bag-of-words (so duplicate tokens are handled via Counter intersection). Returns a dict with score plus metadata (prediction_tokens, ground_truth_tokens). This is the right deterministic choice for QA-style answers where partial token overlap should count.

faithfulness (code heuristic)

Measures what proportion of meaningful output tokens appear in the source context. It reads context from input_data — either input_data["context"] or, if absent, input_data["input"]["context"]. It lowercases everything, drops a built-in stopword list and single-character tokens, then scores grounded_tokens / total_tokens.

It scores 0.0 without comparing tokens when:

  • the output is empty — {"score": 0.0, "metadata": {"reason": "Empty output"}} (a scored zero)
  • no context is found — {"score": 0.0, "error": "No context found in input_data"} (a metric error: the metric cannot judge without context)

This is a dependency-free heuristic, not a model-graded check. For semantic faithfulness, use the faithfulness_llm judge.

Inspecting the registry at runtime

list_available_metrics() prints every registered metric, including the built-in judge names. An unknown name raises a ValueError whose list is the sorted union of custom and built-in names:

Metric 'X' not found. Available metrics: conciseness, contains, correctness, correctness_llm, exact_match, faithfulness, faithfulness_llm, fuzzy_match, hallucination, relevance, response_time, token_count, tool_calling, toxicity

Judge metrics require the openai client at runtime

Seven LLM-graded metrics — relevance, faithfulness_llm, correctness_llm, conciseness, hallucination, toxicity, tool_calling — are always registered. Install their optional runtime client with pip install openai; without it, calling a judge raises ImportError.

Judges need configuration: QYM_JUDGE_MODEL and an API key (QYM_JUDGE_API_KEY, falling back to OPENAI_API_KEY). There is no default model — JudgeConfig.validate() raises a RuntimeError listing the missing variables. Full setup, the built-in judge inputs, and create_judge / create_pairwise_judge live on the dedicated page: LLM-as-judge & pairwise judging.

Built-in vs. recipe

qym's older Metric Bank documents many useful metric ideas — semantic similarity, PII detection, schema compliance, BLEU, tool accuracy, and so on. Those are recipes you write yourself, not built-ins. The seven code metrics and seven registered judges resolve as strings out of the box. Everything else is a custom metric — see Custom metrics for the signature rules, registration, and testing.

Where scores land

Per-metric statistics (mean, std, min, max, success_rate) come from EvaluationResult.get_metric_stats(name). In saved artifacts, each metric contributes a numeric <metric>_score column, with any metadata flattened into <metric>__meta__<key> columns. For the full artifact layout and column naming, see Results, artifacts & tracing.
