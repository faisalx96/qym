SDK GUIDE

LLM-as-judge & pairwise judging

When a deterministic rule cannot capture quality — relevance, faithfulness, tone, "is this actually correct?" — hand the decision to an LLM. qym ships seven prebuilt judges and two factories (single-output and pairwise) that turn a prompt and a set of labels into a scored, explainable metric.

A judge is just a metric. It plugs into the same metrics=[...] list as exact_match and your custom callables, returns a MetricResult, and writes a numeric score plus a human-readable label and explanation to every item. The difference is that the score comes from an LLM verdict instead of code, which makes judges more expensive, non-deterministic, and dependent on an external provider. Reach for them only where rules genuinely fall short — and keep deterministic metrics in the same run as cheap, stable guardrails.

Install the optional client. Judge names are always registered, but execution imports the openai package lazily. Run pip install openai; there is no qym[judges] extra.

Configure the judge provider

Every judge call talks to an OpenAI-compatible chat-completions endpoint (OpenAI, vLLM, Ollama, OpenRouter, and similar). Configuration is read from environment variables — there is no default model, so you must supply one.

export QYM_JUDGE_MODEL=gpt-4o-mini          # required — no default
export QYM_JUDGE_API_KEY=sk-...             # required (falls back to OPENAI_API_KEY)
export QYM_JUDGE_BASE_URL=https://api.openai.com/v1   # optional (falls back to OPENAI_BASE_URL)
VariableRequiredFallbackMeaning
QYM_JUDGE_MODELYes—Model name, e.g. gpt-4o-mini or llama-3.1-8b.
QYM_JUDGE_API_KEYYesOPENAI_API_KEYAPI key for the provider.
QYM_JUDGE_BASE_URLNoOPENAI_BASE_URLBase URL — set this for vLLM, Ollama, etc.

The judge provider is separate from your platform credentials. QYM_JUDGE_* points at the LLM that does the scoring. It has nothing to do with QYM_BASE_URL/QYM_API_KEY, which connect the SDK to the qym platform. Set both when you stream judge runs to the platform.

Configuring in Python instead of env vars

Set a global default that every judge in the process uses:

from qym.metrics import JudgeConfig, set_default_judge_config

set_default_judge_config(
    JudgeConfig(
        model="gpt-4o-mini",
        api_key="sk-...",
        base_url="https://api.openai.com/v1",  # optional
    )
)

JudgeConfig is a dataclass. Any field you leave unset is back-filled from the environment in __post_init__ (model from QYM_JUDGE_MODEL; base URL from QYM_JUDGE_BASE_URL then OPENAI_BASE_URL; key from QYM_JUDGE_API_KEY then OPENAI_API_KEY). Its verified fields and defaults:

FieldDefaultNotes
model""Empty string → resolved from env. Must be non-empty or validate() raises.
base_urlNoneResolved from env; None uses the provider's default URL.
api_keyNoneResolved from env. Required.
temperature0.0Judges run greedy by default for repeatability.
max_tokens1024Cap on the verdict-plus-explanation response.
timeout60.0Per-attempt wall-clock cap (seconds) on each LLM call.

Missing config fails at call time, not at construction. JudgeConfig.validate() runs on the first judge call. If the model or key is absent it raises RuntimeError with: LLM judge metrics require configuration. Missing: ... followed by the exact env-var exports to set. Smoke-test on one item before scaling so you hit this immediately, not 500 items in.

The seven built-in judges

Each is a registry name you can drop straight into metrics=[...]. The required input fields column lists the keys your dataset's input dict must carry — they are substituted into the judge's prompt by name. The labels → scores column is the fixed verdict mapping each judge uses.

NameEvaluatesRequired input fieldsLabels → scores
relevanceDoes the response address the question?questionrelevant=1.0, irrelevant=0.0
faithfulness_llmIs the response grounded in the context?context, questionfaithful=1.0, unfaithful=0.0
correctness_llmDoes the response match the expected answer?question (uses expected)correct=1.0, incorrect=0.0
concisenessIs the response concise vs. padded?questionconcise=1.0, verbose=0.0
hallucinationDoes it stay grounded vs. invent facts?contextgrounded=1.0, hallucinated=0.0
toxicityIs the response free of harmful content?(none)non-toxic=1.0, toxic=0.0
tool_callingAre the tool calls correct for the question?question, tool_definitions, tool_callscorrect=1.0, incorrect=0.0
 
from qym import Evaluator

evaluator = Evaluator(
    task=my_task,
    dataset="my-dataset",
    metrics=["exact_match", "relevance", "faithfulness_llm"],
)
results = evaluator.run()

tool_calling reads the tool calls from your dataset input, not from the task output. Its prompt template fills {question}, {tool_definitions}, and {tool_calls} — all from the item's input dict. It does not reference the task's {output}. Put the model's actual tool calls into input["tool_calls"] (alongside question and tool_definitions) for this judge to score anything meaningful.

Don't confuse faithfulness with faithfulness_llm. faithfulness is a dependency-free code metric (token overlap with the context). faithfulness_llm is the LLM judge described here. Both are registered. See Metrics for the code version.

Custom single-output judges with create_judge

When none of the seven fit, write your own. create_judge returns an async metric function you pass into metrics=[...] exactly like a built-in name.

from qym.metrics.judges import create_judge

# Binary judge
helpfulness = create_judge(
    name="helpfulness",
    prompt="Is this response helpful?\n[Question]: {question}\n[Response]: {output}",
    choices={"helpful": 1.0, "unhelpful": 0.0},
)

# Graded (multi-level) judge — choices can have any number of labels
answer_quality = create_judge(
    name="answer_quality",
    prompt="""\
Rate the quality of this response.
- excellent: fully correct, well structured, comprehensive
- good: mostly correct with minor gaps
- poor: partially correct, missing key information
- bad: incorrect or off-topic

[Question]: {question}
[Response]: {output}""",
    choices={"excellent": 1.0, "good": 0.7, "poor": 0.3, "bad": 0.0},
)

evaluator = Evaluator(
    task=my_task,
    dataset="my-dataset",
    metrics=["exact_match", helpfulness, answer_quality],
)

Per-judge provider override

Run one judge on a cheaper local model while others use a hosted one:

toxicity_local = create_judge(
    name="toxicity_local",
    prompt="Is this response toxic or non-toxic?\n[Response]: {output}",
    choices={"non-toxic": 1.0, "toxic": 0.0},
    judge_model="llama-3.1-8b",
    judge_base_url="http://localhost:11434/v1",
    judge_api_key="ollama",
)

Prompt template substitution

The prompt is filled with simple {key} replacement. Three variables are always available, plus every key of input_data when it is a dict:

PlaceholderFilled from
{output}The task's output (stringified).
{expected}The item's expected output (stringified), or empty string.
{input}The whole input value (stringified), or empty string.
{<any key>}Each key of input_data when it is a dict — e.g. {question}, {context}. The three built-in names above win if a key collides with them.

Missing prompt fields raise before the LLM call. If a prompt references {context} but the metric input has no context, qym raises JudgeInputError. The colored terminal message names the judge, shows expected and received fields, suggests input_mapping, and links to Multiple input columns. This validation applies to built-in, custom, and pairwise judges.

Without input_mapping, a single-column CSV keeps its scalar metric input_data, while its declared column name is exposed separately to judge placeholders. Thus input_col="question" satisfies {question} without changing {input}. If the source column has another name, use input_mapping={"source_column": "question"}; metric input_data then becomes a dict under question, and both source and mapped names remain valid placeholders. Dataset types that provide an unnamed scalar cannot satisfy a named placeholder unless an explicit one-entry mapping supplies the name.

{output} stringifies the whole envelope for envelope-returning tasks. If your task returns the {'output': ..., 'metadata': {...}} envelope, judges receive that entire dict as output, so {output} renders the full dict — metadata and all — not just the answer. Either return a bare string from the task, or write a custom judge that reads output['output']. See Custom metrics for the envelope contract.

Pairwise judging with create_pairwise_judge

Instead of scoring one output on an absolute scale, a pairwise judge compares two outputs (A vs. B) and picks a winner. LLMs are more reliable at relative comparison than absolute scoring, which makes pairwise judging a strong fit for A/B model comparisons and regression gates against a baseline.

from qym.metrics.judges import create_pairwise_judge

compare_quality = create_pairwise_judge(
    name="compare_quality",
    prompt="""\
Compare these two responses to the same question.

[Question]: {question}
[Response A]: {output_a}
[Response B]: {output_b}

Which response is better? Consider accuracy, completeness, and clarity.
Answer A, B, or tie.""",
)

evaluator = Evaluator(
    task=my_task,
    dataset="my-dataset",
    metrics=[compare_quality],
)

Fixed verdict mapping

Pairwise choices are not configurable — they are always:

LabelScoreMeaning
A1.0The task's output (A) wins.
tie0.5No clear winner.
B0.0The comparison output (B) wins.

Where A and B come from

  • {output_a} is always your task's output (the thing being evaluated).
  • {output_b} is resolved in this order: input_data["output_b"] if present, otherwise the item's expected field.

So to compare against a gold answer, leave output_b out and rely on expected. To compare two models head-to-head, put the baseline model's response in an output_b column:

id,question,expected,output_b
1,"What is 2+2?","4","The answer is four."

Your task produces A; the dataset provides B; the judge compares them. The signature mirrors create_judge minus choices and langfuse_prompt:

create_pairwise_judge(
    name: str,
    prompt: str,
    *,
    system_prompt: Optional[str] = None,
    judge_model: Optional[str] = None,
    judge_base_url: Optional[str] = None,
    judge_api_key: Optional[str] = None,
) -> Callable  # async (output, expected=None, input_data=None) -> MetricResult

What a judge returns

Every judge resolves to a MetricResult. The LLM is asked for JSON like {"verdict": "good", "explanation": "..."}; qym maps the verdict through choices and fills these fields:

FieldExampleDescription
score0.7Numeric value mapped from the verdict via choices.
label"good"The verdict label the LLM chose.
explanation"Covers the main points but..."The LLM's stated reasoning.
kind"llm"Always "llm" for judges (code metrics use "code").
metadata{}Empty on success; carries an error key when the verdict could not be obtained (see below).

Labels and explanations are persisted per item, so the dashboard shows not just the score but why the judge decided that way.

How a verdict is extracted (and what failure looks like)

Judges are defensive about messy LLM output. The verdict-extraction path is, in order:

  1. JSON parse. Read verdict and explanation from the JSON response. Verdicts match against choices exactly, then case-insensitively.
  2. One stricter retry. If parsing fails, the judge re-asks once with an explicit "respond with ONLY a JSON object" nudge listing the allowed labels.
  3. Rail snapping. If that still fails, it scans the raw text for any label as a whole word (longest label first, case-insensitive) and uses the first match.
  4. Give up. If nothing matches, the result is score=0.0 with metadata={"error": "Could not parse LLM verdict", "raw_response": ...}.

Transport failures are also handled: each LLM call retries up to three times with exponential backoff and jitter, capped by the per-attempt timeout. If all attempts fail, the judge returns score=0.0 with metadata={"error": "..."} rather than crashing the run.

A failed judge call scores 0.0, not "no data". Because parse and transport failures both return score=0.0 with an error in metadata, a provider outage can quietly look like a wave of zeros. Inspect the per-item error metadata before treating a low judge mean as a real quality drop.

Cost, latency, and concurrency

Judges are network calls, so they dominate run time. Tuning levers:

  • Sample first. Validate prompts and config on a handful of items before a full run — it surfaces the RuntimeError config check and any unfilled {placeholders} immediately.
  • max_metric_concurrency (default 1) controls how many metrics run in parallel per item. Raise it to fan out multiple judge calls on the same item; keep it low when your provider's rate limits are strict.
  • metric_timeout (default 60.0s) is the wall-clock budget per judge attempt. Raise it (or set it to None) for slow models.
  • metric_max_retries (default 2) retries attempts that reach that wall-clock limit. Exhausted timeouts become ordinary metric errors and are excluded from the mean.
  • Tier your judges. Use a cheap model for smoke tests and a stronger one for release gates via per-judge judge_model overrides.
  • Record provenance. Store the judge model and prompt version in your run metadata so scores stay comparable across runs.

See Configs & options for where these live on EvaluatorConfig.
