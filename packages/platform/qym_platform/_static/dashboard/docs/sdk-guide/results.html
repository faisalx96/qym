SDK GUIDE

Results, artifacts & tracing

Every qym run produces a durable, inspectable record: an in-memory EvaluationResult you can analyze in code, local artifact files (CSV / JSON / XLSX) you can review or upload later, and optional OpenTelemetry spans that explain what happened inside each item. This page is the reference for all three.

The result is the durable fallback even when platform streaming is enabled — if the platform is unreachable, your run still completes and your artifacts are still written to disk. Treat the local files as the source of truth and the platform as a richer, optional view on top.

The EvaluationResult object

Both run() and arun() return an EvaluationResult for a single-model run. A multi-model run (model=[...]) returns a list of EvaluationResult — one per model. See Multi-model, multi-run & group analysis for that path.

from qym import Evaluator, CsvDataset

result = Evaluator(
    task=my_task,
    dataset=CsvDataset("qa.csv", input_col="question", expected_col="answer"),
    metrics=["exact_match"],
).run(show_tui=False)

print(result.run_name)        # e.g. "my_task-241120-1432"
print(result.total_items)     # successes + failures
print(result.success_rate)    # 0.0 - 1.0 (a fraction, not a percentage)
print(result.get_metric_stats("exact_match"))

Successes and failures live in different places. Successful items are in results; failed items are in errors. To iterate over everything, walk both — or read the artifact CSV, which writes failed items as rows too.

How metric aggregation handles errors

This is the SDK's local summary. The platform run mean differs: it counts a scorer error as 0, or leaves it out for a lower-is-better metric (see Metrics). Locally, get_metric_stats() only reads from successful items, and within those it applies a precise rule for how each score is counted:

  • A bool counts as 1.0 / 0.0.
  • A plain number counts as itself.
  • A dict with a numeric score contributes score.
  • A dict containing an error key is excluded from mean/std/min/max and instead lowers that metric's reported success_rate.

So in the local summary a metric failure does not pull the mean toward zero: it is left out of the average and surfaces as a reduced metric success rate. Timeouts follow the same rule after metric_max_retries is exhausted; they are stored as score 0 plus an error, not as a special timeout label or a real quality zero. See Configs & options.

The console prints nothing by default. run() calls print_summary(), but it is a no-op unless you opt in with QYM_SHOW_SUMMARY=1 (also accepts true/yes/on). If you want the summary unconditionally from code, call result.print_summary(force=True) or just print result.summary().

The to_dict() shape

to_dict() is the canonical serialization and exactly what JSON export writes. Its keys:

{
  "dataset_name": "qa",
  "run_name": "my_task-241120-1432",
  "start_time": "2024-11-20T14:32:01.123456",
  "end_time": "2024-11-20T14:32:09.654321",
  "duration": 8.53,
  "total_items": 20,
  "success_rate": 0.95,
  "metrics": ["exact_match"],
  "metric_stats": {
    "exact_match": { "mean": 0.8, "std": 0.41, "min": 0.0, "max": 1.0, "success_rate": 1.0 }
  },
  "langfuse_url": null,
  "inputs": { "item_0": "..." },
  "metadatas": { "item_0": { } },
  "results": { "item_0": { "output": "...", "expected": "...", "scores": { }, "time": 0.42, "trace_id": "..." } },
  "errors": { "item_7": { "error": "...", "trace_id": null, "task_started_at_ms": null, "time": 0.0 } }
}

langfuse_url is always null in current runs — it is a legacy field kept for backward compatibility and is not populated. Langfuse has been removed from the SDK runtime, so ignore it.

Saving artifacts

Use result.save(...) to write a file. The signature is:

result.save(format="json", filepath=None, output_dir=".")
ArgumentDefaultNotes
format"json"One of "json", "csv", "xlsx" (case-insensitive). Anything else raises ValueError.
filepathNoneExplicit output path. If omitted, qym derives a hierarchical path (see below).
output_dir"."Base directory used only when filepath is not given.
 
json_path = result.save("csv")                       # positional format
csv_path  = result.save(format="csv")                # keyword form — identical
xlsx_path = result.save(format="xlsx")
here_path = result.save("json", filepath="run.json") # exact path, no hierarchy

save() defaults to JSON, but auto-save defaults to CSV. An unqualified result.save() writes JSON. The auto_save path on run(), however, uses save_format="csv". Pass the format explicitly to avoid surprises. Note that xlsx requires openpyxl — without it, export raises ImportError: openpyxl is required for Excel export. Install it with: pip install openpyxl.

Auto-save and checkpoints

run() defaults to auto_save=True; arun() defaults to auto_save=False. The default save_format for both is "csv". With the default config, checkpoint_enabled=True means qym is already streaming each item to a CSV checkpoint as it runs — so when checkpointing is active, the run does not auto-save a second file at the end; the checkpoint is the artifact, and last_saved_path points at it. Read result.last_saved_path rather than guessing.

Where files land by default

When you do not pass filepath, qym builds a stable hierarchy under the base directory:

<output_dir>/<task>/<model>/<date>/<run-file>

The CLI and the EvaluatorConfig default the run-level output_dir to qym_results, so a typical layout is:

qym_results/my_task/gpt-4o-mini/2024-11-20/my_task-qa-gpt-4o-mini-241120-1432.csv
  • task comes from run_metadata["task_name"] (falls back to task).
  • model comes from run metadata/config (falls back to nomodel).
  • date is YYYY-MM-DD, derived from the run-name timestamp when present.
  • Each path component is sanitized for the filesystem.

Do not treat the derived path as a stable API. The filename encodes task/model/date and can change. For downstream automation, either pass an explicit filepath or read result.last_saved_path after saving.

Artifact formats

CSV

Flat, one row per item (successes and failures). Best for spreadsheet review and for uploading to the platform.

JSON

The full to_dict() structure — nested, lossless. Best when another program consumes results directly.

XLSX

Same logical columns as CSV, written via openpyxl. Best for business review in Excel-compatible tools.

CSV / XLSX columns

CSV and XLSX share the same column model. The base columns, in order:

ColumnMeaning
dataset_nameDataset name or file-backed label.
run_nameqym run name.
run_metadataJSON-encoded run metadata.
run_configJSON-encoded config snapshot (concurrency / timeout fields).
trace_idTrace ID for the item, when a trace was created.
item_idDataset item ID.
inputTask input.
item_metadataJSON-encoded item metadata (string).
outputTask output, or ERROR: ... for failed items.
expected_outputExpected/reference output (empty for failed items).
timeTask duration in seconds.
task_started_at_msEpoch milliseconds when the task began.

After the base columns come per-metric columns. For each metric, qym writes a score column plus one column per metadata key that any item produced:

<metric>_score
<metric>__meta__<key>

For example, a run with exact_match and an LLM judge named relevance (which returns a label and explanation) yields:

exact_match_score
relevance_score
relevance__meta__label
relevance__meta__explanation

The double-underscore __meta__ separator distinguishes metadata columns from the score column. Nested metadata dicts are flattened one level using a single underscore (e.g. a metric whose metadata is {"usage": {"tokens": 12}} becomes a key usage_tokens, surfaced as <metric>__meta__usage_tokens). Metadata columns are unioned across all items, so the header is stable even if some items omitted a key.

How scores are encoded in a cell

The value written to <metric>_score depends on what the metric returned for that item:

Metric returnCell value
bool / numberThe value itself.
dict with scoreThe numeric score.
dict with an error keyERROR: <message>.
(item failed entirely)N/A for every metric column.

Failed items in the artifact

Failed items are written as full rows so failure rate never disappears:

  • output starts with ERROR: followed by the message.
  • Every <metric>_score is N/A; metric metadata columns are blank.
  • trace_id, time, and task_started_at_ms are included when available.

JSON export

JSON preserves the structured object from to_dict(): dataset/run names, metric list and aggregate metric_stats, run metadata and config, plus per-item inputs, metadatas, results, and errors. Use JSON when a downstream program reads qym results directly; use CSV/XLSX for human review and platform upload.

Parsing artifacts downstream

When you read a qym CSV in another tool, apply these rules:

  • Parse run_metadata, run_config, and item_metadata as JSON when they look like JSON.
  • Treat any output beginning with ERROR: as a failed item.
  • Treat N/A metric scores as missing-due-to-failure, not as zero.
  • Split metric metadata columns on the __meta__ separator: text before it is the metric name, text after it is the metadata key.
MistakeImpactFix
Consuming only successful rowsFailure rate vanishes.Include rows whose output starts with ERROR:.
Ignoring metric metadataJudge labels/explanations are lost.Parse <metric>__meta__* columns.
Treating the artifact path as a stable APIBreaks when task/model/date change.Use the returned last_saved_path or an explicit filepath.
Storing secrets in metadataSecrets can land in artifacts.Keep run/item metadata non-sensitive.

Uploading a saved artifact later

A CSV (or JSON) written earlier can be ingested into the platform without re-running the task. Only .csv and .json files are accepted by the upload endpoint — .xlsx is rejected. See the Developer / API docs for the HTTP contract and the CLI for the convenience wrapper.

Tracing

Metrics tell you that something failed; traces help explain why. qym instruments each item with OpenTelemetry spans and can route that span data to two destinations: the qym platform (when streaming is enabled) and, optionally, a Phoenix collector.

OpenTelemetry instrumentation

otel_enabled defaults to True. When the OpenTelemetry SDK and supported OpenInference instrumentors are installed, qym wraps each item in a span tree (a root eval span, a task span, and a metrics span) and auto-captures spans for instrumented LLM/framework calls made inside the task.

Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=["exact_match"],
    config={"otel_enabled": True},  # default
).run()

Auto-instrumentation is best-effort and degrades quietly:

  • If otel_enabled=False, qym uses a no-op manager — no spans, no overhead.
  • If the OpenTelemetry SDK is not installed, qym also falls back to the no-op manager.
  • If the SDK is present but no instrumentors are found, tracing initializes but captures no LLM/framework spans (auto-instrumentation is inactive). The run still succeeds.

qym recognizes OpenInference instrumentors for OpenAI, Anthropic, LangChain, and LiteLLM among others; the instrumentors it actually registered are reported per run. Disable OTEL only when tracing overhead or a provider interaction is causing problems:

config={"otel_enabled": False}

Trace IDs on results

When a trace is created for an item, its trace_id appears on the per-item result (and in the trace_id CSV column, and on failed items' errors entries). This lets you correlate a row in the artifact with the trace stored on the platform.

Platform trace streaming

When platform streaming is enabled (a QYM_API_KEY is configured — see Link your repo & create API keys), qym emits a span_completed wire event for each finished span. The platform stores the span tree and exposes trace views from the run's items. Each span event carries:

FieldMeaning
trace_id / span_idHex IDs (32 / 16 chars).
parent_span_idParent span hex ID, or null for a root span.
nameSpan name.
kindSpan kind (e.g. INTERNAL, CLIENT).
start_time_ns / end_time_nsStart/end timestamps in nanoseconds.
duration_msComputed span duration in milliseconds.
statusSpan status code name (e.g. OK, ERROR, UNSET).
attributesSpan attributes (includes OpenInference fields and inputs/outputs).
events / linksSpan events (including per-metric score events) and any span links.

span_completed is one of qym's platform wire events. The local progress events your wrappers see (run_start, item_complete, etc.) are a separate vocabulary covered in Progress, observers & wrappers.

Phoenix export

You can also export spans to an Arize Phoenix collector, in parallel with platform streaming. Set an endpoint via config or environment; an endpoint alone is enough to enable export.

config={
    "phoenix_enabled": True,
    "phoenix_endpoint": "http://localhost:6006/v1/traces",
}

Equivalent environment variables (read at run start): PHOENIX_ENDPOINT (or PHOENIX_COLLECTOR_ENDPOINT) sets the endpoint, and PHOENIX_ENABLED=true is honored as a legacy flag. Export requires the OTLP HTTP exporter package; if it is missing, qym logs a warning and disables Phoenix export while the run continues.

Trace-friendly task code

For traces to be useful, keep the LLM/framework calls inside the task function so the instrumentor can wrap them under the active item span:

async def answer_question(question, context, model_name="gpt-4o-mini"):
    prompt = build_prompt(question, context)
    response = await llm_client.chat.completions.create(
        model=model_name,
        messages=[{"role": "user", "content": prompt}],
    )
    return response.choices[0].message.content

Avoid hiding all the real work behind an opaque subprocess or a remote job ID. If you must, attach the relevant trace/job IDs to your own logs so you can still correlate them.
