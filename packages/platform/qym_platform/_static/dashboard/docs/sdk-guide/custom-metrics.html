Custom metrics

When a built-in metric is too generic, write your own. A custom metric is just a Python callable that scores one task output — pass it to Evaluator directly, or register it once and reference it by name everywhere.

When to write a custom metric

Reach for a custom metric whenever scoring follows a deterministic rule you can express in code: JSON or schema validity, required citations, field-level equality, tool-call correctness, numeric tolerances, or any domain-specific check. They are fast, free, and reproducible — no model calls involved.

If scoring needs semantic judgement that no rule captures, use an LLM-as-judge metric instead. The two compose freely: most suites mix a few deterministic custom metrics with one or two judges.

The metric contract

A metric is any callable. qym inspects its signature and passes the values it recognizes. The full set of recognized parameter names is:

ParameterWhat qym passes
outputThe task's output for this item. For tasks that return the envelope {"output": ..., "metadata": ...}, custom metrics receive the whole envelope here (see Reading task metadata below).
expectedThe item's expected_output from the dataset (may be None).
input_dataThe item's input. Configured field-name mappings are applied; without input_mapping, the original value and shape are preserved.
task_metadataThe hidden metadata dict returned by the task-output envelope, or {}.
metadataThe dataset item's metadata dict (the row's metadata, not the task's).
item_metadataAn alias for the same dataset item metadata. Use whichever name reads better.
any dict input keyThe individual value from input_data. For mapped CSV inputs, both the original CSV name and mapped task-parameter name are recognized.

The simplest possible metric takes only output:

def has_answer(output, expected=None):
    return 1.0 if str(output).strip() else 0.0

result = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=[has_answer],
).run(show_tui=False)

The metric's name is taken from the function's __name__ (has_answer above), so it appears as has_answer_score in artifacts and on the platform.

Two callables with the same name collide. Metrics are keyed by __name__ in an internal dict, so passing two functions both named score (or two lambdas, which share the name <lambda>) means the second silently overwrites the first. Give each metric a distinct function name, or register it under an explicit name (below).

Parameter names are load-bearing

qym resolves arguments by name only when every parameter your function declares is one of the recognized names above, an individual key in a dict input, or you accept **kwargs. In that case order does not matter — def m(expected, output) works fine.

If your function declares a parameter outside that set (for example def valid_sql(output, expected, schema)), qym falls back to positional passing in this fixed order:

output, expected, input_data, item_metadata

So a third positional parameter receives input_data regardless of what you named it. The safest habit is to stick to the recognized names and give optional ones defaults:

def my_metric(output, expected=None, input_data=None, metadata=None):
    ...

For a multi-column CSV input, a metric may read the mapped dict through input_data or request one field directly. If input_mapping={"sql_context": "schema"} is set, input_data contains schema, while both sql_context and schema work as individual metric parameters:

def execution_accuracy(output, expected, schema=None):
    return run_sql_against_schema(output, expected, schema)

Return types

qym normalizes whatever you return into a structured score. The accepted shapes are:

You returnqym records
boolTrue → 1.0, False → 0.0.
int / floatUsed directly as the numeric score (coerced to float).
dict with a score keyNumeric score plus optional label, explanation, and metadata. A non-numeric score becomes 0.0.
dict with an error keyScore forced to 0.0 and the item is treated as a metric error — see the warning below.
MetricResultPassed through unchanged (richest option).
anything elseScore 0.0; the raw value is stashed in metadata under raw.

Returning a dict with metadata

A dict lets you attach evidence alongside the score. The metadata you return is saved to artifacts and shown in the platform's item detail, which makes failures debuggable later:

def citation_score(output, expected=None):
    has_citation = "[" in str(output) and "]" in str(output)
    return {
        "score": 1.0 if has_citation else 0.0,
        "metadata": {
            "has_citation": has_citation,
            "rule": "square-bracket citation required",
        },
    }

A top-level error key excludes the item from aggregation. A dict whose top level contains error (e.g. {"score": 0, "error": "..."}) is recorded as a metric error: it counts against the metric's success rate but is left out of the mean. If instead you want a genuine failing score that still pulls the average down, return a real 0.0 and put the reason in metadata — i.e. {"score": 0.0, "metadata": {"error": "..."}}. The nested form is a normal scored zero; only the top-level error key triggers exclusion.

MetricResult — the structured form

For full control, return a MetricResult. It carries a score plus a human-readable label and explanation, a kind and direction, and arbitrary metadata:

import json
from qym.metrics.result import MetricResult

def json_validity(output, expected=None):
    try:
        json.loads(output)
        return MetricResult(
            score=1.0,
            label="valid",
            explanation="Output parses as JSON.",
            metadata={"parser": "json.loads"},
        )
    except Exception as exc:
        return MetricResult(
            score=0.0,
            label="invalid",
            explanation=str(exc),
            metadata={"parser": "json.loads"},
        )

MetricResult fields:

FieldType / defaultMeaning
scorefloat (required)The numeric score.
labelstr / NoneShort categorical tag (e.g. "valid", "timeout").
explanationstr / NoneFree-text reason, surfaced in the UI.
kind"code" (default), "llm", or "human"How the score was produced.
direction"maximize" (default) or "minimize"Whether higher or lower is better.
metadatadict (default {})Arbitrary evidence saved with the score.

Reading task metadata from the envelope

A task can hand hidden context to its metrics by returning qym's task-output envelope instead of a bare value:

def rag_task(question):
    docs = retrieve(question)
    answer = generate_answer(question, docs)
    return {
        "output": answer,
        "metadata": {"retrieved_context": docs},
    }

Only the envelope's output field is the visible output written to artifacts and shown on the platform. But a custom metric receives the entire envelope as its output argument, so it can read the hidden context:

def grounded_in_context(output, expected=None):
    answer = output["output"]
    docs = output["metadata"]["retrieved_context"]
    return 1.0 if any(d in answer for d in docs) else 0.0

The envelope keys are exact. A dict task return must contain exactly output and metadata (where metadata is a dict). Any missing or extra key raises InvalidTaskOutputError for that item. To return a plain value, return it directly — do not wrap it in a dict. Built-in metrics auto-unwrap the envelope; only custom metrics see it whole.

A real example

Here is a deterministic metric that decides whether generated SQL is syntactically valid, using the third positional parameter to reach the row's schema via input_data. It returns a scored dict with diagnostic metadata and degrades gracefully when an optional dependency is missing:

def valid_sql(output, expected, input_data):
    """1.0 if the generated SQL parses, else 0.0."""
    if output is None or str(output).strip() == "":
        return {"score": 0.0, "metadata": {"is_valid": False, "error": "Empty output"}}

    sql = str(output).strip()
    try:
        import sqlglot
        sqlglot.parse(sql)
        return {"score": 1.0, "metadata": {"is_valid": True}}
    except ImportError:
        # Fallback heuristic when sqlglot isn't installed
        up = sql.upper()
        is_valid = "SELECT" in up and "FROM" in up
        return {
            "score": 1.0 if is_valid else 0.0,
            "metadata": {"is_valid": is_valid, "note": "sqlglot not installed"},
        }
    except Exception as exc:
        return {"score": 0.0, "metadata": {"is_valid": False, "error": str(exc)}}

Note the failure path returns a real 0.0 with the reason nested in metadata — those zeros stay in the aggregate, which is what you want for a "this output is wrong" signal.

Async metrics

Make a metric async only when it must await a genuinely async dependency. Synchronous metrics are already run in a thread pool, so they never block the event loop:

async def policy_check(output, expected=None):
    result = await policy_client.check(str(output))
    return {"score": 1.0 if result.allowed else 0.0, "metadata": result.details}

Don't make a blocking function async. An async metric that does CPU work or a blocking network call stalls the whole run. qym probes for this and warns: "Async metric '…' appears to block the event loop … Fix: remove 'async' from your metric function so qym runs it in a thread pool automatically." If you aren't awaiting something, leave the metric synchronous.

Guarding against hangs

Every metric attempt has a wall-clock budget set by metric_timeout (default 60.0 seconds; see Configs & options). A timeout retries up to metric_max_retries (default 2). If every attempt times out, qym records an ordinary error dict such as {"score": 0, "error": "metric timeout after 60.0s (3 attempts)"}; it is visible in item detail, excluded from the metric mean, and lowers metric success rate. Raise the timeout for legitimately slow checks, lower retries for faster failure, or set metric_timeout=None to disable both. Metrics run with a per-item concurrency of max_metric_concurrency (default 1).

Registering a metric by name

For a metric you reuse across runs, register it once at import time and then reference it by string — the same way you use built-ins:

from qym.metrics.registry import register_metric

register_metric("has_citation", citation_score, score_type="boolean")

For a metric used directly by one evaluator, prefer the more visible typed wrapper:

from qym import Evaluator, Metric

evaluator = Evaluator(
    task=my_task,
    dataset=my_dataset,
    metrics=[Metric(citation_score, score_type="boolean")],
)
metrics = ["has_citation", "exact_match"]

Custom names shadow built-ins. Lookup checks the custom registry before the built-ins, so registering a metric named contains or correctness replaces the built-in of that name. Use it deliberately to override a built-in, or pick a unique name to avoid surprises. An unknown name raises ValueError: Metric '<name>' not found. Available metrics: ... with the full sorted list.

Testing your metric

A custom metric is plain Python — test it directly, before it ever touches a run:

def test_citation_score():
    assert citation_score("Answer [1]")["score"] == 1.0
    assert citation_score("Answer")["score"] == 0.0

Then run it against a tiny 5-row dataset (a smoke run) and confirm the scores and the saved <metric>_score column look right before adding it to a large regression suite.
