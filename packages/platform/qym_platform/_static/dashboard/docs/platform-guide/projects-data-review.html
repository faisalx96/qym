PLATFORM GUIDE

Projects, data & review

Projects are the platform's access and data boundary. Their settings connect people and automation; datasets define the evidence; reviews turn analysis into reusable corrections.

Projects

The Projects page lists projects you can access, with your role and activity summary. Platform admins can create projects. A project manager can also create another project; its creator becomes its first manager.

Project Settings contains five areas:

TabPurpose
GeneralName, slug, description, current role, member count, and status.
MembersAdd people and assign MEMBER or MANAGER. Only managers/admins can change membership, and the final manager cannot be removed or demoted. Removing a member revokes their API keys for the project.
API KeysCreate project-bound Bearer keys, identify them by name/prefix, and revoke eligible keys.
LLM ConnectionsAdd, edit, test, choose a default, or remove providers used by AI-assisted root-cause analysis.
Danger ZoneAdmins can archive the project (reversible), unarchive it, or delete it permanently.

Archive hides; Delete removes. Archiving takes the project out of the project list and switcher, stops its API keys and makes it read-only, but deletes nothing. Admins and its members still open it from Admin → Projects or a link: its runs list, run pages, compare, dashboard, charts, models, datasets and settings stay readable under a read-only notice, and nothing can be changed until an admin unarchives it. Auto-analysis and Reviews stay hidden meanwhile. Access can still be taken away: admins and managers revoke API keys and remove members in Project Settings, and an admin can delete the project. Deleted runs of an archived project wait in Trash with their purge paused (Deleted Runs says so); the countdown resumes where it stopped after the unarchive. Runs still in progress lose their remaining results when their keys stop, so the Archive dialog lists them first. Unarchiving asks first and names the API keys that start working again, so you can revoke any of them before the project comes back. Deleting is permanent and removes the project's datasets, API keys, members, LLM connections and analysis settings after you type the project name. A project that still has runs, including runs in Trash, cannot be deleted: its runs must be deleted and then purged from Trash after the deleted-run grace period, which does not count time spent archived. Until then, archive it.

API keys

Any project member may create a key. The raw token is shown once; save it immediately. Later lists show only metadata and the first eight-character prefix. A key is fixed to one project, so use a different key for every project and environment.

QYM_BASE_URL=https://qym.example.com
QYM_API_KEY=<token-shown-once>

A key's creator, a project manager, or a platform admin may revoke it. Stored scope labels are informational today and are not enforced; project membership is the security boundary.

LLM connections

Project members can manage connections used by root-cause analysis. Give each connection a provider, model, endpoint where applicable, and secret key; test it before setting it as default. Secrets are encrypted at rest when the operator has configured the platform encryption key.

The analyzer uses the project's default connection, or the first available connection when no default is set. Approved corrections from Reviews provide reusable examples for later analysis.

For a repeat run the analyzer first asks which sample (pass) to analyze, and loads only that sample's items. Switching samples with the Sample selector stays on the page; it waits while a background analysis is still running.

Datasets

The dataset catalog is project-scoped. Import CSV or JSONL to create a dataset, then work through its version lifecycle:

  1. Create or clone a draft.
  2. Add, edit, bulk upsert, or remove items while it is a draft.
  3. Publish the nonempty version to make its content immutable.
  4. Assign an alias such as production to a published version.

Who can do what with a dataset: every project member creates datasets and drafts, edits draft items, publishes drafts and renames a dataset's display name. Moving the production alias (which decides what future evaluations run on) and changing a dataset's slug (which SDK and CI references use) need a project manager; a dataset's creator may still set production on its first publish. Deleting needs the dataset's creator or a project manager. Each delete, restore, slug change, publish and production move is recorded with who did it. Controls a member cannot use are disabled and say which role can.

Deleting a dataset moves it, with every version, item and history entry, to Deleted datasets (a link in the catalog header). A project manager can restore it there under its original slug; if another dataset took that slug or name meanwhile, rename that one first. Deleted datasets are not purged automatically.

Inside a dataset, use:

  • Items for search (it matches item IDs, inputs, expected outputs and metadata values), labels, item editing, revision history, neighboring items, and each item's linked runs. Each row's index is a link: Tab reaches it, Enter opens the item, and it opens in a new tab like any link;
  • Runs for evaluations that used the dataset or selected version;
  • Lineage for version ancestry and change counts, with each version's creation and publish time, and a Change log listing every upload, draft, publish and alias move oldest first, with its time and who made it; and
  • Compare for item-level differences between two versions. Changes are listed in the order they happened, oldest first, each with its time (the head version's creation time when an item has no recorded edit). Each list loads 50 rows at a time (Show more loads the next 50), the first rows open expanded, and the open list stays in the URL. Word changes are highlighted; a field too large to highlight is shown side by side with a note. Download diff saves the complete diff.

The version switcher, row menus and the upload wizard work from the keyboard: arrow keys move through versions and menu items, Enter chooses, and Escape closes and returns focus. In the upload wizard each column gets an Import as choice (Input, Expected output, Metadata, Item ID or Ignore). Columns qym does not recognise start as Metadata, so nothing is dropped unless you choose Ignore. Closing the wizard after choosing a file asks before discarding it.

Downloads are JSONL. To change published content, create a new draft from that version rather than editing it in place.

Reviews and corrections

Reviews collects root-cause and solution corrections from manual work and AI analysis. It opens on the queue: the To review tab with the pending corrections, how many are left, and how many of the corrections in view are already reviewed. Switch to Approved, Rejected, or All with the status tabs. Sort the list oldest first, lowest AI confidence first, or most recent first, and filter by source, task, dataset, model, run, confidence, and text. Pending corrections carry a priority tag: High when the AI was under 50% confident, or a reviewer changed a diagnosis it was under 75% sure of; Medium for one weaker signal (under 75% confidence, a changed diagnosis, or a wait of 14 days or more). Hover the tag for its reasons.

The list loads 25 corrections at a time and adds more as you scroll. Each card shows a short preview of the input, expected, and output; open it to load the full text and its revision and review history. The Run chip on a card opens the item it is about in that run; on the all-projects Reviews page a Project chip names the project. Filters live in the address (?status=pending&model=…&q=…), so a filtered queue can be shared or bookmarked, and ?id=<review> highlights one review.

StatusMeaning
PendingWaiting for a human decision.
ApprovedAccepted and available as a few-shot example for future analysis.
RejectedRetained for audit, but excluded from analyzer examples.

You can edit a correction, approve or reject it with a comment, reset it to pending, or delete it. Select several corrections for bulk approve, reject, reset, or delete; the confirmation names the tab and filters the selection came from, and the action is refused if a selected correction was edited, removed, or moved to another status (for example by another reviewer) in the meantime. Editing an approved correction sends the new text back to Pending: it is reviewed again, and the earlier approval stays in its history.

Project settings decide who reviews corrections. Who can approve corrections is either all project members (the default) or project managers and admins; it covers approve, reject and reset, single or bulk, on Reviews and on the run page. Require a different reviewer (off by default) keeps the person who wrote a correction from deciding it; an AI diagnosis taken as it is has no human author. When a rule stops you, the buttons are disabled and their tooltip names the rule. A correction decided by its own author is marked Self-approved or Self-rejected. Anyone can still delete a correction they wrote; deleting someone else's needs the right to decide it.

Keyboard: j/k move between corrections, a approves and moves to the next, r rejects with a reason, e edits, o opens details, x selects, Shift+A approves the selection, / searches, and ? lists the shortcuts.

Deleted runs

Deleting a run is soft-delete: it leaves active views but keeps its data and deletion audit details. Deleted Runs is visible only to platform admins, who can restore a run to its project. Retention permanently removes a deleted run and all its results after a grace period (QYM_DELETED_RUN_GRACE_DAYS, 30 days by default); the page shows each run's purge date and flags runs with fewer than 3 days left. It lists every deleted run, 50 per page, with its project; search by run name or ID, filter by project, and select several runs to restore them at once. Restore stays pinned to the right edge of the table.
