PLATFORM GUIDE

Run detail & item analysis

Run detail moves from summary to evidence: first the execution context and aggregate behavior, then each item's input, outputs, metric results, trace, and review data.

Start with the run header

The header identifies the run, status, owner, task, model, dataset, version, timing, configuration, and execution context. A repeat run also shows its pass count. Available submit, approve, reject, export, and delete actions follow ownership and project-role rules.

While the run is RUNNING or PENDING the page follows it: new items and scores appear in place, Runtime counts up, and Live · updated Ns ago beside the status says when it last checked. Filters, the page, opened items and your scroll position stay as they are. Checking pauses while the browser tab is hidden. When the run ends, the page loads it once more and stops.

Task, model, owner, and dataset are links: they open the Runs list filtered to that task, model, or owner, and the dataset opens its dataset page (its Runs tab) when the run used a managed dataset version, or the Runs list filtered to the dataset name otherwise. Copy link copies a link to the run as you see it: the pass you are viewing and the item view (filters, search, sort, page, layout and analysis metric). Export HTML downloads the run as a standalone file.

Under the header actions, the up and down arrows open the previous and next run of the Runs list you came from, in its order and with its filters, search and sort, also across its pages; the count beside them (for example 12 of 140) is this run's place in that list. A run opened from anywhere else, or from a link, steps through the project's Runs list newest first with no filters, and so does a run that is no longer in the list you came from (its count says so on hover). The arrows are links: Tab reaches them, and they are dimmed at the first and last run.

The header's Compare with previous opens Compare with the previous finished run of the same task, model and dataset as the baseline, and notes the change in the primary metric between the two run means. It is hidden when there is no earlier run.

Move around the page

Under the header, a section bar stays at the top while you scroll. It links to each section on the page (Overview, Latency and traces, Deep analysis, Categories, Step latency, Errors with its error count, and Items with the filtered and total item counts) and underlines the section you are reading. Once the bar sticks it also shows the run name and status, and an arrow back to the top. Filters and Clear sit on the right of the bar because they scope every section, not only the item list; the filter builder drops down under the bar, and Escape or a click outside closes it. When a filter changes, the sections above you re-render without moving the section you are reading.

Overview

The overview begins with item, completion, and error counts. A completed run whose items did not all report an outcome (the platform rejected their events) also shows Not received: those items carry that tag instead of a verdict and are left out of the metric means and of Execution success. Metric cards adapt to their type:

  • Boolean metrics show pass/fail rates.
  • Percentage or score metrics show an average and score distribution.
  • Numeric metrics show minimum, average, maximum, and total.
  • Latency shows distribution and percentile landmarks.

Click a distribution segment to filter the items; an empty bar holds no items and does nothing. The Pass and Fail segments of a metric that declares a pass rule, and any Error segment, also take you to the item list, where a banner says what it now holds (for example, "Filtered to 16 items that fail correctness") and offers Clear filter. The overview is filtered too. Deep analysis appears when the run has enough item-level evidence and can show metric relationships and quality-versus-latency behavior. Filtering, sorting and paging keep you where you are: the sections update in place, and the rows on screen stay (dimmed) until the new ones arrive.

Trace stats shows only what the run captured. A run without LLM or tool spans says so instead of showing empty tiles. Step latency distributions start collapsed; open them from their header (this browser remembers the choice). Its Export menu downloads the CSV summary, the raw spans CSV, or the plot as SVG.

Repeat-run analysis

For samples=k, the repeat section adds a metric picker, pass threshold, group metrics, a pass sweep, accuracy-versus-k analysis, correct-pass distribution, and stability views.

A repeat run judges task errors per pass. Each item's value is the mean over its passes: a pass whose task or scorer failed counts as 0, or is left out when lower is better. Which pass failed does not matter, including the last one.

MeasureInterpretation
Pass@kCapability: at least one of k executions passes.
Pass^kReliability: all k executions pass.
Avg@kAverage score across executions.
Max@kAverage of each item's best execution.
ConsistencyHow often repeated outcomes agree.
ReliabilityFor items solved at least once, how often attempts solve them.

The pass sweep gives each pass's metrics, average and median latency, errors, and completed items. Change the metric or threshold to recompute the pass/fail interpretation without rerunning.

Open one pass

Click a pass in the Runs expansion or an item's pass heading. The Pass N/k lens replaces every item's reduced values with that pass's output, metrics, latency, status, error, and trace. Use the pass pill to return to the all-pass view.

Items

Each collapsed item is one row of aligned columns: its number, its Pass/Fail status for the displayed metric, the input, the reason it failed, and its metric values. When the metric values do not fit on one line, the displayed metric comes first and the rest collapse into +N more (hover it for the values); on narrower screens the values move to a second line.

Why an item failed

A row that fails the displayed metric shows a one-line reason (hover it for the full text) with its source underneath. The first of these that exists is shown:

  1. task error: the item's task failed; its error message.
  2. scorer error: the metric raised (status error, failed or timeout).
  3. reason: the metric's reason, or an error recorded without an error status (older metrics stored verdict reasons there).
  4. explanation: the metric's explanation.
  5. label: the metric's label.
  6. no reason recorded: the score and what a pass needs, such as "Scored False, pass needs True".

Other metadata keys are not read. To get a precise reason, have the metric return reason in its metadata.

Search inputs and outputs, sort by index, score, or latency, and use Display to choose the analysis metric, threshold, item metadata columns, and metric-detail fields. Repeat runs also offer Cards and Heatmap layouts. Export the current filtered item set with CSV.

The address bar keeps the item view: the filters (bar clicks and the filter builder), search, sort, page, the Cards or Heatmap layout and the analysis metric with its pass threshold. Reload, Back and a copied address open the same view, filtered from the first moment.

To share one item, open it and use Copy link beside its input, or copy the address bar: it names the item you opened (?item=<item id>, plus &pass=N in a pass view). The link opens the run on that item's page, expanded and highlighted.

Inputs and outputs show exactly as stored (Raw) by default. Display › Text › Rendered formats markdown in prose while code and SQL stay as stored; the choice is remembered in this browser, and Compare has the same switch.

Build precise filters

Open Filters in the section bar, add conditions, and choose whether AND or OR joins them. Groups can be nested. Filter fields include every metric, item categories, approval state, output text, errors, edited metrics, retries, trace errors, and latency.

AND — every rule below must match
  correctness  is  failed
  faithfulness ≥ 0.80
  Has error    false

For a metric's passed/failed operator, the run's current threshold is used. Direct comparisons such as >= 0.8 use the value you enter. This makes an AND query across several metrics explicit; adding separate chart filters is not a substitute.

AND means the same item must satisfy every condition. Use OR when any condition may qualify the item, and a nested group for combinations such as “failed correctness AND (error OR slow).”

Read a classic item

Expand a card to see the full input, expected output, system output, latency, trace, metric strip, metadata, and root-cause fields. A metric row shows its score, opens judge or metric details when recorded, and exposes score editing. Edited values are marked Edited; hover the badge to see who changed the score, when, from which value to which, and the original score. The reset action beside it gives the score back its original value (on a repeat run, resetting the item resets each of its edited passes). Every edit and reset is recorded in the audit log. Scores of a submitted or approved run are locked: a note at the top of the page says so, and a project manager can reject or unapprove the run to reopen them.

Compare repeat outputs and variants

A repeat item opens into synchronized pass columns. Each column shows one pass's output, pass/fail verdict for the selected analysis metric, latency, trace, metric values, and edit control. Toggle pass headings to hide or show columns.

The output header reports how many distinct variants occurred. Variant identity uses exact output equality after trimming and collapsing whitespace. It is not a semantic or fuzzy match.

Per-pass metric explanations

Click a metric in any pass column to align that metric's recorded explanation or structured metadata beneath the visible columns. If the run did not store pass-specific details, the page says so and shows the run-level metric detail instead. Editing a pass score updates that pass and the run's reduced item score.
