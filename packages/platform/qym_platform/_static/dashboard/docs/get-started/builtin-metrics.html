Built-in metrics tour

qym ships a small set of metrics you can use by name — no code required. Seven work offline; seven more call an OpenAI-compatible LLM and require the optional openai client at execution time. This page lists their exact names and behavior.

How metrics are selected

You pass metrics to the Evaluator as a list. Each entry can be a string (the registry name of a built-in), a legacy callable, or a typed Metric(...) wrapper. Use the wrapper for custom metrics so qym can validate and correctly display booleans, percentages, counts, and raw numbers. See Metrics (deep dive).

from qym import Evaluator, CsvDataset

result = Evaluator(
    task,
    CsvDataset("qa.csv"),
    metrics=["exact_match", "contains", my_custom_metric],
).run(show_tui=False)

When you pass a string, qym looks it up in the metric registry. If the name is not registered, it raises ValueError with this exact message:

Metric 'X' not found. Available metrics: conciseness, contains, correctness, correctness_llm, exact_match, faithfulness, faithfulness_llm, fuzzy_match, hallucination, relevance, response_time, token_count, tool_calling, toxicity

List them from code or CLI. Run qym metric list, or in Python from qym import list_available_metrics; list_available_metrics(). Judge names are registered even before the optional client is installed.

The seven built-ins (no extras)

These are registered unconditionally and run with zero external dependencies — no API key, no network. The registry name is on the left; note that several differ from the function name in the source.

NameWhat it measuresReads from the itemReturns
exact_matchOutput equals expected after str().strip() on both sides.output, expected1.0 / 0.0
containsLowercased expected appears as a substring of lowercased output.output, expected1.0 / 0.0
fuzzy_matchSequence-similarity ratio via difflib.SequenceMatcher.output, expectedContinuous 0.0–1.0
correctnessSQuAD-style token-level F1 between output and expected (lowercased, articles & punctuation stripped).output, expectedContinuous 0.0–1.0
faithfulnessFraction of meaningful (non-stopword) output tokens that also appear in the context. A heuristic, not an LLM.output, input_data["context"]Continuous 0.0–1.0
response_timePlaceholder. Always returns 1.0 regardless of input.output (ignored)Always 1.0
token_countRough token estimate: word count × 1.3, floored to an int.outputInteger count

The name is contains, not contains_expected. The function in the source is called contains_expected, but it is registered under the name contains. Use the registry name in your metrics=[...] list. Passing "contains_expected" raises the "not found" error above.

faithfulness (code) is not faithfulness_llm (judge). The built-in faithfulness is a dependency-free token-overlap heuristic. The LLM-based version is a separate judge registered as faithfulness_llm and requires openai when called.

Behavior notes worth knowing

  • fuzzy_match's threshold argument is inert. The function accepts threshold=0.8 but never applies it — the returned value is always the raw similarity ratio. (You can't pass it via a string name anyway; string metrics call the function with default arguments.)
  • response_time and token_count are placeholders. response_time always returns 1.0 — actual latency is captured by the evaluator elsewhere, not by this metric. token_count is a whitespace-based estimate, not a real tokenizer.
  • None handling. exact_match, contains, and fuzzy_match score 0.0 when either side is None. correctness coerces None to the empty string before comparing.
  • faithfulness reports why it scored 0. An empty output scores {"score": 0.0, "metadata": {"reason": "Empty output"}}. With no context in the input it cannot judge, so it records a metric error: {"score": 0.0, "error": "No context found in input_data"}. It looks for context at input_data["context"] and, failing that, input_data["input"]["context"].

How built-ins read your task output

If your task returns the output envelope — a dict that is exactly {"output": ..., "metadata": {...}} — the built-in metrics automatically unwrap it and score the inner output value. You don't have to strip the envelope yourself.

def rag_task(question):
    docs = retrieve(question)
    answer = generate(question, docs)
    # The envelope: built-ins score `answer`, the platform hides `metadata`
    return {"output": answer, "metadata": {"retrieved": len(docs)}}

Custom metrics see the whole envelope. Auto-unwrapping is a convenience of the built-ins only. A custom metric receives the full envelope as its output argument — read output["output"] and output["metadata"] yourself. See Custom metrics.

LLM-as-judge metrics

Seven additional metrics use an OpenAI-compatible model to grade each output and return a verdict label plus the model's explanation. The names are always registered; install the optional client before executing one:

pip install openai

Each judge fills its prompt from your dataset's fields — {output} and {expected} are filled automatically, and any other {variable} is pulled from the matching key in the item's input dict.

NameWhat it evaluatesVerdict labels (score)Prompt variables it reads
relevanceDoes the response address the question?relevant (1.0) / irrelevant (0.0){question}, {output}
faithfulness_llmIs the response supported by the context?faithful (1.0) / unfaithful (0.0){context}, {question}, {output}
correctness_llmDoes the response match the expected answer in meaning?correct (1.0) / incorrect (0.0){question}, {expected}, {output}
concisenessIs the response concise rather than padded?concise (1.0) / verbose (0.0){question}, {output}
hallucinationIs the response grounded in the context, or invented?grounded (1.0) / hallucinated (0.0){context}, {output}
toxicityIs the response free of harmful content?non-toxic (1.0) / toxic (0.0){output}
tool_callingAre the tool calls correct for the question?correct (1.0) / incorrect (0.0){question}, {tool_definitions}, {tool_calls}

Higher is always better. For every judge, 1.0 is the good outcome — including the safety ones. toxicity scores 1.0 for non-toxic and 0.0 for toxic; hallucination scores 1.0 for grounded. There is no "lower is better" judge in the built-in set.

tool_calling reads {tool_calls}, not the output. Its prompt expects three input fields — {question}, {tool_definitions}, and {tool_calls} — all sourced from your item's input dict. Put the calls your agent made under a tool_calls key in the input, not in the task's return value.

Configuring the judge model

Judges have no default model. Before a run reaches a judge you must set the model and an API key, or the judge raises RuntimeError at evaluation time. Configuration comes from environment variables:

export QYM_JUDGE_MODEL=gpt-4o-mini        # required: no default
export QYM_JUDGE_API_KEY=sk-...           # required (falls back to OPENAI_API_KEY)
export QYM_JUDGE_BASE_URL=https://...     # optional (falls back to OPENAI_BASE_URL)

If the model or key is missing, the raised error names the missing variables verbatim, e.g. LLM judge metrics require configuration. Missing: QYM_JUDGE_MODEL. You can also configure programmatically with JudgeConfig:

from qym.metrics import JudgeConfig, set_default_judge_config

set_default_judge_config(JudgeConfig(model="gpt-4o-mini", api_key="sk-..."))

Judges call the model with response_format={"type": "json_object"}, so any OpenAI-compatible endpoint that supports JSON mode (including vLLM and similar self-hosted servers) works via QYM_JUDGE_BASE_URL. Temperature defaults to 0.0 and each call has its own 60.0s timeout with retry/backoff.

Dependencies and credentials fail differently. A judge without openai raises ImportError when called. With the client installed but no configured model or key, JudgeConfig.validate() raises RuntimeError. The judge name remains registered in both cases.

Custom and pairwise judges

When the built-in judges don't fit, build your own with the factories from qym.metrics.judges. create_judge takes a name, a prompt template using {variable} placeholders, and a choices dict mapping verdict labels to scores:

from qym.metrics.judges import create_judge

helpfulness = create_judge(
    name="helpfulness",
    prompt="Is this response helpful?\n[Question]: {question}\n[Response]: {output}",
    choices={"helpful": 1.0, "partial": 0.5, "unhelpful": 0.0},
)

result = Evaluator(task, dataset, metrics=[helpfulness]).run(show_tui=False)

For comparative evaluation, create_pairwise_judge compares two outputs (A vs B) and uses a fixed set of choices: {"A": 1.0, "B": 0.0, "tie": 0.5}. Its prompt exposes {output_a} and {output_b} (B is taken from input_data["output_b"], falling back to expected).

Missing prompt fields fail before the LLM call. If a prompt references a field that is not available, qym raises JudgeInputError naming the missing and received fields. Use matching dataset keys or input_mapping.

Return shapes, in brief

Built-ins return one of three shapes, all normalized into a MetricResult internally: a bare number (mapped straight to score), a {"score": ..., "metadata": {...}} dict, or — for judges — a full MetricResult carrying score, label, and explanation. One detail to know now: a metric that returns a dict containing an "error" key is recorded with score 0.0 and excluded from aggregate scoring rather than dragging the average down silently. The full return-type contract for your own metrics lives in Metrics (deep dive).

Picking a starter set

Short factual answers

Start with exact_match; add contains when wording may vary but a key fact must appear. Reach for correctness (F1) when partial credit matters.

Typo / format tolerance

fuzzy_match for OCR, transcription, or near-miss formatting where a continuous similarity score is more useful than pass/fail.

RAG / grounding

Begin with the offline faithfulness heuristic (needs a context field). Upgrade to faithfulness_llm or hallucination after installing openai and configuring a judge provider.

Open-ended quality

Use judges — relevance, conciseness, correctness_llm — when there's no single correct string and you need a model's judgment with an explanation.

Combine cheap and expensive. Mix a deterministic metric (free, instant) with a judge (slower, paid) in the same metrics=[...] list. The deterministic one catches obvious regressions; the judge handles nuance. Each metric scores every item independently.
