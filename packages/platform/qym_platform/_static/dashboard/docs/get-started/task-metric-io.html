Task & metric I/O structure

The one contract worth memorizing: a dataset item flows into your task, your task returns an output, and that output flows into your metrics. Get the shapes right at each hop and everything else in qym just works.

Every qym run is the same four-step pipeline, repeated once per dataset item:

dataset item  -->  task(input)  -->  output  -->  metric(output, expected, ...)  -->  score

This page is the high-level map of what each step receives and what it must hand to the next. For the full reference on writing tasks, custom metrics, and configs, follow the links to the SDK Guide as you go.

1. The dataset item

Every item — whether it came from a local CSV, a JSONL file, an in-memory list, or a qym platform dataset — is normalized to the same four fields before your task ever sees it:

FieldTypeWhat it is
idstringStable identifier for the item. Auto-generated from a content fingerprint when you don't supply one.
inputany JSON valueThe payload passed to your task. A string, number, list, or dict.
expected_outputany JSON value or NoneThe reference answer. Passed to metrics as expected. Optional, but most built-in metrics need it.
metadatadictSide data about the item (category, difficulty, source, etc.). Not passed to the task; available to metrics.

These names are fixed at the item level. When you load from a CSV with different column names, you remap them at load time (input_col=, expected_col=, id_col=, metadata_cols=) — see Using datasets & reaching data in code.

2. What the task receives

Your task is called once per item and receives only that item's input — not the whole item. qym inspects your function's signature and resolves the call for you, so you can name your parameter whatever reads well.

Smart argument resolution

How input maps onto your parameters depends on both the input's shape and your signature:

Your functionItem inputHow qym calls it
def task(question)"What is 2+2?"task(question="What is 2+2?")
def task(x)"What is 2+2?"task(x="What is 2+2?") — any single name works
def task(q, context){"q": "...", "context": "..."}task(q=..., context=...) — dict keys matched to params
def task(item){"q": "...", "context": "..."}task(item={...}) — single param, no key match → whole dict
def task(**kwargs){"q": "...", "context": "..."}task(q=..., context=...)
def task(question, schema){"sql_prompt": "...", "sql_context": "..."} plus input_mappingtask(question=..., schema=...) — CSV names remapped before the call

In short: a dict input is unpacked into matching keyword arguments when your parameter names line up (or when you accept **kwargs or have more than one parameter). A non-dict input goes to your single parameter. A single parameter that matches no dict key receives the whole dict.

CSV input mapping

When a local CSV has multiple input columns, CsvDataset(input_col=[...]) produces a dict input. If the column names are not the task parameter names, pass input_mapping to Evaluator. The mapping direction is dataset input name → task parameter name:

dataset = CsvDataset(
    "text2sql.csv",
    input_col=["sql_prompt", "sql_context"],
    expected_col="sql",
)

def task(question, schema):
    return generate_sql(question=question, schema=schema)

Evaluator(
    task=task,
    dataset=dataset,
    metrics=[valid_sql],
    input_mapping={
        "sql_prompt": "question",
        "sql_context": "schema",
    },
)

The original input dict is preserved for saved artifacts and display. Metric input_data uses the mapped names, while metrics can still request either the original names (sql_prompt, sql_context) or the mapped names (question, schema) as individual parameters.

Auto-injected parameters

Three parameter names are special. If your task declares any of them, qym fills them in automatically — they are not drawn from the item input:

Parameterqym injects
model or model_nameThe model being evaluated (the current entry of model=[...], or the configured single model). Add this to support multi-model runs.
trace_idThe trace identifier for the current item, for correlating your own logging.
 
async def task(question, model_name="gpt-4o-mini"):
    # `question` comes from item.input; `model_name` is injected by qym
    return await call_llm(model=model_name, prompt=question)

Sync or async, your choice. An async def task is awaited directly on the event loop; a plain def task is run in a worker thread so it never blocks the loop. Prefer async for I/O-heavy LLM calls — qym warns if a sync client (e.g. requests.get) blocks the loop inside an async def.

3. What the task returns

Your task's return value becomes the item's output. There are exactly two accepted shapes:

A plain value (the common case)

Return a string, number, list — anything that is not a dict. That value is the output, stored as-is and passed straight to your metrics.

def task(question):
    return "Paris"   # output = "Paris"

The output envelope (when metrics need extra detail)

To expose supporting data to metrics without polluting the visible output, return a dict in qym's envelope shape. It must contain exactly the keys output and metadata, and metadata must be a dict:

def rag_task(question):
    docs = retrieve(question)
    answer = call_llm(question, context=docs)
    return {
        "output": answer,                       # the visible output
        "metadata": {"retrieved_context": docs} # hidden, for metrics
    }
  • The visible output shown in the platform and saved to artifacts is the envelope's output field only.
  • The envelope's metadata is merged into the item's stored metadata under task_metadata.

Dict returns are reserved. Any dict return is treated as the envelope. If the keys are not exactly {output, metadata} (or metadata isn't a dict), qym raises InvalidTaskOutputError for that item — e.g. {"answer": "Paris"} is rejected because qym can't tell which field is the visible output. To return a literal dict as your output, wrap it: {"output": {...}, "metadata": {}}.

4. What the metric receives

Each metric is called once per item with the task output and the item's reference data. qym resolves a metric's arguments much like it resolves a task's — by inspecting the signature — but the set of available values is different. These are the names qym recognizes:

Parameter nameValue
outputWhat the task returned (see the envelope note below).
expectedThe item's expected_output (or None).
input_dataThe item input, using mapped field names when input_mapping applies.
task_metadataThe hidden metadata dict returned by the task-output envelope, or {}.
metadata or item_metadataThe item's metadata dict. Both names resolve to the same value.
any key in a dict inputThat individual input value. If input_mapping is set, both the original and mapped names are recognized.

Naming vs. positional order

If your metric's parameter names are all drawn from the recognized set above, qym passes them by keyword — order doesn't matter. If you use names outside that set, qym falls back to positional order:

position 1 -> output
position 2 -> expected
position 3 -> input_data
position 4 -> item_metadata
# Recognized names -> matched by keyword (order-independent)
def my_metric(expected, output):
    return 1.0 if output == expected else 0.0

# Custom names -> matched by POSITION (order is load-bearing)
def my_metric(result, ground_truth):   # result=output, ground_truth=expected
    return 1.0 if result == ground_truth else 0.0

Declare only the parameters you actually use; a one-arg def m(output) and a four-arg def m(output, expected, input_data, metadata) are both valid.

The envelope, from the metric's side

This is the subtle part. When your task returns the {output, metadata} envelope, the two kinds of metric see output differently:

  • Built-in metrics auto-unwrap. They read only the envelope's inner output value, so exact_match compares the visible answer, never the wrapper.
  • Custom metrics receive the full envelope. Your function's output argument is the entire {"output": ..., "metadata": ...} dict, so you can reach task metadata via output["metadata"].
# Task returned {"output": "Paris", "metadata": {"confidence": 0.95}}

def confidence(output, expected):
    # custom metric: `output` is the whole envelope
    return output["metadata"]["confidence"]      # -> 0.95

# Built-in "exact_match" on the same item compares "Paris" to expected

5. What the metric returns

A metric can return any of these shapes; qym normalizes them all into a structured score:

Return valueBecomes
True / Falsescore 1.0 / 0.0
an int or floatthat numeric score
{"score": 0.85, "label": "good", "explanation": "...", "metadata": {...}}score plus optional label, explanation, and per-metric metadata
a MetricResult objectused directly

One special case: a dict containing an "error" key is recorded with score 0.0 and the error stashed in metadata, so a single broken metric doesn't crash the item. A metric that raises an exception is also caught and recorded as a failure rather than aborting the run.

Metrics have a wall-clock budget. Each metric attempt is capped by metric_timeout (default 60.0s) and retried up to metric_max_retries times (default 2). Exhausted timeouts become ordinary metric errors: visible in item detail, excluded from the mean, and counted against metric success rate. Tune both fields in Configs & options.

Putting the hops together

A single end-to-end view of one item flowing through the pipeline:

from qym import Evaluator, CsvDataset

# item: input="What is the capital of France?", expected_output="Paris"
data = CsvDataset("qa.csv")

def task(question):              # receives item.input
    return "Paris"               # plain value -> output

def looks_capitalized(output, expected):   # recognized names
    return output[:1].isupper()  # bool -> 1.0 / 0.0

# built-in "exact_match" compares output to expected_output
Evaluator(task, data, metrics=["exact_match", looks_capitalized]).run(show_tui=False)
